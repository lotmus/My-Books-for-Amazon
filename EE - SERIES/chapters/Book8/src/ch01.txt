PART: Part I. Tools and Method
H1: Chapter 1. The Firmware Engineer's Job and a Method That Works
P: A weather node runs perfectly on your desk for a week. You screw it to the garden fence, and on the first frosty morning it stops reporting. Nothing is broken. The humidity reading went above 100 % in fog, a line of code that never expected it divided by a number that was now zero, and the watchdog that should have restarted the board was never switched on. Every one of those three mistakes would have been caught by a one-page specification and a ten-minute review. This chapter is about that page and that review.
P: Where you meet this: Every product with a microcontroller in it, every bench test that a script runs instead of a person, and every time you ask an AI assistant to write code that will touch real hardware.
P: Many products now depend on software for much of their behavior: the thermostat's control loop, the drone's attitude filter, the battery charger's state machine, and the test rig that checks each board before it ships. Engineers who can write that software and understand the hardware it controls are valuable across product, test, and validation teams. This book teaches software from the bench side. It assumes you know what a pull-up resistor does (Book 1), how a MOSFET switches a load (Book 2), and roughly why a radio link has a range (Books 4 and 5). It does not assume you have written much code.
H2: 1.1 Four languages, one bench
P: Four languages cover nearly everything an electronics engineer writes. C, with a little C++, runs on the microcontroller, because it compiles to small, fast machine code and gives direct access to hardware registers. Python runs in two places: as MicroPython or CircuitPython on the board, where it is the quickest way to try a sensor, and as ordinary Python on the PC, where it drives instruments, logs data, and plots results. C# runs on the PC, where Visual Studio and .NET make serial dashboards, test benches, and unit tests unusually productive, and, through .NET nanoFramework and Meadow, on some microcontrollers too. The fourth language, Verilog, describes hardware rather than instructions; Chapter 26 shows how it becomes a circuit inside an FPGA.

H2: 1.2 What firmware is, and why it is different
P: Firmware is software that controls hardware directly and usually runs without an operating system, or with a very small one. Three things make it different from the code on a laptop. First, it shares the world with physics: a pin that changes 1 µs too late can break a protocol, and a loop that never sleeps empties a battery. Second, it often cannot be watched: there is no screen, sometimes no serial port, and the bug appears only on a cold morning on a fence. Third, it must survive on its own for months, so every error has to be expected, handled, and recovered from without a person.
P: Those three facts explain the habits of good firmware engineers. They measure timing with a scope instead of trusting it. They design for the failure first and the feature second. And they work in small, tested steps, because a bug that slips through costs hours to find on hardware and days to fix in the field.
H2: 1.3 The method
P: Every worked example in this book follows the same nine steps. They are deliberately ordinary. Their value is that you do all of them, every time, whether you write the code yourself, copy it from a forum, or ask an AI assistant for it.
P: 1. Write a short spec: purpose, hardware, pins, interfaces, timing, power, error handling, and acceptance tests.
P: 2. Break the job into small modules, each with one responsibility and a clear interface.
P: 3. Write, or prompt for, one module at a time, with the spec attached.
P: 4. Review the code against a checklist before running it.
P: 5. Build it and unit-test it on the PC, where tests are fast and repeatable.
P: 6. Test it on the hardware, with the scope or logic analyzer confirming the timing.
P: 7. Commit it to version control with a message that says what changed and why.
P: 8. Iterate with precise bug reports: what you did, what you expected, what you measured.
P: 9. Document it: the spec, the pin map, the test results, and the known limits.

P: The spec does not need to be long. One page is enough for most modules, and a good spec is mostly numbers: which pins, which bus speed, how often, how much current, how long the module may block, and what it must do when the sensor does not answer. The template below is the one this book uses. Copy it into the top of a project's README and fill it in before writing any code.
P: Spec template (one page per module or feature)
LI: Purpose: one sentence. What the module does and for whom.
LI: Hardware: board, chip, sensor or actuator, supply voltage, logic level.
LI: Pins: every GPIO with its direction, pull-up or pull-down, and active level.
LI: Interfaces: bus and speed (I2C 400 kHz, UART 115200 8N1, SPI mode 0 at 8 MHz), addresses, data formats, units.
LI: Timing: how often it runs, deadlines, the longest it may block, and its startup time.
LI: Power: active and sleep current targets, and when it may sleep.
LI: Error handling: what happens on a timeout, a bad checksum, an out-of-range value, a lost connection.
LI: Acceptance tests: numbered, measurable checks that decide when the module is done.
LI: Out of scope: what this module deliberately does not do.
P: The review checklist is the other half. It is short enough to use on every module and specific enough to catch the bugs that firmware really has.
P: Review checklist (use before the first run)
LI: Pins and addresses match the spec and the schematic, not a tutorial.
LI: Bus speed, baud rate, mode, and byte order match both ends.
LI: Every wait has a timeout; nothing blocks forever.
LI: Interrupt handlers are short, set a flag or send to a queue, and call no blocking or printing functions.
LI: Shared variables are volatile or protected, and multi-byte values are read atomically.
LI: Every return code is checked, and every error path does something sensible.
LI: Units and scaling are written down and tested at both ends of the range.
LI: No secrets, passwords, or keys in the source code.
LI: Every library call exists in the version you build against; check the documentation for each one you have not used before.
LI: A watchdog or a recovery path exists for the case nobody thought of.

P: Key idea. The method is not paperwork. It moves bug-finding from the fence post, where it costs a day, to the desk, where it costs a minute. The spec states what correct means; the checklist and the tests prove it.
H2: Worked Example 1.1: A spec for the garden weather node
P: Problem. Write the spec for the reader lab's weather node: an ESP32-S3 that reads the BME280 every 10 seconds, shows the values on the OLED, and logs them to a 4 MB flash partition. Each log record holds a 4-byte timestamp and three 4-byte floats. How many days of records fit before the log wraps?
P: Solution. Purpose: measure and log temperature, humidity, and pressure in the garden. Hardware: ESP32-S3 board, BME280 and SSD1306 OLED, both at 3.3 V. Pins: I2C SDA on GPIO 8, SCL on GPIO 9, external 4.7 kΩ pull-ups (the pull-up sizing is Book 1's). Interfaces: I2C at 400 kHz; BME280 at address 0x76, chip ID 0x60; OLED at 0x3C. Timing: one reading every 10 s, the I2C transaction may block at most 10 ms. Power: mains-powered in this version. Error handling: three failed reads in a row show "SENSOR?" and keep retrying; humidity is clamped to 0 to 100 %. Acceptance tests: (1) temperature within 1 °C of a reference thermometer, (2) a pulled sensor cable is reported within 30 s and recovers when reconnected, (3) 24 hours without a reset. Out of scope: wireless, which comes in Chapter 17. The record is 4 + 3 × 4 = 16 bytes. A day holds 86 400/10 = 8640 records, or 138 240 bytes. The partition holds 4 194 304 bytes, so the log lasts 4 194 304/138 240 = 30.3 days before it wraps. The usual mistake is to write the spec after the code, when it describes what was built instead of what was needed.
H2: Worked Example 1.2: Splitting the node into modules
P: Problem. Split the weather node of Worked Example 1.1 into modules, and decide which can be unit-tested on the PC.
P: Solution. Five modules, each with one job: bme280 (read raw registers and compensate them into °C, %, and hPa), display (draw three lines on the OLED), logger (append 16-byte records to the flash ring), scheduler (run the others every 10 s and count failures), and main (startup and pin setup). The compensation math in bme280, the ring-buffer arithmetic in logger, and the failure counting in scheduler are pure functions of their inputs, so they compile and run on the PC with test data. Only the thin layer that touches the I2C peripheral and the flash chip needs the board. That split is the point: most of the logic, and most of the bugs, can be tested in seconds without hardware.
H2: 1.4 What firmware engineers actually do
P: The work is less heroic and more interesting than it looks from outside. A typical week mixes reading data sheets and errata, writing and reviewing drivers, chasing a timing bug with a logic analyzer, writing test scripts, and arguing with the hardware engineer about which side owns a problem. The most valuable skill is not typing code fast; it is turning a vague symptom into a precise, reproducible bug report.
P: On the Job
P: Embedded work is one of the largest areas of electronics employment, in cars, medical devices, appliances, industrial controls, drones, and smart-home products. The chips are STM32, ESP32, NXP, Infineon, and Renesas parts; the tools are a vendor IDE or VS Code, a debug probe, a logic analyzer, git, and a continuous-integration server that builds and tests every commit. A realistic first task: bring up a new revision of a sensor board, confirm the I2C sensor answers, measure the sleep current, and write the test script that production will run on every unit.
H2: 1.5 AI assistants on the bench
P: AI coding assistants, built into code editors or used as separate chat tools, now write many first drafts, including firmware. They are fast and often right about general programming, and they are most often wrong about the specific things that matter in embedded work: pin numbers, register addresses, bus settings, and the exact API of the library version you use. The method above is how to use them safely. Give them the spec, ask for one module, review against the checklist, test on the PC and then on the bench. Chapter 25 develops this in full; most chapters carry a short note on what assistants tend to get wrong in that chapter's topic.
P: AI Pair-Programming Note
P: Paste the filled-in spec template into the prompt and ask for one module. An assistant that sees "BME280 at 0x76 on GPIO 8 and 9, I2C 400 kHz, at most 10 ms blocking" produces far better code than one asked to "read a BME280".
BENCH: Keep a lab notebook, paper or text file, for every board. Write the date, the firmware commit, what you changed, and what you measured. When a problem comes back three weeks later, the notebook is usually the fastest debugger you own.
H2: Practice
P: 1. (Core) Name the four languages of this book and one job each does best.
P: 2. (Core) A log record has an 8-byte timestamp and four 2-byte integers. How many records fit in a 1 MB (1 048 576 byte) partition?
P: 3. (Core) At one record per 30 s, how many days does the partition of Problem 2 last?
P: 4. (Core) Write the Timing line of a spec for a button that must be recognized within 50 ms and an OLED that refreshes twice per second.
P: 5. (Extension) A module reads a sensor that sometimes does not answer. Write two acceptance tests for its error handling.
P: 6. (Extension) Which modules of the weather node in Worked Example 1.2 need the real board for testing, and why?
P: 7. (Extension) Rewrite the bug report "the display is broken" as a precise report.
P: 8. (Challenge) The weather node must keep 90 days of 16-byte records at one per 10 s. How big must the partition be, and what could you change if the flash only has 4 MB free?
