H1: Chapter 11. Register Level versus HAL
P: HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_5) is one line of C. Underneath, it reads a register, flips a bit, and writes a 32-bit value to an address that the reference manual calls GPIOA_BSRR, 0x40020018. One day the library call will be too slow, will not exist for the feature you need, or will hide a bug, and on that day the reference manual and its register tables are the only documentation that is never wrong. This chapter goes down one layer, and then explains why you will usually come back up.
P: Where you meet this: Every vendor HAL, every "why is this pin not toggling", every peripheral feature the library does not expose, and every job interview that asks what volatile is for.
H2: 11.1 The layers
P: Firmware sits on a stack of layers. At the bottom are the peripheral registers: memory addresses where reading or writing bits controls the hardware. Above them, a thin layer of definitions turns addresses into names; for Arm chips that is CMSIS, the vendor's header files that define structs such as GPIOA->BSRR. Above that, the vendor's hardware abstraction layer, ST's HAL and LL, the Pico SDK's hardware_ functions, Espressif's drivers, wraps sequences of register writes into functions with checking. Your drivers and your application sit on top. The Arduino framework and MicroPython add one more layer above the vendor's.

H2: 11.2 Reading a register map
P: A reference manual describes each peripheral by a base address and a list of registers at offsets from it. For the STM32F411's GPIO port A the base is 0x40020000. MODER, at offset 0x00, holds two mode bits per pin. ODR, at 0x14, is the output data. BSRR, at 0x18, is the bit set/reset register: writing 1 to bit n (0 to 15) sets pin n, writing 1 to bit n + 16 resets it, and zeros do nothing. It exists so that one write changes some pins without reading or disturbing the others, which makes it safe even if an interrupt changes another pin of the same port at the same time.
P: Listing 11.1 — Register-level blink on an STM32F411: enable the port clock, set the mode bits, and write BSRR (C).
P: // Register-level blink on an STM32F411 Nucleo (LED LD2 on PA5), no HAL.// Addresses from the STM32F411 reference manual (RM0383).#include <stddef.h>#include <stdint.h>typedef struct {    volatile uint32_t MODER, OTYPER, OSPEEDR, PUPDR, IDR, ODR, BSRR, LCKR, AFR[2];} gpio_regs_t;_Static_assert(offsetof(gpio_regs_t, BSRR) == 0x18, "BSRR must be at offset 0x18");#define RCC_AHB1ENR (*(volatile uint32_t *)0x40023830u)#define GPIOA       ((gpio_regs_t *)0x40020000u)#define LED_PIN     5ustatic void delay(volatile uint32_t n) { while (n--) { } }int main(void){    RCC_AHB1ENR |= 1u << 0;                                // clock the GPIOA block first    GPIOA->MODER = (GPIOA->MODER & ~(3u << (LED_PIN * 2))) // 2 mode bits per pin                 | (1u << (LED_PIN * 2));                  // 01 = general-purpose output    for (;;) {        GPIOA->BSRR = 1u << LED_PIN;                       // set PA5: one write, no read        delay(400000);        GPIOA->BSRR = 1u << (LED_PIN + 16);                // reset PA5        delay(400000);    }}
H2: Worked Example 11.1: One write, two pins
P: Problem. Find the single BSRR value that sets PA5 and resets PA6. Why is it safer than ODR |= (1 << 5); ODR &= ~(1 << 6);?
P: Solution. Setting PA5 needs bit 5: 0x0000 0020. Resetting PA6 needs bit 6 + 16 = 22: 0x0040 0000. Together: 0x0040 0020. The two ODR statements each read ODR, modify it, and write it back. If an interrupt between the read and the write changes another pin of port A, the main code's write restores the old value and undoes the interrupt's change. The BSRR write has no read, so there is nothing to undo, and both pins change in the same clock cycle.

H2: 11.3 The HAL, honestly
P: The HAL version of the same blink, Listing 11.2, is longer to set up and shorter to read. It enables the clock with a named macro, configures the pin with a struct that names every option, and toggles with a function. It is portable across the STM32 family, CubeMX generates most of it, and colleagues can read it without the reference manual. Its costs are a little speed and code size, and a habit of hiding things: HAL_Delay depends on the SysTick interrupt, so calling it inside an interrupt handler of higher priority hangs forever.
P: Listing 11.2 — The same blink with the STM32 HAL (C).
P: // The same blink with the STM32 HAL (as generated by STM32CubeIDE, trimmed).#include "stm32f4xx_hal.h"int main(void){    HAL_Init();                                 // SysTick at 1 kHz, flash settings    __HAL_RCC_GPIOA_CLK_ENABLE();    GPIO_InitTypeDef io = {0};    io.Pin = GPIO_PIN_5;    io.Mode = GPIO_MODE_OUTPUT_PP;    io.Pull = GPIO_NOPULL;    io.Speed = GPIO_SPEED_FREQ_LOW;    HAL_GPIO_Init(GPIOA, &io);    for (;;) {        HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_5);        HAL_Delay(500);                         // ms, from the SysTick counter    }}
P: The RP2040 shows the other side of the argument. Its SDK's gpio_put is an inline function that compiles to one write to the single-cycle I/O block (SIO) at 0xd0000000, so there is nothing to gain by bypassing it, and its sio_hw struct gives direct access when you want two pins to change in the same cycle, as Listing 11.3 does with the toggle register.
P: Listing 11.3 — The Pico SDK's gpio_put and the SIO set, clear, and toggle registers it uses (C).
P: // RP2040: the SDK call and the register write it becomes (Pico SDK).// sio_hw points at the single-cycle I/O block at 0xd0000000.#include "pico/stdlib.h"#include "hardware/structs/sio.h"#define PIN_A 2#define PIN_B 3int main(void){    gpio_init(PIN_A);    gpio_init(PIN_B);    gpio_set_dir(PIN_A, GPIO_OUT);    gpio_set_dir(PIN_B, GPIO_OUT);    const uint32_t mask = (1u << PIN_A) | (1u << PIN_B);    for (;;) {        gpio_put(PIN_A, 1);            // SDK: inline function writing the SIO set register        sio_hw->gpio_clr = 1u << PIN_A;// direct: GPIO_OUT_CLR at offset 0x018        sio_hw->gpio_togl = mask;      // both pins flip in the same cycle    }}
H2: Worked Example 11.2: How fast can a pin toggle?
P: Problem. A disassembly shows that a register-level toggle loop on a 125 MHz RP2040 takes 4 cycles per iteration, and a loop calling a non-inline library function takes 24 cycles. Find the toggle rates and the resulting square-wave frequencies.
P: Solution. 125 MHz/4 = 31.25 million toggles per second; a square wave needs two toggles per period, so 15.6 MHz. With 24 cycles: 5.2 million toggles per second, a 2.6 MHz square wave. A factor of six matters for bit-banging a protocol; it does not matter for an LED. For anything faster or more regular, the RP2040's PIO state machines or a hardware peripheral generate the waveform without the CPU. The method's step 6 applies: measure the pin on a scope rather than trusting cycle counts, because flash wait states and interrupts change them.
H2: 11.4 DMA: letting the hardware copy
P: Direct memory access is a peripheral that copies data between memory and other peripherals without the CPU. Firmware configures a source, a destination, a length, and a trigger, such as "SPI transmit buffer empty", and the DMA controller moves each byte when the trigger fires, interrupting the CPU only when the whole transfer is done. It is how a display refreshes, an ADC streams samples at a steady rate, and a UART receives a burst while the CPU sleeps.
H2: Worked Example 11.3: What DMA buys the OLED
P: Problem. The OLED frame of Worked Example 10.1 takes 1.02 ms over SPI at 8 MHz. At 30 frames per second, what fraction of the CPU does a waiting transfer use, and what does DMA leave?
P: Solution. 30 × 1.02 ms = 30.7 ms per second, 3.1 % of the CPU spent waiting. With DMA the CPU spends a few microseconds per frame starting the transfer and handling the completion interrupt, roughly 0.01 %. The catch is that the frame buffer must not be changed while the DMA reads it: draw into a second buffer and swap when the completion interrupt arrives (double buffering). On the ESP32-S3, the SPI master driver uses DMA automatically for large transfers, and the buffer must be in DMA-capable internal RAM.
P: Key idea. Use the HAL by default and the registers on purpose: for speed, for features the HAL lacks, or to understand what the HAL is doing. Either way, the reference manual is the authority.
P: Common misconception. Register-level code is always faster. Modern SDK functions are often inline and compile to the same single write; the speed gain is real only in tight loops that call non-inline functions, and the maintenance cost is paid on every future change.
P: AI Pair-Programming Note
P: Register addresses and bit positions are where assistants are least reliable: they confidently produce offsets from a different chip family or a different peripheral. Check every address and bit against the reference manual, and prefer the vendor's header names (GPIOA->BSRR) over raw numbers, so the compiler checks the names.
BENCH: When a peripheral does nothing at all, check its clock enable first. On STM32 parts every peripheral's clock is off after reset, and writes to an unclocked peripheral's registers are ignored. In a debugger, read the register back: if it still shows the reset value after your write, the clock is off.

H3: What You’ll Actually Use
P: Everyday working tools
LI: Base address plus offset; bit fields from the reference manual.
LI: Atomic set and reset registers (BSRR, SIO set/clear/xor) instead of read-modify-write.
LI: Clock enable first, and read back to confirm.
LI: DMA with double buffering or circular half-transfer interrupts.
P: Mostly for exams and deeper study
LI: Writing a whole HAL of your own; you will read one more often than you write one.
