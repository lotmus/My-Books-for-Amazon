H1: Chapter 13. FreeRTOS: Tasks, Queues, and Real Time
P: On 4 July 1997 the Mars Pathfinder lander touched down, and within days it began resetting itself. The cause, found by engineers on Earth reproducing the fault, was a textbook case of priority inversion: a low-priority task held a shared resource, a high-priority task waited for it, and medium-priority tasks kept the low one from finishing. The watchdog saw the high-priority task miss its deadline and reset the computer. One configuration flag, priority inheritance on the shared mutex, fixed it, uploaded from Earth. A real-time operating system gives you tasks that make firmware easier to write, and it gives you new ways to fail.
P: Where you meet this: ESP-IDF (FreeRTOS is always running underneath it), most STM32 projects beyond a blink, drones, audio, network stacks, and any product with more than three things to do at different rates.
H2: 13.1 Tasks and the scheduler
P: A task is a function with its own stack that runs as if it had the CPU to itself. The scheduler decides which task runs: in FreeRTOS, always the highest-priority task that is ready, and among equal priorities, each in turn at every tick. A task that waits, for a delay, a queue, or a semaphore, is blocked and uses no CPU, so lower-priority tasks run. That is the big gain over the super loop: a slow job no longer delays a fast one, because the fast one has a higher priority and preempts it.
P: The tick is a periodic interrupt that drives time in the RTOS. ESP-IDF's default is 100 Hz, a 10 ms tick; many STM32 projects use 1000 Hz. Delays are counted in ticks, so their resolution is one tick, a fact that Worked Example 13.2 turns into a bug.

H2: Worked Example 13.1: Is the task set schedulable?
P: Problem. The weather node has a sensor task (0.4 ms every 10 ms), a display task (8 ms every 100 ms), and a LoRa task (60 ms every 60 s). Find the total CPU load and compare it with the rate-monotonic bound for three tasks, n(2^(1/n) − 1).
P: Solution. Loads: 0.4/10 = 4 %, 8/100 = 8 %, 60/60 000 = 0.1 %; total 12.1 %. The bound for three tasks is 3(2^(1/3) − 1) = 0.780, so 78 %. With priorities assigned by rate (fastest period, highest priority), every task meets its deadline when the total is under the bound, and 12.1 % is far under it. The bound is sufficient, not necessary; above it, a timeline like Figure 13.1 decides. The numbers come from measurement: toggle a GPIO in each task and read the durations with a logic analyzer.
H2: 13.2 Queues and semaphores
P: Tasks must exchange data without the races of Chapter 3. A queue copies fixed-size items from a producer to a consumer, and a consumer that waits on an empty queue blocks without using CPU. A binary semaphore signals that something happened, for example from an ISR to a task. A mutex protects a shared resource, such as an I2C bus used by two tasks, and in FreeRTOS a mutex includes priority inheritance: while a high-priority task waits for it, the holder temporarily runs at that high priority. That is the Pathfinder fix.
P: Listing 13.1 — A sensor task feeding a display task through a queue, with a fixed-rate delay, a receive timeout, and a stack check (ESP-IDF, C).
P: // Two FreeRTOS tasks and a queue on the ESP32-S3 (ESP-IDF 5.x): the sensor task// produces readings every 100 ms, the display task consumes them.#include <stdint.h>#include "freertos/FreeRTOS.h"#include "freertos/queue.h"#include "freertos/task.h"#include "esp_log.h"typedef struct { int32_t t_x100; uint32_t seq; } reading_t;static const char *TAG = "rtos";static QueueHandle_t q;static void sensor_task(void *arg){    TickType_t next = xTaskGetTickCount();    uint32_t seq = 0;    for (;;) {        reading_t r = { .t_x100 = 2341, .seq = seq++ };   // stand-in for the BME280 read        if (xQueueSend(q, &r, 0) != pdTRUE)               // never block the producer            ESP_LOGW(TAG, "queue full, reading %lu dropped", (unsigned long)r.seq);        vTaskDelayUntil(&next, pdMS_TO_TICKS(100));       // fixed rate, no drift    }}static void display_task(void *arg){    reading_t r;    for (;;) {        if (xQueueReceive(q, &r, pdMS_TO_TICKS(1000)) != pdTRUE) {            ESP_LOGW(TAG, "no reading for 1 s");            // spec: detect a dead sensor task            continue;        }        ESP_LOGI(TAG, "#%lu  %ld.%02ld C", (unsigned long)r.seq,                 (long)(r.t_x100 / 100), (long)(r.t_x100 % 100));        if (r.seq % 50 == 0)                               // stack check every 5 s            ESP_LOGI(TAG, "display stack free: %u bytes",                     (unsigned)uxTaskGetStackHighWaterMark(NULL));    }}void app_main(void){    q = xQueueCreate(16, sizeof(reading_t));    // ESP-IDF stack sizes are in bytes; higher number = higher priority    xTaskCreate(sensor_task, "sensor", 3072, NULL, 6, NULL);    xTaskCreate(display_task, "display", 4096, NULL, 4, NULL);}
H2: Worked Example 13.2: The 5 ms delay that is zero
P: Problem. At the ESP-IDF default tick of 100 Hz, what do vTaskDelay(pdMS_TO_TICKS(5)) and vTaskDelay(pdMS_TO_TICKS(15)) actually wait? What about 25 ms?
P: Solution. pdMS_TO_TICKS multiplies by 100 and divides by 1000 with integer arithmetic. 5 ms becomes 500/1000 = 0 ticks, and vTaskDelay(0) only yields: no delay at all. 15 ms becomes 1 tick, and because the delay starts somewhere inside the current tick, it ends at the next tick boundary, 0 to 10 ms later. 25 ms becomes 2 ticks, 10 to 20 ms. Listing 13.2 prints the table. A sensor that needs 5 ms between commands gets 0 ms and returns garbage. Raise the tick to 1000 Hz in menuconfig, or use a hardware timer or esp_rom_delay_us for short waits, and never rely on a delay of one or two ticks for timing.
P: Listing 13.2 — The arithmetic of pdMS_TO_TICKS at a 100 Hz tick (C, runs on the PC).
P: // Why vTaskDelay(pdMS_TO_TICKS(5)) does not wait 5 ms at a 100 Hz tick: run on the PC.#include <stdint.h>#include <stdio.h>typedef uint32_t TickType_t;#define configTICK_RATE_HZ 100u                               // the ESP-IDF default#define pdMS_TO_TICKS(ms) ((TickType_t)(((TickType_t)(ms) * (TickType_t)configTICK_RATE_HZ) / (TickType_t)1000u))int main(void){    const unsigned ms[] = { 5, 10, 15, 25, 100 };    for (int i = 0; i < 5; i++) {        TickType_t t = pdMS_TO_TICKS(ms[i]);        unsigned lo = t ? (t - 1) * 1000u / configTICK_RATE_HZ : 0;   // delay starts mid-tick        unsigned hi = t * 1000u / configTICK_RATE_HZ;        printf("%3u ms -> %u ticks -> real delay %u to %u ms\n", ms[i], (unsigned)t, lo, hi);    }    return 0;}
H2: Worked Example 13.3: Sizing a queue and a stack
P: Problem. A producer can deliver bursts of 20 readings within 50 ms; the consumer handles one reading every 5 ms. How deep must the queue be? The display task's stack is 4096 bytes and uxTaskGetStackHighWaterMark reports 1200 bytes never used. Is the stack size right?
P: Solution. During the 50 ms burst the consumer removes 10 readings, so 10 accumulate; the queue needs at least 10 slots, and 16 gives margin for a late consumer. Each reading_t is 8 bytes, so 16 slots cost 128 bytes. The stack used at most 4096 − 1200 = 2896 bytes. A margin of about 25 % is a common rule, so 1200 bytes free, 29 %, is acceptable, provided the test exercised the deepest path, for example a log message with formatting, which uses a lot of stack. On ESP-IDF stack sizes and the high-water mark are in bytes; in standard FreeRTOS they are in words of 4 bytes, a factor of four that trips people moving between the two.

P: Key idea. Give each job its own task, give the fastest jobs the highest priorities, connect tasks with queues, protect shared resources with mutexes, and never wait without a timeout.
P: Common misconception. More tasks make firmware faster. Every task needs its own stack and adds context switches and synchronization. Group jobs that run at the same rate and share data into one task; use a separate task when a job must wait or must preempt another.
P: On the Job
P: Firmware engineers spend more time on concurrency bugs than on almost any other kind: a reading occasionally lost, a display that freezes after three days, a deadlock between two mutexes taken in opposite orders. The professional habits are a written task table (name, period, priority, stack, worst-case time), a rule for the order in which mutexes are taken, trace tools such as SEGGER SystemView or Percepio Tracealyzer that record every context switch, and a soak test that runs the product for days with the logic analyzer watching.
P: AI Pair-Programming Note
P: Assistants regularly call blocking APIs from ISRs (xQueueSend instead of xQueueSendFromISR), pass portMAX_DELAY everywhere, give stack sizes in words to ESP-IDF, or use vTaskDelay(1) as if it were 1 ms. Each one is on the review checklist; add "tick rate: 100 Hz" and "stack sizes in bytes" to the spec you paste into the prompt.
BENCH: Measure, do not guess, a task's timing: set a GPIO high when the task starts its work and low when it blocks, one pin per task, and record all of them on a logic analyzer for a few seconds. The capture is the real Figure 13.1 of your system, and preemption, jitter, and missed deadlines become visible at a glance.
