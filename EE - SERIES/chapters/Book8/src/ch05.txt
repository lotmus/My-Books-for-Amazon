H1: Chapter 5. C# for Electronics: .NET on the Desktop and on the Chip
P: The board works, the serial monitor scrolls numbers, and your manager asks for "a little window with a graph and a big red light when the pressure drops". In C# with Visual Studio that window is an afternoon's work: drag a chart onto a form, open the serial port, parse the lines, and bind the values to the display. Test engineers have built production rigs this way for twenty years, and the same language now runs on an ESP32 too.
P: Where you meet this: Serial dashboards, production test benches, calibration tools, configuration utilities shipped with a product, and unit tests that check firmware logic on the PC.
H2: 5.1 Why C# belongs in an electronics book
P: C# is a statically typed language that runs on .NET, Microsoft's open-source runtime for Windows, Linux, and macOS. Three things make it unusually productive for bench software. The tooling is excellent: Visual Studio and VS Code with the C# Dev Kit give a debugger, refactoring, and IntelliSense that knows every method's signature, which catches many mistakes before the program runs. The libraries cover the bench: System.IO.Ports for serial ports, sockets and HTTP for networked instruments, and mature charting and plotting packages. And the desktop frameworks, WPF and WinForms on Windows, WinUI 3 for modern Windows apps, and .NET MAUI across Windows, macOS, Android, and iOS, turn a parser into a usable tool with little extra code.
P: C# catches many type errors at compile time. A .NET application can be published as a self-contained, single-file executable for a target operating system and architecture, which can simplify deployment; native libraries and framework-specific requirements may still add steps. Compared with C, C# manages memory automatically and has safe strings and collections, so whole classes of crashes disappear. The trade-off is that C# on a PC is not hard real-time: the operating system and garbage collector can delay your code, a fact Worked Example 5.1 measures.

H2: 5.2 A serial console in C#
P: The SerialPort class opens a COM port (or /dev/ttyACM0 on Linux) with a baud rate, parity, data bits, and stop bits, and reads text lines or raw bytes. Listing 5.1 is the C# counterpart of Chapter 4's Python logger. Three details matter more than the rest. The read timeout means the program notices a dead board instead of hanging. The invariant culture means “23.41” parses as twenty-three point four one in a locale such as de-DE, where the decimal separator is a comma; without it, parsing follows the active locale and can reject or misread machine-readable data. And every line is checked before it is used.
P: Listing 5.1 — A .NET console program that reads and validates the reader lab's CSV lines (C#).
P: // .NET console app: read "t,h,p" lines from the ESP32-S3 and print them with checks.// Project: dotnet new console; dotnet add package System.IO.Portsusing System;using System.Globalization;using System.IO.Ports;class SerialConsole{    static void Main(string[] args)    {        string portName = args.Length > 0 ? args[0] : "COM5";        using var port = new SerialPort(portName, 115200, Parity.None, 8, StopBits.One)        {            NewLine = "\r\n",            ReadTimeout = 2000           // ms; never wait forever        };        port.Open();        Console.WriteLine($"Listening on {portName}. Ctrl+C to stop.");        while (true)        {            try            {                string line = port.ReadLine();                string[] f = line.Split(',');                if (f.Length == 3 &&                    double.TryParse(f[0], NumberStyles.Float, CultureInfo.InvariantCulture, out double t) &&                    double.TryParse(f[1], NumberStyles.Float, CultureInfo.InvariantCulture, out double h) &&                    double.TryParse(f[2], NumberStyles.Float, CultureInfo.InvariantCulture, out double p))                    Console.WriteLine($"{DateTime.Now:HH:mm:ss}  {t,6:F2} °C  {h,5:F1} %  {p,7:F2} hPa");                else                    Console.WriteLine($"bad line: {line}");            }            catch (TimeoutException)            {                Console.WriteLine("no data for 2 s - is the board running?");            }        }    }}
H2: Worked Example 5.1: A 10 ms timer on a 15.625 ms system tick
P: Problem. A dashboard uses a System.Threading.Timer with a 10 ms period to poll a board 100 times per second. Suppose it runs on a Windows configuration whose effective timer granularity is 15.625 ms. What rate might it achieve, and how do you check the actual rate on the PC that will run the dashboard?
P: Solution. On a configuration where callbacks are constrained by a 15.625 ms timer granularity, they may arrive about every 15.6 ms, roughly 64 per second rather than 100. System.Threading.Timer uses thread-pool callbacks, and scheduling, system configuration, or load can change the observed intervals; this is an example, not a guarantee for every Windows PC. Listing 5.2 measures 200 callbacks with a Stopwatch. If polling rate matters, let the firmware stream at a fixed rate with its hardware timer and timestamp each sample on the board; let the PC read what has arrived.
P: Listing 5.2 — Measuring the real period of a 10 ms timer with a Stopwatch (C#).
P: // Measure what a 10 ms System.Threading.Timer really delivers on this PC.using System;using System.Diagnostics;using System.Threading;class TimerCheck{    static void Main()    {        const int N = 200;        var stamps = new double[N];        int n = 0;        var sw = Stopwatch.StartNew();        using var done = new ManualResetEventSlim(false);        using var timer = new Timer(_ =>        {            if (n < N) stamps[n++] = sw.Elapsed.TotalMilliseconds;            if (n == N) done.Set();        }, null, 0, 10);              // ask for one tick every 10 ms        done.Wait();        double mean = (stamps[N - 1] - stamps[0]) / (N - 1);        Console.WriteLine($"requested 10.0 ms, measured mean {mean:F2} ms ({1000 / mean:F1} Hz)");    }}

H2: Worked Example 5.2: How long until the receive buffer overflows?
P: Problem. SerialPort's default receive buffer holds 4096 bytes. The board streams continuously at 115 200 baud, 8N1. The dashboard's UI thread freezes while a file dialog is open. How long can it stay frozen before data is lost, if nothing else reads the port?
P: Solution. The byte rate is 115 200/10 = 11 520 bytes per second. The buffer fills in 4096/11 520 = 0.36 s. A file dialog stays open for seconds, so data is lost almost every time. The fix is architectural, not a bigger number: read the port on a background thread or with the DataReceived event, push complete lines into a thread-safe queue, and let the UI take what it needs on its own timer (Chapter 22). Raising ReadBufferSize to 64 KB only stretches the margin to 5.7 s.
H2: 5.3 C# on the microcontroller
P: .NET nanoFramework is an open-source runtime that runs a subset of C# on microcontrollers, including the ESP32 family and several STM32 boards. You write and debug in Visual Studio with breakpoints on the real chip, and you add hardware support as NuGet packages such as nanoFramework.System.Device.Gpio and drivers for common sensors. The code is interpreted, so it is slower than C and uses more memory, but for a sensor node or a control panel the productivity is the point. Meadow, from Wilderness Labs, takes a different route: its own boards run full .NET on an STM32F7, with a large driver library.

P: On the Job
P: In production test departments, C# is common for test executives and station software: the program that powers a board, runs fifty measurements, compares each with limits, prints a label, and writes the result to a database. A realistic task is to add a new measurement to such a station: write the step, its limits, and its xUnit test, then validate it on ten known-good and two known-bad boards before release.
P: AI Pair-Programming Note
P: Assistants write good WPF and SerialPort code, with two recurring flaws: updating UI controls directly from the serial thread, which throws a cross-thread exception, and parsing numbers with the PC's culture. Put "use the invariant culture; marshal UI updates through the Dispatcher" in the prompt, and check both in review.
BENCH: Windows renumbers COM ports when a board is plugged into a different USB socket. A dashboard that hard-codes COM5 fails on the next desk. List the ports with SerialPort.GetPortNames() and let the user pick, and remember the last choice in a settings file.
