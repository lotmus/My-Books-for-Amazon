H1: Appendix A. Quick Reference: Formulas, Spec Template, Review Checklist, and Prompt Skeleton
H2: A.1 Formulas used in this book
P: Build sizes (Chapter 2): flash = text + data; static RAM = data + bss, plus stack and heap.
P: Bit operations (Chapter 3): set r |= m; clear r &= ~m; toggle r ^= m; read a field (r & mask) >> shift.
P: Timer and PWM (Chapter 7): f_PWM = f_clk/((PSC + 1)(ARR + 1)); duty = CCR/(ARR + 1). Servo pulses of 1.0 to 2.0 ms in a 20 ms frame.
P: Ultrasonic ranging (Chapter 7): d = c t/2, with c ≈ 331.3 + 0.606 T m/s for T in °C; 5.824 ms of echo is 1.000 m at 20 °C.
P: ADC (Chapter 8): code = V_in/V_ref × 2^N and V_in = code × V_ref/2^N; averaging n samples divides random noise by √n; a two-point calibration fits gain and offset.
P: UART (Chapter 9): one bit lasts 1/baud, 8.68 µs at 115 200 baud; an 8N1 frame is 10 bits, 86.8 µs.
P: Average current and battery life (Chapter 14): I_avg = (I_active t_active + I_sleep t_sleep)/T; life ≈ capacity/I_avg, reduced by self-discharge and the cell's usable fraction.
P: Fixed point (Chapter 15): a Qm.n value is the integer divided by 2^n; Q15 covers −1 to 1 − 2^−15 in steps of 1/32 768. A first-order IIR filter y ← y + (x − y)/2^k has a time constant of −1/ln(1 − 2^−k) samples, 15.5 samples for k = 4.
P: Complementary filter (Chapter 16): angle ← α(angle + ω Δt) + (1 − α) angle_acc, with time constant τ = α Δt/(1 − α). Kalman gain in one dimension K = P/(P + R).
P: LoRa duty cycle (Chapter 18): the shortest legal interval is airtime/duty cycle, 123.9 ms/0.01 = 12.4 s at SF9 for 8 bytes. The airtime formula is Book 5's.
P: Reconnect back-off (Chapter 17): wait = min(cap, base × 2^attempt), less up to 25 % random jitter.
P: Time of flight (Chapter 20): t = 2d/c; each centimeter of range adds 66.7 ps of round-trip time.
P: Int8 quantization (Chapter 20): q = round(x/s) + z, clipped to −128..127; x ≈ s(q − z). For the range −2 to 6, s = 8/255 = 0.03137 and z = −64.
P: RC low-pass corner (Chapter 21): f_c = 1/(2πRC), 1591.5 Hz for 10 kΩ and 10 nF.
P: Test limits with guard band (Chapter 22): accept only readings inside the specification limits shrunk by the measurement uncertainty on each side.
P: Ring buffer (Chapter 24): with free-running counters and a power-of-two size N, the index is count & (N − 1) and the fill level is head − tail, which stays correct across counter wrap-around.
P: HDL counters (Chapter 26): an N-bit PWM counter at f_clk gives f_clk/2^N, 105.5 kHz for 8 bits at 27 MHz; a UART divider of 27 000 000/115 200 rounds to 234, giving 115 385 baud, 0.16 % fast.
H2: A.2 Spec template
LI: Purpose: one sentence. What the module does and for whom.
LI: Hardware: board, chip, sensor or actuator, supply voltage, logic level.
LI: Pins: every GPIO with its direction, pull-up or pull-down, and active level.
LI: Interfaces: bus and speed (I2C 400 kHz, UART 115200 8N1, SPI mode 0 at 8 MHz), addresses, data formats, units.
LI: Timing: how often it runs, deadlines, the longest it may block, and its startup time.
LI: Power: active and sleep current targets, and when it may sleep.
LI: Error handling: what happens on a timeout, a bad checksum, an out-of-range value, a lost connection.
LI: Acceptance tests: numbered, measurable checks that decide when the module is done.
LI: Out of scope: what this module deliberately does not do.
H2: A.3 Review checklist
LI: Pins and addresses match the spec and the schematic, not a tutorial.
LI: Bus speed, baud rate, mode, and byte order match both ends.
LI: Every wait has a timeout; nothing blocks forever.
LI: Interrupt handlers are short, set a flag or send to a queue, and call no blocking or printing functions.
LI: Shared mutable data is accessed atomically or protected by an appropriate lock or critical section; volatile alone does not make shared access thread-safe. Use volatile for memory-mapped I/O or asynchronous observations only when the platform requires it.
LI: Every return code is checked, and every error path does something sensible.
LI: Units and scaling are written down and tested at both ends of the range.
LI: No secrets, passwords, or keys in the source code.
LI: Every library call exists in the version you build against; check the documentation for each one you have not used before.
LI: A watchdog or a recovery path exists for the case nobody thought of.
H2: A.4 Common AI mistakes in firmware
LI: Pins from a different board: the classic ESP32's I2C pins 21 and 22 on an ESP32-S3, which has no GPIO 22 at all.
LI: Wrong or default addresses: a library's default I2C address instead of the one on your module.
LI: Blocking calls in interrupt handlers: delay(), Serial.print, printf, or a mutex inside an ISR.
LI: Missing pull-ups or wrong input modes: buttons and I2C lines assumed to have resistors that are not on the board.
LI: Wrong baud rate, data format, units, or byte order between the two ends.
LI: Invented or outdated library APIs: a function that sounds right but does not exist in the version you use.
LI: Wrong register names or bit positions copied from a related chip.
LI: Error handling left out: return codes ignored, no timeouts, no reconnect.
LI: Security shortcuts that make an example work: certificate checks off, passwords in the source.
H2: A.5 Prompt skeleton
LI: Role and platform: chip, board, framework and version, language.
LI: Goal: one module, one sentence.
LI: Hardware facts from the spec: pins, addresses, voltages, pull-ups, clock and baud rates.
LI: Interface: exact formats, units, decimal separator, line endings, commands and replies.
LI: Constraints: libraries by name and version, no blocking in ISRs, timeouts, memory limits.
LI: Error behavior: what happens when the sensor, the link, or the input is missing or wrong.
LI: Deliverable: the file(s), plus a list of every assumption not stated in the prompt.
H1: Appendix B. Worked Solutions to the Practice Problems
P: Each solution shows the working and, where one is common, the usual mistake. Problems are numbered as in their chapter.
H2: Chapter 1
P: 1. C (and C++) on the microcontroller, for small fast code with register access; Python on the board for quick experiments and on the PC for instruments, logging, and plots; C# on the PC for dashboards, test benches, and unit tests; Verilog for describing logic inside an FPGA. The usual mistake is to pick one language for everything: Python on a battery node, or C for a quick plot.
P: 2. The record is 8 + 4 × 2 = 16 bytes. 1 048 576/16 = 65 536 records. The usual mistake is to forget the timestamp, or to count 1 MB as 1 000 000 bytes, which gives 62 500.
P: 3. One record per 30 s gives 86 400/30 = 2880 records per day, so 65 536/2880 = 22.8 days. Check the units: records divided by records per day gives days. The usual mistake is to stop at 2185, dividing 65 536 by 30, which is a count of 30-second intervals, not days.
P: 4. "Button: sampled every 5 ms, debounced over 20 ms, recognized within 50 ms of the press. OLED: redrawn every 500 ms; a redraw may block for at most 30 ms." The usual mistake is a timing line without numbers ("the button should feel responsive"), which cannot be tested.
P: 5. (1) With the sensor disconnected, the module returns an error code within 100 ms and the display shows "SENSOR?" within one measurement period. (2) After the sensor is reconnected, valid readings resume within two periods without a reset. Each test names a measurable time. The usual mistake is "the module handles errors", which is a wish, not a test.
P: 6. Only the thin hardware layers: the I2C read in bme280, the flash writes in logger, and the OLED driver in display. They depend on real peripherals and timing. The compensation math, the ring-buffer arithmetic, and the failure counting are pure functions and run on the PC. The usual mistake is to test everything on the board, which makes every test slow and every failure ambiguous.
P: 7. "Firmware commit 3f2a1c, ESP32-S3 board B. After power-up the OLED shows the first reading, then stays blank from the second update on. Expected: a new reading every 10 s. The logic analyzer shows the I2C write to 0x3C is NACKed from the second update. Started after the change that raised I2C to 1 MHz." It says what was done, what was expected, what was measured, and when it started. The usual mistake is a report that names the symptom but not the firmware version, the board, what was expected, or what was measured.
P: 8. 90 days need 90 × 8640 = 777 600 records of 16 bytes, which is 12 441 600 bytes, about 11.9 MB, three times the 4 MB available. Options: log every 30 s instead of 10 s (one third the data, 4 147 200 bytes, which fits with only 1 % to spare), store temperature, humidity, and pressure as scaled 16-bit integers instead of floats (4 + 3 × 2 = 10 bytes, 7.8 MB at 10 s, 2.6 MB at 30 s), or keep hourly averages after the first week. The usual mistake is to change the requirement silently instead of writing the trade-off into the spec.
H2: Chapter 2
P: 1. The linker. The function was declared (in a header, so the compiler was satisfied) but no object file or library defines it: usually the .c file is not in the build (missing from CMakeLists.txt or the src folder) or the library is not linked. The usual mistake is to keep editing the header, which the linker never reads.
P: 2. Flash = 210 000 + 3 000 = 213 000 bytes. Static RAM = 3 000 + 41 000 = 44 000 bytes. The usual mistake is to count bss in flash; it costs only RAM, because the startup code zeroes it.
P: 3. 460 800/10 = 46 080 bytes per second; 600 000/46 080 = 13.0 s. Half the image at half the baud rate takes the same time. The usual mistake is to use 8 bits per byte, which gives 10.4 s and forgets the start and stop bits.
P: 4. A .uf2 file. Hold the BOOTSEL button while plugging the Pico into USB; it appears as a drive called RPI-RP2 (RP2350 on a Pico 2), and copying the file flashes it and reboots the chip. The usual mistake is to press BOOTSEL after plugging in; the button must be held while the board powers up.
P: 5. A non-const initialized array is a variable: its 1024 bytes of starting values sit in flash (data) and are copied into 1024 bytes of RAM at startup, where the program may change them. A const array never changes, so the linker places it in flash (text or rodata) and the program reads it there; it costs 1024 bytes of flash and no RAM. The usual mistake is to forget const on large lookup tables and run out of RAM. (On the ESP32 the same is true; on AVR chips such as the classic Uno, const alone is not enough and PROGMEM is needed.)
P: 6. A library or toolchain updated itself (an unpinned lib_deps entry or a framework update), or the build picked up a different board or configuration file. Prevent both by pinning library and platform versions in platformio.ini or the component manifest, and by committing the configuration (sdkconfig, platformio.ini) to version control. The usual mistake is to start editing the code before checking what changed in the toolchain and the libraries.
P: 7. Only 264 − 252 = 12 KB remain for the stack, the heap, and anything the SDK allocates at run time. The program will probably crash or behave strangely when a deep call chain or an allocation overruns that space, and the linker cannot predict it. Reduce the large buffers or move constant tables to flash. The usual mistake is to take a successful link as proof that RAM is sufficient; the linker counts only static data, not the stack and the heap.
P: 8. The image is 905 000 + 48 000 = 953 000 bytes. Adding 90 000 gives 1 043 000 bytes, which is below 1 048 576, so it fits, but with only 5 576 bytes to spare, too little for the next change. First check the map file for the largest symbols: debug logging strings, unused library features, and fonts or images are the usual suspects. The usual mistake is to compare against 1 000 000 instead of 1 048 576, or to forget that data also lives in flash.
H2: Chapter 3
P: 1. Set: r |= (uint8_t)(BIT(0) | BIT(4)), that is r |= 0x11. Clear bit 7: r &= (uint8_t)~0x80, which is r &= 0x7F. The cast avoids a conversion warning, because ~0x80 is an int with many high bits set. The usual mistake is to write r |= ~0x80 or r &= 0x80, which set or clear every other bit instead.
P: 2. 0x5A is 0101 1010; XOR with 0000 1111 gives 0101 0101 = 0x55. XOR flips exactly the bits that are 1 in the mask. The usual mistake is to confuse XOR with OR, which would give 0x5F.
P: 3. 0x1C is 0001 1100. Mask with 0x1C (bits 4..2), giving 0x1C, then shift right by 2: 0x07, so the field is 7. The usual mistake is to forget the shift and report 28.
P: 4. 2^32 µs = 4 294.97 s = 71.6 minutes, so a microsecond counter wraps every 71.6 minutes, not days. A seconds counter wraps after 4 294 967 296 s = 136 years. The usual mistake is to assume a 32-bit counter "never" wraps; at microsecond resolution it wraps many times a day.
P: 5. 180 + 90 = 270 is computed as an int and then truncated to 270 − 256 = 14 when stored. -Wconversion warns about the implicit narrowing; storing into uint16_t, or checking with an explicit test before the store, avoids it. The usual mistake is to think the addition itself overflows in 8 bits; it is computed as an int, and the value is lost at the store.
P: 6. a at 0, padding at 1, b at 2 and 3, c at 4, padding at 5 to 7, d at 8 to 11: 12 bytes. Ordered d, b, a, c: 0 to 3, 4 and 5, 6, 7: 8 bytes, the sum of the field sizes, so no smaller layout exists without packing. The usual mistake is to add the field sizes, 8 bytes, and forget the padding that alignment inserts.
P: 7. At -O2 the compiler sees that nothing in the loop changes data_ready, reads it once, and loops forever on the cached value. Declaring it volatile bool data_ready forces a fresh read each time. In an RTOS, a better fix is to block on a semaphore or queue that the interrupt gives (Chapter 13), which also lets the CPU sleep. The usual mistake is to blame the optimizer and ship at -O0, which hides the bug instead of fixing it.
P: 8. int16_t spans −32 768 to 32 767, so −327.68 °C to +327.67 °C. A reading of 400.00 °C is 40 000 hundredths, which does not fit; converted to int16_t it wraps to 40 000 − 65 536 = −25 536, which reads as −255.36 °C. Validate the range before storing (Chapter 1's checklist: units and scaling tested at both ends) and store an explicit error code instead. The usual mistake is to assume the conversion stops at 327.67 °C; it wraps to a large negative value instead.
H2: Chapter 4
P: 1. 0x60, read from register 0xD0. 0x58 is the BMP280, a pressure and temperature sensor without humidity, often sold on look-alike modules. The usual mistake is to treat 0x58 as a faulty BME280 and keep debugging the humidity code; the chip is a different part.
P: 2. 32 bytes × 10 bits = 320 bits; 320/115 200 = 2.78 ms. The usual mistake is 32 × 8 = 256 bits, which gives 2.22 ms and ignores the start and stop bits.
P: 3. MicroPython runs main.py at boot (after boot.py). CircuitPython runs code.py and restarts it whenever the file is saved to the CIRCUITPY drive. The usual mistake is to save code.py to a MicroPython board, or main.py to a CircuitPython board, and wonder why nothing runs.
P: 4. 8640 rows per day × 365 = 3 153 600 rows; × 60 bytes = 189 216 000 bytes, about 189 MB per year (180 MiB). The usual mistake is to count 6 rows per hour instead of 6 per minute, which is 60 times too small.
P: 5. 1000/0.038 s = 26 300 samples per second, but with jitter from the interpreter. A 1 kHz tone needs more than 2 kS/s, so the rate is enough on paper, but irregular sample spacing smears the spectrum. For audio, use the ADC with DMA or a timer-triggered conversion (Chapter 8), or write that part in C. The usual mistake is to look only at the average rate and ignore the jitter, which matters more than the rate for a spectrum.
P: 6. A range check against the sensor's physical limits, for example: if not (-40 <= t <= 85 and 0 <= h <= 100 and 300 <= p <= 1100): print("out of range:", line); continue. The BME280's specified operating ranges are −40 to +85 °C and 300 to 1100 hPa. The usual mistake is to check only the format, so a well-formed line with an impossible value, such as 150 °C after an I2C glitch, ends up in the log.
P: 7. The file object buffers writes in memory. If the script is stopped with Ctrl-C or the PC loses power, the buffered rows are lost and the last row can be cut in half. Flushing after every row costs little at one row per second and keeps the file valid. The usual mistake is to rely on the file being written when the script ends; a crash or Ctrl-C does not guarantee it.
P: 8. Printing to a console is slow, often slower than 576 lines per second on Windows, so the loop falls behind, the operating system's serial buffer fills, and bytes are dropped. Fixes: stop printing every line (print a summary every second), read in a separate thread into a queue and write in batches, or reduce the data rate at the board by averaging. The method step that catches this is the hardware test at the full data rate, not only at one line per second. The usual mistake is to raise the baud rate, which makes the PC side fall behind even faster.
H2: Chapter 5
P: 1. For C#: compile-time type checking and a strong debugger in Visual Studio; a single executable that runs on a test station without installing an interpreter; fast desktop UIs with WPF or WinForms. For Python: faster experimenting and a huge scientific library (numpy, pandas, matplotlib), and pyvisa for instruments. The usual mistake is to choose by habit rather than by who runs the program: an operator at a test station needs an executable, an engineer exploring data needs Python.
P: 2. 921 600/10 = 92 160 bytes per second; 4096/92 160 = 44 ms. At high baud rates the buffer covers only a few tens of milliseconds, so a background reader is mandatory. The usual mistake is to use 8 bits per byte, which gives 36 ms; the start and stop bits make it 10.
P: 3. It returns 2341. In the de-DE locale, the period is the thousands separator, and double.Parse's default number style accepts thousands separators, so the value is silently a hundred times too large, with no exception. Use double.Parse(s, CultureInfo.InvariantCulture) or TryParse with NumberStyles.Float and the invariant culture, as Listing 5.1 does. The usual mistake is to expect an exception; there is none, which is why a test suite run only with a decimal-point locale can miss the bug.
P: 4. One per tick: 1/0.015625 = 64 per second, the same as for 10 ms. Any period shorter than the tick gives the tick rate. Measure with Listing 5.2. The usual mistake is to expect 200 callbacks per second from a 5 ms setting.
P: 5. DataReceived runs on a thread-pool thread, and WPF and WinForms controls may only be touched from the UI thread that created them. Touching them from another thread throws an InvalidOperationException (WPF) or causes intermittent faults. Queue the data and update the UI through the Dispatcher or a UI timer. The usual mistake is to wrap the update in a try-catch, which hides the exception but keeps the threading bug.
P: 6. foreach (string name in SerialPort.GetPortNames()) Console.WriteLine(name); The method returns names such as COM3 and COM5 on Windows and /dev/ttyACM0 on Linux. The usual mistake is to hard-code COM3, which works on one PC and fails on the next.
P: 7. nanoFramework runs a subset of C# on many third-party boards, including the ESP32 family and some STM32 boards, and you flash its firmware onto your own board. Meadow runs full .NET, but only on Wilderness Labs' own Meadow boards. The usual mistake is to expect nanoFramework to run any .NET library; it runs its own, smaller set of packages.
P: 8. The ESP32-S3 owns the timing: a hardware timer triggers the ADC every 10 ms (Chapter 8), the firmware stores 200 samples with their sample indices, and sends the block over USB when done. The C# program starts the test with a command, waits for the block, checks that 200 samples arrived with consecutive indices, and evaluates the limits. The PC is never asked to keep 10 ms timing, which Worked Example 5.1 shows it cannot promise. The usual mistake is to let the PC keep the 10 ms timing with a Windows timer, whose 15.6 ms tick makes the specification impossible.
H2: Chapter 6
P: 1. GPIO 0, 3, 45, and 46. They are read at reset to choose the boot mode and flash voltage settings; a button that holds GPIO 0 low at power-up puts the chip into download mode instead of running the firmware. The usual mistake is to pick pins from a tutorial for a different ESP32 variant.
P: 2. Bounce ends after 4 ms; the next sample comes up to 10 ms later; two more samples take 20 ms. Worst case 4 + 10 + 20 = 34 ms. The usual mistake is to count only the three samples, 30 ms, and forget the bounce and the wait for the first sample.
P: 3. Blocking (delays or waiting for a bus), printing or logging, allocating memory, and long computation. Also any API that is not marked ISR-safe, such as the non-FromISR FreeRTOS queue calls. The usual mistake is to print from the ISR while debugging it, which blocks, slows, or crashes the very thing being debugged.
P: 4. The PIR module's output idles low and goes high on motion, and the interrupt is on the rising edge. A pull-down keeps the input low if the sensor is unplugged, so a missing sensor reads as "no motion" instead of floating and firing random interrupts. With a pull-up, an unplugged sensor would read as constant motion. The usual mistake is to enable the pull-up from habit, which makes an unplugged sensor look like permanent motion.
P: 5. 96 × 10 = 960 interrupts per second; 960 × 4 µs = 3.84 ms per second, 0.38 % of the CPU. The usual mistake is to use the turns per second alone and forget the 96 edges per turn.
P: 6. A 32-bit aligned read is a single instruction on a 32-bit core, so the main loop sees either the old or the new value, never a mix: safe, provided the variable is volatile. A 64-bit counter is read with two instructions; if the ISR increments it between them, for example from 0x00000000FFFFFFFF to 0x0000000100000000, the main loop can read 0x00000001FFFFFFFF. Disable interrupts around the read, or read the high word twice and retry if it changed. The usual mistake is to think volatile makes the 64-bit read safe; it forces two fresh reads but does not make them one.
P: 7. Keep the debouncer unchanged and test the result: if (debounce_update(&d, raw) && d.stable == false) count++; The debouncer's job is to report clean level changes; deciding which ones are presses belongs to the caller. The usual mistake is to change the debouncer itself, which breaks its test.
P: 8. Timing: a rising edge on the PIR line starts a capture within 300 ms; after a capture, further edges are ignored for 30 s; a retrigger during the lockout does not extend it. Error handling: if the camera does not answer within 2 s, log the error, skip the photo, and keep the lockout running; if the PIR line stays high for more than 60 s, report a stuck sensor. In the ISR: only timestamp the edge and send it to a queue. In the task: the lockout check, the capture, and the error handling. The usual mistake is to start the capture inside the ISR; the ISR should record the edge and its time, and nothing else.
H2: Chapter 7
P: 1. 72 MHz/1 MHz = 72, so PSC = 71. A 1 ms period is 1000 ticks, so ARR = 999. The usual mistake is PSC = 72 and ARR = 1000, forgetting that the timer divides by the register value plus one.
P: 2. Duty = CCR/(ARR + 1), so CCR = 0.25 × 4000 = 1000. The usual mistake is 0.25 × 3999 = 999.75, which forgets that the counter has ARR + 1 states.
P: 3. 20 ms/4096 = 4.88 µs per step. The usual mistake is to divide 20 ms by 12 instead of by 2¹² = 4096.
P: 4. c = 331.3 + 0.606 × 25 = 346.5 m/s. t = 2 × 2.50/346.5 = 14.43 ms. The usual mistake is to forget the factor 2 for the round trip, which gives 7.22 ms.
P: 5. 80 MHz/20 kHz = 4000 steps, log2(4000) = 11.97, so a little under 12 bits. The usual mistake is to call 4000 steps 12 bits; 12 bits would need 4096.
P: 6. 45° is a quarter of the range: 500 + 2000/4 = 1000 µs. Duty = 1000/20 000 × 16 384 = 819.2, so 819. The usual mistake is to map 45° onto the nominal 1 to 2 ms range, which gives 1.25 ms and a different angle on this servo.
P: 7. The echo width is 2 × 0.85/343 = 4.956 ms. At 35 °C, c = 331.3 + 21.2 = 352.5 m/s, so the true distance is 352.5 × 4.956 ms/2 = 0.874 m. The program reads 24 mm short. The usual mistake is to correct in the wrong direction; sound is faster when it is warm, so the true distance is longer than the reading.
P: 8. One period of 1 kHz is 1000 ticks, so one tick is 0.1 % resolution. One period of 100 kHz is 10 ticks: 10 % resolution, useless. Measure many periods instead: capture the time of 1000 periods (10 ms, 10 000 ticks) for 0.01 %, or count edges in a fixed 100 ms gate with the signal clocking a counter, which gives 10 000 counts. Faster signals need gate counting; slow ones need period timing. The usual mistake is to raise the tick rate; measuring over many periods improves the resolution more cheaply.
H2: Chapter 8
P: 1. 3.3/1024 = 3.22 mV; 2.5/65 536 = 38.1 µV. The usual mistake is to mix the conventions V_ref/2^N and V_ref/(2^N − 1) within one program; pick the data sheet's and use it everywhere.
P: 2. 3000 × 3.3/4096 = 2.417 V at the pin, × 2 = 4.834 V, which is above the 4.2 V maximum of a lithium-ion cell: check the wiring, the divider, or the reference before believing it. The usual mistake is to forget the divider and report 2.42 V, or to report 4.83 V without asking whether a lithium cell can show it.
P: 3. √64 = 8, three bits' worth. The usual mistake is to expect a factor of 64; random noise falls with the square root of the number of samples.
P: 4. On the ESP32 family ADC2 is shared with the Wi-Fi radio, and reads fail or are blocked while Wi-Fi is active. ADC1 is free for the application. The usual mistake is to choose the pin for layout convenience and discover the ADC2 conflict only when Wi-Fi is added.
P: 5. Ratio: 3.0/4.2 = 0.714 maximum. Current: 3.7 V/2 µA = 1.85 MΩ minimum total. Try R_top = 820 kΩ and R_bottom = 1.8 MΩ: ratio 1.8/2.62 = 0.687, so 4.2 V gives 2.885 V (below 3.0 V), and 3.7 V/2.62 MΩ = 1.41 µA. Add 100 nF at the pin to supply the sampling charge from such a high impedance. The usual mistake is to leave out the capacitor: without it, a megohm divider reads low because the ADC's sampling capacitor cannot charge through it in time.
P: 6. The single point makes 1.500 V read correctly, but the slope stays 2 % too steep: at 3.000 V the reading is 1.500 + 1.500 × 1.02 = 3.030 V, a 30 mV error. One point cannot fix the slope. The usual mistake is to trust a one-point calibration because it reads correctly at its calibration point.
P: 7. Nothing: the average of sixteen 1823s is 1823. Without noise, averaging cannot resolve fractions of an LSB. Either the input is quieter than one LSB (add a little dither, or accept 12-bit resolution) or something is filtering the input heavily. The usual mistake is to keep increasing the number of samples; with no noise, more averaging changes nothing.
P: 8. Acceptance tests: (1) with a reference source at 3.000, 3.600, and 4.200 V on the battery terminal, each averaged reading is within ±20 mV; (2) with 50 mV of ripple at 1 kHz added, the readings stay within ±20 mV; (3) after a power cycle, the stored calibration constants are used (readings unchanged within ±5 mV). Bench: a programmable supply in place of the cell, checked with a 5½-digit multimeter at the battery connector, and a script (Chapter 21) that steps the supply, waits 1 s, and logs the firmware's reading against the meter. The usual mistake is to test at one voltage only, which cannot reveal a gain error.
H2: Chapter 9
P: 1. 10 bits/9600 = 1.04 ms per byte; 960 bytes per second. The usual mistake is 9600/8 = 1200 bytes per second, which forgets the start and stop bits.
P: 2. 0xEE >> 1 = 0x77. The usual mistake is to use 0xEE in software, which addresses a non-existent device.
P: 3. G (0x47) ^ P (0x50) = 0x17; ^ T (0x54) = 0x43; ^ X (0x58) = 0x1B; ^ T (0x54) = 0x4F; ^ ',' (0x2C) = 0x63; ^ '0' (0x30) = 0x53; ^ '1' (0x31) = 0x62. The checksum is 62, sent as *62. The usual mistake is to include the $ or the * in the XOR.
P: 4. 33° + 29.6720'/60 = 33° + 0.49453° = 33.4945° N. The usual mistake is to read 3329.6720 as 33.296720°, which mixes minutes with decimal degrees and puts you 22 km off.
P: 5. 48 MHz/(16 × 230 400) = 13.02, rounded to 13: 48 MHz/(16 × 13) = 230 769 baud, +0.16 %. Fine. The usual mistake is to leave out the factor 16 of the oversampling, which gives a divider of 208 and a link that does not work.

P: 2. Five decades × 10 + 1 = 51 points. The usual mistake is to forget the endpoint and answer 50.
P: 3. fc = 1/(2π × 4700 × 22 × 10⁻⁹) = 1539 Hz. The usual mistake is to forget the 2π and quote 9671, which is the corner in radians per second.
P: 4. 1.00871 × 30.00 − 0.6443 = 29.62 °C. The usual mistake is to add the offset instead of subtracting it, which gives 30.91 °C.
P: 5. Each point makes two queries, and each query waits for the scope to measure and answer, often 100 to 300 ms over USB or LAN, plus the generator's own settling. Reduce it by querying both channels in one command if the scope allows, reducing the averaging, or using the scope's single-acquisition mode with *OPC?. The usual mistake is to shorten the settling time, which risks wrong data, before measuring where the time actually goes.
P: 6. Local time jumps by an hour twice a year, which creates a duplicate or missing hour in the data and breaks every rate calculation across the change. UTC is continuous; convert to local time only for display. The usual mistake is to log local time and repair the duplicate and missing hours by hand later.
P: 7. The sensor's response is not linear over this range, so a straight line leaves a systematic error. Fit a second-order polynomial (and check that its residuals are random), or calibrate a narrower range. The usual mistake is to accept the line because the rms residual looks small.
P: 8. Calibrate many sensors in the chamber at once: a fixture with, for example, 50 sensors on a bus (each with its own address or a multiplexer) and one reference. Two temperature points of 10 minutes each per batch of 50 gives 20 minutes per 50 sensors, 24 s of chamber time per sensor; ten batches cover the day's 500. The script reads all sensors and the reference at each point, computes each sensor's gain and offset, and writes them into the sensor's board, with its serial number, into the log. The usual mistake is to calibrate one sensor at a time: 20 minutes each is 167 chamber hours a day for 500 sensors.
H2: Chapter 22
P: 1. The node always sends a period as the decimal separator; parsing with the PC's current culture would misread "23.41" as 2341 in de-DE, fr-FR, and other decimal-comma locales. InvariantCulture makes the parse independent of the PC. The usual mistake is to switch the whole application to an English culture instead, which also changes the dates and numbers shown to the user.
P: 2. A thread-pool thread. The handler must hand the update to the UI thread with Dispatcher.BeginInvoke (or Invoke); touching the control directly throws an InvalidOperationException. The usual mistake is to use Invoke, which makes the serial thread wait whenever the UI is busy; BeginInvoke does not wait.
P: 3. 4.75 V to 5.25 V. The usual mistake is to take 5 % of 5.0 V as 0.5 V.
P: 4. [InlineData("23.41,101,1013.25", "humidity 101 out of range")] The usual mistake is to test only values far out of range, such as 150 %, and miss the boundary at 101 %.
P: 5. 4.77 V to 5.23 V. A board must read inside these to pass. The usual mistake is to widen the limits by the uncertainty instead of narrowing them, which passes bad boards.
P: 6. Updating the UI 200 times per second wastes the UI thread; collect the readings in a thread-safe queue in the handler and refresh the display from a DispatcherTimer at about 20 Hz, drawing at most as many points as the plot has pixels. The parser stays the same, which is the payoff of keeping it separate. The usual mistake is to redraw on every line, which freezes the window although the parser keeps up.
P: 7. So the bench logic can be tested with fakes (Listing 22.5) without hardware, and so a different DMM model needs only a new class implementing IDmm, not changes to the test logic. The usual mistake is to test the bench only on the real station, where a failing limit check cannot be told apart from a faulty instrument.
P: 8. Each board needs 32 s of station time; one station handles 7.5 × 3600/32 = 843 boards per shift, so one station suffices with margin. If the test took 60 s plus 20 s handling, one station would give 337, and two would be needed. The largest reductions come from a fixture that cuts handling time (pogo pins, a lever instead of connectors) and from running independent test steps in parallel; the usual mistake is to shorten the measurement's settling time and buy speed with false failures.
H2: Chapter 23
P: 1. 25 × 10/115 200 = 2.17 ms. The usual mistake is to use 8 bits per character, which gives 1.74 ms.
P: 2. It stops the CPU when a chosen memory location is written (or read). It finds memory corruption, a variable overwritten by a wrong pointer or a buffer overrun, in one run instead of days of guessing.
P: 3. The scope. A logic analyzer reduces every signal to 0 or 1 at a threshold and hides the analog shape. The usual mistake is to take a clean logic-analyzer trace as proof of a clean signal.
P: 4. log₂ 1000 = 9.97, so 10 steps. The usual mistake is to answer 500, as if bisect removed one commit at a time; each step halves the range.
P: 5. 6.4 µs × 2000/s = 12.8 ms per second, 1.28 % of the CPU. The usual mistake is to drop the conversion from microseconds and report 12.8 %.
P: 6. trace_head++ is a read, an add, and a write. If an interrupt arrives between the read and the write and records its own event, both get the same slot index; one event is overwritten and the counter loses a step. An atomic fetch-and-add (or briefly disabling interrupts) makes the claim indivisible. The usual mistake is to declare trace_head volatile and believe that makes the increment atomic.
P: 7. An 8 MHz SPI bit lasts 125 ns; four samples per bit needs 32 MS/s and ten needs 80 MS/s, so a 24 MS/s analyzer (3 samples per bit) is not enough. Slow the SPI clock for debugging (the bus works at any lower clock), or use a faster analyzer. The usual mistake is to trust a decode at 24 MS/s because it looks plausible most of the time.
P: 8. Log the reset reason and an uptime counter in RTC memory at every boot, plus the task watchdog's report, which names the task that failed to feed it; keep a trace buffer in RTC memory or noinit RAM and dump it after the reset. Reproduce faster by stressing the suspect: shorten the reporting interval tenfold, cut the Wi-Fi link repeatedly, unplug the sensor. First hypotheses: a blocking call without a timeout (an I2C read or a network wait), a priority problem that starves a task (Chapter 13), and a deadlock between two mutexes. Test each with an observation, not a change. The usual mistake is to change several things at once to make the resets stop, which destroys the evidence of which change mattered.
H2: Chapter 24
P: 1. Host unit tests, integration tests on the chip, hardware-in-the-loop tests, system tests. The usual mistake is to rely on the slow upper layers for everything, which makes each test cycle take hours.
P: 2. 92 160 bytes per second; 4 294 967 296/92 160 = 46 603 s, about 12.9 hours. A faster link makes the rare case a daily one. The usual mistake is to assume a 32-bit counter never wraps in practice.
P: 3. (499 + 1) × 64/32 000 = 1.0 s. The usual mistake is to use 499 instead of 499 + 1, or the 40 kHz LSI value of other STM32 families.
P: 4. "Fix ring buffer count across 32-bit counter wrap. rb_count compared head and tail directly and failed after 2^32 bytes (4.3 days at 115200 baud). Use unsigned head - tail; add test_index_wraparound." The usual mistake is "fix bug", which says nothing to the next reader.
P: 5. Unsigned overflow is defined in C to wrap modulo 2^N, so the difference is always correct modulo 2^32. Signed overflow is undefined behavior: the compiler may assume it never happens and optimize the comparison in ways that break at the wrap. The usual mistake is to cast the counters to int for the subtraction, which brings the undefined behavior back.
P: 6. A task blocked forever on a mutex or an I2C read without a timeout. SysTick keeps interrupting and feeding the watchdog, so the board never resets and the product is silently dead. The usual mistake is to think any feeding is good; the feed must depend on every task having made progress.
P: 7. The exact toolchain version (a later rebuild gives a different binary or fails), the partition table and configuration files such as sdkconfig (the build differs from the shipped one), and the tests themselves (the next developer cannot check a change). Secrets committed by mistake are the opposite error and must be rotated, not only deleted, because the history keeps them.
P: 8. The test switches the broker's power (or network port) off with a relay, waits 5 minutes, switches it on, and subscribes to the node's topic. It measures the time from broker availability to the node's first message and checks that no reset occurred (the boot counter or uptime in the message). Pass: first message within 75 s (Chapter 17's spec), uptime continuous, and the broker log shows one connection, not a storm. Repeat ten times, because a reconnect bug may show only sometimes. The usual mistake is to check only that messages resume, not how long it took or whether the node reset itself to get there.
H2: Chapter 25
P: 1. Pins from a different board, wrong I2C addresses, blocking calls in ISRs, missing pull-ups, wrong baud rates or units or byte order, missing error handling, security shortcuts. Invented APIs and wrong register names are caught by the compiler only if the real library or header is used.
P: 2. It turns hidden guesses into a visible list. Every assumption is either confirmed against the spec or corrected, and gaps in the spec show up for the next prompt. The usual mistake is to accept the code because it compiles, leaving the guesses inside it unexamined.
P: 3. "Pressing the BOOT button (GPIO 0) once prints 'mark' two or three times in about one press in five. The scope shows about 2 ms of bounce on the falling edge. The ISR prints directly on every falling edge. Expected: one 'mark' per press. Record the edge time in the ISR and print from loop() only after 30 ms without a new edge, if the pin is still low." The usual mistake is to omit the measurement, which leaves the cause to be guessed.
P: 4. Axis label: low consequence, visible: trust and run. BLE byte order: silent until a phone shows 94.77 °C, medium consequence: test with nRF Connect. MQTT topic string: silent (messages go nowhere), low to medium consequence: test with mosquitto_sub. Motor driver duty limit: high consequence, possibly silent until something burns: check every line against the datasheet and measure. The usual mistake is to judge by how hard the code looks rather than by how costly and how hidden a failure would be.
P: 5. Not necessarily: on the Arduino ESP32 core, Wire.begin() without arguments uses the board variant's default SDA and SCL, which for the ESP32-S3 DevKitC-1 are GPIO 8 and 9 in current core versions. Check the variant's pins_arduino.h for your core version and board; better, pass the pins from the spec explicitly so the code does not depend on a default. The usual mistake is to copy the classic ESP32's pins 21 and 22 into the call; the S3 has no GPIO 22.
P: 6. Idea: put the hardware facts and failure behavior in the prompt so they are reviewable. Example constraints: ESP-IDF 5.x, stack size in bytes, task priority below Wi-Fi, I2C on port 0 with SDA 1 and SCL 2 at 400 kHz, sensor address 0x29 with 16-bit registers, a 20 ms transfer timeout, three-failure recovery, 50 ms period, and a four-item queue that never blocks when full. Check: verify the pins and register format against the board and sensor documentation, then measure timing and stack use under Wi-Fi load. Usual mistake: leave timeout and recovery behavior to the assistant, whose first draft may wait indefinitely.
P: 7. Idea: establish whether the function belongs to the library version in the build. Check: search Adafruit_BME280.h or its versioned documentation, or compile against the installed library; then ask the assistant to use only declared functions and provide the relevant declarations. Usual mistake: implement the invented function from the assistant's description, hiding the library's actual interface.
P: 8. Idea: specify the partition layout, image limit, server trust, signature verification, rollback conditions, and self-test before asking for the OTA module. Check: review certificate and signature settings, rollback behavior, and any eFuse operation line by line; then run Chapter 19’s interrupted-download, altered-image, and failed-self-test cases. Tag each OTA-capable release so the last known-good image and its verification evidence remain identifiable. Usual mistake: review only application logic and let the assistant supply security settings.
H2: Chapter 26
P: 1. 12 MHz/256 = 46.9 kHz. The usual mistake is to divide by 255 instead of 256; an 8-bit counter has 256 states.
P: 2. 27 000 000/9600 = 2812.5, so 2812 or 2813; 2812 gives 9601.7 baud (+0.018 %), 2813 gives 9598.3 baud (−0.018 %). Either is fine, and tick needs 12 bits. The usual mistake is to divide by 16 as well, as for a microcontroller UART with oversampling; this transmitter counts one bit per divider period.
P: 3. The testbench only ever runs in the simulator, which can wait for time and print; synthesis turns the design into gates, which have no notion of "wait 18 ns" or of printing, so it ignores or rejects those constructs. The usual mistake is to add a #delay to the design to fix a timing problem; it works in simulation and disappears in hardware.
P: 4. With <= every right-hand side is evaluated with the values from before the clock edge, and all registers update together, which matches flip-flops. With = each line sees the result of the previous one, so the meaning depends on the order of the lines and often differs from the intended hardware; synthesis and simulation can even disagree. The usual mistake is to use = in a clocked block for a shift register, which gives every stage the same value in one clock.
P: 5. Compare with a 9-bit duty, or add a special case: out <= (duty == 8'hFF) ? 1'b1 : (count < duty). The second keeps the 8-bit port but makes 255 mean 100 %, losing the 255/256 step. The usual mistake is to change the comparison to <=, which makes duty 0 produce a one-clock pulse.
P: 6. 12 000 000/115 200 = 104.17, so DIV = 104: 115 385 baud, +0.16 %, acceptable. The same error as on the Tang Nano 9K, by coincidence of the ratios. The usual mistake is to round 104.17 up to 105, which gives 114 286 baud, −0.79 %, still usable but needlessly worse.
P: 7. Idea: when sel is 0, y must retain its old value, so synthesis builds a latch: a level-sensitive storage element, timing-sensitive and usually unintended. Check: exercise sel transitions in the testbench and inspect the synthesized design for unintended storage. If y controls a PWM or power-stage output, the latch can hold an old level and shift a switching interval. Usual mistake: test only steady inputs, which may never expose the latch.
P: 8. Use the 8 inputs as a data bus and the bidirectional pins (configured as inputs) for control: one pin as a write strobe that loads the 8 inputs into the duty register on its rising edge, one as an enable. Alternatively load the duty serially over a 2-wire interface (clock and data) on two inputs and keep six for other functions. The outputs carry the PWM signal and status. The usual mistake is to wire the 8 inputs straight to the comparator, which makes the duty change in the middle of a period whenever the inputs change.
