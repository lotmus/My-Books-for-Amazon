PART: Part III. Structure, Time, and Energy
H1: Chapter 12. Super Loops and State Machines
P: The wildlife camera took 400 photographs of one deer. Each motion event started another capture, including while the previous image was being saved. The card filled; the battery followed. The missing rule was simple: ignore motion during a 30-second cooldown. Five states—SLEEP, CAPTURE, SAVE, COOLDOWN, and LOWBATT—and their transitions make that rule explicit. The switch statement is short. In the field, it is the difference between one useful photograph and a record of repeated failure.
P: Where you meet this: Every product with modes: chargers, thermostats, vending machines, protocol handlers, menu systems, robots, and every bug report that starts "but it only happens if you press the button while it's saving".
H2: 12.1 The super loop
P: The simplest firmware structure is an initialization followed by an endless loop that calls each job in turn: read the sensors, update the logic, refresh the display, check the buttons. It needs no operating system, it is easy to follow, and for many products it is the right answer. It has one rule: no job may block. A job that waits, for a sensor, a network, or a delay, delays every other job, and the slowest job sets the response time of all of them.
P: The cure is to let each job run briefly and often: check whether it is time to do something, do a small piece of work, and return. Listing 12.1 runs three jobs at 5 ms, 500 ms, and 1 s intervals, each with its own timestamp and the wraparound-safe test of Chapter 3. Nothing in it calls delay().
P: Listing 12.1 — Three jobs at three rates in one non-blocking loop (Arduino framework, C++).
P: // Arduino framework (ESP32-S3): three jobs at three rates, none of them blocking.#include <Arduino.h>const int LED_PIN = 4;const int BUTTON_PIN = 14;unsigned long lastBlink = 0, lastSample = 0, lastReport = 0;int presses = 0;bool ledOn = false, lastButton = true;void setup() {  pinMode(LED_PIN, OUTPUT);  pinMode(BUTTON_PIN, INPUT_PULLUP);  Serial.begin(115200);}void loop() {  unsigned long now = millis();  if (now - lastSample >= 5) {            // every 5 ms: sample the button    lastSample = now;    bool b = digitalRead(BUTTON_PIN);    if (lastButton && !b) presses++;      // falling edge (debounce as in Chapter 6)    lastButton = b;  }  if (now - lastBlink >= 500) {           // every 500 ms: heartbeat LED    lastBlink = now;    ledOn = !ledOn;    digitalWrite(LED_PIN, ledOn);  }  if (now - lastReport >= 1000) {         // every second: report    lastReport = now;    Serial.printf("presses: %d\n", presses);  }}
H2: Worked Example 12.1: The slowest job sets the latency
P: Problem. A super loop reads the BME280 (2 ms), runs the control logic (5 ms), and redraws the whole OLED over I2C (12 ms, a partial update). The button is sampled once per loop, and the debouncer needs 4 equal samples. Find the worst-case button latency. The spec says 50 ms. Fix it.
P: Solution. One loop takes 2 + 5 + 12 = 19 ms. Four samples at one per loop take up to 4 × 19 = 76 ms, plus up to one more loop before the first sample: up to 95 ms. That fails the spec. The fix is to split the slow job: redraw one of the OLED's eight 128 × 8-pixel pages per loop, about 1.5 ms each, so the loop takes 2 + 5 + 1.5 = 8.5 ms. The latency becomes at most 5 × 8.5 = 42.5 ms, and the full display still refreshes every 68 ms, about 15 times per second. Splitting the work fixed the timing without an operating system.

H2: 12.2 State machines
P: A state machine describes behavior as a set of states, the events that can happen, and for each state and event, the next state and the action to take. It makes two things visible that ordinary code hides: what the device does in every combination of mode and input, including the awkward ones, and which inputs are deliberately ignored. The drawing comes first, as part of the spec; the code follows the drawing one-to-one.
FIG: fig12_2.png | Figure 12.2 — The wildlife camera's state machine. Motion wakes it from SLEEP to CAPTURE; a good photo goes to SAVE and then COOLDOWN for 30 s, during which motion is ignored; a failed capture counts an error and also cools down; a low-battery event from any state ends in LOWBATT. | A state diagram with five rounded boxes: SLEEP, CAPTURE, SAVE, COOLDOWN, LOWBATT. Arrows: SLEEP to CAPTURE on motion; CAPTURE to SAVE on capture OK; CAPTURE to COOLDOWN on capture fail with errors plus one; SAVE to COOLDOWN on saved with photos plus one; COOLDOWN to SLEEP after 30 one-second ticks; a self-loop on COOLDOWN labeled motion ignored; and a note that battery low from any state goes to LOWBATT.
P: In C, the simplest implementation is an enum for the states, an enum for the events, and one function with a switch on the current state. Listing 12.2 is exactly the drawing. Because the function only changes a struct, it runs on the PC with a scripted list of events, which is the method's step 5: the test feeds a motion event during cool-down and checks that it is ignored, then ticks 30 seconds and checks that the camera sleeps again.
P: Listing 12.2 — The camera state machine as a switch on the current state, with a scripted PC test (C).
P: // Wildlife-camera state machine: pure logic, driven by events, tested on the PC.#include <stdio.h>typedef enum { ST_SLEEP, ST_CAPTURE, ST_SAVE, ST_COOLDOWN, ST_LOWBATT } state_t;typedef enum { EV_MOTION, EV_CAPTURE_OK, EV_CAPTURE_FAIL, EV_SAVED, EV_TICK_1S, EV_BATT_LOW } event_t;#define COOLDOWN_S 30typedef struct { state_t st; int cooldown_left; int photos; int errors; } cam_t;static const char *NAMES[] = { "SLEEP", "CAPTURE", "SAVE", "COOLDOWN", "LOWBATT" };static void cam_handle(cam_t *c, event_t ev){    if (ev == EV_BATT_LOW) { c->st = ST_LOWBATT; return; }     // from any state    switch (c->st) {    case ST_SLEEP:        if (ev == EV_MOTION) c->st = ST_CAPTURE;               // action: start camera        break;    case ST_CAPTURE:        if (ev == EV_CAPTURE_OK) c->st = ST_SAVE;        else if (ev == EV_CAPTURE_FAIL) { c->errors++; c->st = ST_COOLDOWN; c->cooldown_left = COOLDOWN_S; }        break;    case ST_SAVE:        if (ev == EV_SAVED) { c->photos++; c->st = ST_COOLDOWN; c->cooldown_left = COOLDOWN_S; }        break;    case ST_COOLDOWN:                                          // motion is ignored here        if (ev == EV_TICK_1S && --c->cooldown_left == 0) c->st = ST_SLEEP;        break;    case ST_LOWBATT:                                           // stays until reset        break;    }}int main(void){    cam_t c = { ST_SLEEP, 0, 0, 0 };    const event_t script[] = { EV_MOTION, EV_CAPTURE_OK, EV_SAVED, EV_MOTION };    for (unsigned i = 0; i < sizeof script / sizeof script[0]; i++) cam_handle(&c, script[i]);    printf("after photo + motion in cooldown: %s, photos %d\n", NAMES[c.st], c.photos);    for (int s = 0; s < COOLDOWN_S; s++) cam_handle(&c, EV_TICK_1S);    printf("after 30 ticks: %s\n", NAMES[c.st]);    cam_handle(&c, EV_BATT_LOW);    printf("after low battery: %s\n", NAMES[c.st]);    return (c.photos == 1 && c.st == ST_LOWBATT) ? 0 : 1;}
H2: Worked Example 12.2: From drawing to test cases
P: Problem. List the test cases that cover every arrow of Figure 12.2 at least once, and the one ignored input that matters most.
P: Solution. Seven arrows, seven cases: (1) SLEEP + motion → CAPTURE; (2) CAPTURE + OK → SAVE; (3) CAPTURE + fail → COOLDOWN with errors = 1; (4) SAVE + saved → COOLDOWN with photos = 1; (5) COOLDOWN + 30 ticks → SLEEP, and 29 ticks are not enough; (6) battery low from at least two different states → LOWBATT; (7) COOLDOWN + motion → still COOLDOWN, and the count of remaining seconds is unchanged. Case 7 is the deer bug from the opening; it gets its own test because it is the requirement most likely to break when someone later "improves" the code. Listing 12.2 runs cases 2, 4, 5, 6, and 7.
P: Key idea. Draw the states before writing the code. A state machine turns a vague behavior into a finite list of cases, and a finite list of cases can be tested completely on the PC.
P: Common misconception. State machines are for complicated protocols only. A button with short and long presses, a charger with four phases, and a menu with three screens are all state machines; writing them as one is shorter than the nest of flags it replaces.
P: AI Pair-Programming Note
P: Ask the assistant for the state table first, as text, before any code: "list every state, event, next state, and action, including events that are ignored". Review the table against the spec; then ask for the code that implements exactly that table, plus the test sequence. Assistants are good at this when the table is fixed first and poor at inventing the behavior.
BENCH: Log every state change with a timestamp: "12:03:07.214 SLEEP -> CAPTURE (motion)". One line per transition costs almost nothing, and when a field unit misbehaves, the log tells you exactly which path it took. Keep the last 100 transitions in a RAM ring buffer, and dump it after a watchdog reset (Chapter 24).
