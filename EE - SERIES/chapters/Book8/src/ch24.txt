H1: Chapter 24. Testing, Version Control, and Safety
P: The UART receive code had worked in every test for two years. Then a customer's logger, streaming at 115 200 baud around the clock, started dropping data every four and a bit days, exactly. The ring buffer's 32-bit byte counters wrapped around after 4.3 billion bytes, and one comparison in the code did not survive the wrap. No bench test had run that long. A unit test that sets the counters a few bytes short of the wrap would have found it in a millisecond. Testing is the art of reaching the rare cases on purpose, and version control and safety habits are what make the fixes stick.
P: Where you meet this: Every professional firmware team: code review, continuous integration, release tags, test reports, and, in automotive, medical, and industrial products, safety standards that make these practices mandatory.
H2: 24.1 The test pyramid
P: Tests come in layers. At the bottom, many fast unit tests run on the PC: pure logic such as parsers, filters, state machines, and buffers, compiled with the PC's gcc or run with xUnit and pytest, thousands of checks in a second. In the middle, integration tests run the firmware on the real chip with simulated or real peripherals. At the top, hardware-in-the-loop (HIL) tests drive the real board from the PC, checking its outputs against limits, and system tests run the whole product in its real environment for days. The layers get slower, more expensive, and rarer toward the top, so the design goal is to push as much logic as possible down into code that can be tested on the PC. That is why Chapters 15 and 22 kept their arithmetic and parsing away from the hardware.

P: Listing 24.1, part 2: Release/acquire publication, wrap-safe indices, and lock-free checks.
P: #include "l24_1_ringbuf.h"bool rb_init(ringbuf_t *rb){    atomic_init(&rb->head, 0u);    atomic_init(&rb->tail, 0u);    atomic_init(&rb->dropped, 0u);    return atomic_is_lock_free(&rb->head) &&           atomic_is_lock_free(&rb->tail) &&           atomic_is_lock_free(&rb->dropped);}uint32_t rb_count(const ringbuf_t *rb){    uint32_t head = atomic_load_explicit(&rb->head, memory_order_acquire);    uint32_t tail = atomic_load_explicit(&rb->tail, memory_order_acquire);    uint32_t count = head - tail;              /* unsigned subtraction wraps */    return count > RB_SIZE ? RB_SIZE : count; /* diagnostic snapshot only */}uint32_t rb_dropped(const ringbuf_t *rb){    return atomic_load_explicit(&rb->dropped, memory_order_relaxed);}bool rb_put(ringbuf_t *rb, uint8_t b){    uint32_t head = atomic_load_explicit(&rb->head, memory_order_relaxed);    uint32_t tail = atomic_load_explicit(&rb->tail, memory_order_acquire);    /* Reject any observed distance at or above the buffer capacity. */    if ((uint32_t)(head - tail) >= RB_SIZE) {        uint32_t dropped = atomic_load_explicit(&rb->dropped, memory_order_relaxed);        atomic_store_explicit(&rb->dropped, dropped + 1u, memory_order_relaxed);        return false;    }    rb->data[head & (RB_SIZE - 1u)] = b;    atomic_store_explicit(&rb->head, head + 1u, memory_order_release);    return true;}bool rb_get(ringbuf_t *rb, uint8_t *b){    uint32_t tail = atomic_load_explicit(&rb->tail, memory_order_relaxed);    uint32_t head = atomic_load_explicit(&rb->head, memory_order_acquire);    if (head == tail) return false;    *b = rb->data[tail & (RB_SIZE - 1u)];    atomic_store_explicit(&rb->tail, tail + 1u, memory_order_release);    return true;}
P: Initialize the buffer before enabling the UART interrupt or starting its reader task, and require rb_init to succeed. The release/acquire operations publish each byte before the producer advances head and ensure the consumer finishes reading before that slot is reused. rb_count is a diagnostic snapshot only. The host tests below exercise sequential behavior and counter wrap-around; they do not test interrupt scheduling. The C standard does not define an MCU interrupt ABI or ISR-safety contract: verify that the selected compiler/runtime supports these lock-free atomics in the ISR and on any participating cores. Lock-free status alone does not prove that target contract. Otherwise use the vendor RTOS queue or a documented platform-specific critical section. Keep exactly one producer and one consumer.

H2: Worked Example 24.1: When do the counters wrap?
P: Problem. The ring buffer uses 32-bit counters. At 115 200 baud, 8N1, with the line busy continuously, how long until the counters wrap, and why does unsigned counter subtraction remain useful across that wrap?
P: Solution. 8N1 sends 10 bits per byte, so 11 520 bytes per second. 2^32 = 4 294 967 296 bytes take 4 294 967 296/11 520 = 372 827 s = 4.3 days. The producer and consumer use unsigned 32-bit counter differences, whose arithmetic wraps modulo 2^32; the buffer invariant keeps their distance at no more than RB_SIZE. The concurrent rb_count function is only a clamped diagnostic snapshot and must not decide whether to put or get. The wrap-around test starts both counters 16 bytes before wrap and runs through it; Listing 24.2 reports 413 checks and 0 failures.

H2: 24.2 Version control as the safety net
P: Git records every change with its author, time, and reason, and lets you return to any earlier state. For firmware that means a few habits. Commit small, working steps with messages that say why ("Fix ring buffer count across counter wrap; add test"), which is step 7 of the method. Keep secrets, build outputs, and personal settings out of the repository with a .gitignore file. Tag every release (v1.4.2) so the exact source of any shipped binary can be checked out years later. Work on a branch for anything larger than an afternoon and merge after review. And let a continuous integration (CI) service build the firmware and run the host tests on every push, so a broken build is noticed in minutes, not at the next release. When code comes from an AI assistant, version control is what makes experimenting safe: commit before accepting a large change, and git diff shows exactly what it changed.

P: What belongs in the repository, and what does not
LI: In: source code, headers, build files (CMakeLists.txt, platformio.ini, .csproj), partition tables, tests, the spec, the review checklist, schematics or a link to them.
LI: In: a README with the toolchain version and the exact build command.
LI: Out (.gitignore): build/, bin/, obj/, .pio/, IDE settings, and anything generated.
LI: Out, always: passwords, API keys, private signing keys, Wi-Fi credentials (Chapter 19).
H2: 24.3 Watchdogs and the safety mindset
P: A watchdog is a hardware timer that resets the chip unless the firmware feeds it in time. Feeding it from a timer interrupt is useless, because the interrupt keeps running while the tasks are stuck; feed it only when every important task has proved it is alive, as Listing 24.5 does. The STM32's independent watchdog (IWDG) runs from its own low-speed oscillator and cannot be stopped once started; the ESP32-S3 has a task watchdog in ESP-IDF that names the task that failed to check in.
P: Listing 24.5 — An STM32 independent watchdog of about 1 s, fed only when all three tasks have checked in (STM32 HAL, C).
P: // STM32 HAL: an independent watchdog of about 1 s, fed only when every task has reported in.#include "stm32f4xx_hal.h"IWDG_HandleTypeDef hiwdg;static volatile uint32_t alive_flags;          // one bit per task#define ALL_TASKS 0x07u                         // three tasks must check invoid watchdog_init(void){    hiwdg.Instance = IWDG;    hiwdg.Init.Prescaler = IWDG_PRESCALER_32;   // LSI 32 kHz / 32 = 1 kHz    hiwdg.Init.Reload = 999;                    // (999 + 1) / 1 kHz = 1.0 s    HAL_IWDG_Init(&hiwdg);                      // starts at once; cannot be stopped}void task_alive(uint32_t bit) { __disable_irq(); alive_flags |= bit; __enable_irq(); }void watchdog_service(void)                     // call from the lowest-priority loop, every ~250 ms{    if ((alive_flags & ALL_TASKS) == ALL_TASKS) {        alive_flags = 0;        HAL_IWDG_Refresh(&hiwdg);    }                                           // otherwise: let the watchdog reset the chip}
H2: Worked Example 24.2: The watchdog's real timeout
P: Problem. The IWDG uses prescaler 32 and reload 999 with the LSI oscillator, nominally 32 kHz. Find the nominal timeout. The STM32F4 datasheet gives the LSI as 17 to 47 kHz. Find the range of timeouts and a safe feeding interval.
P: Solution. Nominal: (999 + 1) × 32/32 000 Hz = 1.000 s. At 47 kHz: 32 000/47 000 = 0.681 s; at 17 kHz: 32 000/17 000 = 1.88 s. The firmware must feed within the shortest, 0.68 s, so a 250 ms service interval leaves margin, and a hang may take up to 1.88 s to be caught. The usual mistake is to feed every 900 ms because the nominal timeout is 1 s; on some chips that works, and on others the board resets during normal operation.
P: Products whose failure can hurt people are developed under functional-safety standards: IEC 61508 in general industry, ISO 26262 in cars, IEC 62304 for medical device software. They require documented requirements, traceable tests, reviews, and coding rules. The coding rules most often used for C are MISRA C; for example, its 2012 edition's Rule 21.3 forbids malloc and free, and Rule 17.2 forbids recursion, because both make memory use and timing hard to prove. Static analyzers (cppcheck, clang-tidy, and commercial MISRA checkers) find many violations automatically. A hobby project does not need certification, but the habits transfer: no dynamic allocation after startup, every loop bounded, every input checked, every error handled, and a watchdog behind it all.
P: Key idea. Push logic down into code you can test on the PC, test the rare cases on purpose (wrap-arounds, full buffers, timeouts), commit small steps with reasons, let CI run the tests on every push, and feed the watchdog only when the whole system is alive.
P: Common misconception. Feeding the watchdog in a timer interrupt or at the top of the main loop "to be safe". Then a task can hang forever while the watchdog stays happy, which is the one situation it exists for.
P: AI Pair-Programming Note
P: Ask an assistant for unit tests and it writes tests that pass, often by testing what the code does rather than what the spec requires; ask instead for tests of the edge cases listed in the spec (empty, full, wrap-around, invalid input) and check that each one fails when you break the code on purpose. That last step, mutating the code to see the test fail, is the quickest review of any test, whoever wrote it.
BENCH: Keep one "golden" board with a label, flashed with the last released firmware, in a drawer. When a new build behaves strangely, compare it with the golden board on the same bench, same cable, same sensor. It separates "the new firmware" from "this board" or "today's bench" in five minutes.
