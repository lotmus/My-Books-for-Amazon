PART: Part VI. New Ways to Build
H1: Chapter 25. AI-Assisted Development: The Method in Practice
P: The assistant returned a complete, neatly commented sketch in eight seconds. It compiled. It also chose GPIO 22, absent on the ESP32-S3, used the wrong address and baud rate, and called delay() inside an interrupt handler. The compiler had verified the syntax; it had not checked a single hardware assumption. This is the boundary: the tool can confirm what the language permits, while the engineer has to establish what the board will do. The method begins with a specification and ends only after review and measurement.
P: Where you meet this: Many software teams now use AI assistants, either built into the code editor or as separate chat tools. The tools change every few months; the method in this chapter does not depend on any of them, and none is endorsed here.
H2: 25.1 What assistants are good and bad at
P: Assistants have read an enormous amount of public code, so they are strong where that code is plentiful and consistent: desktop C# and Python, common library patterns, parsers, test cases, plotting scripts, and the boilerplate of a WPF window or a FreeRTOS task. They are weak where the truth is specific to your board and not in their training data, or changes between versions: which pins your module exposes, your sensor's address, a library's current API, a register layout, and timing. They do not see your hardware, they cannot measure, and they write an invented function with the same confidence as a real one. Lothar builds his own C# programs this way, including his MediaStar WPF application, by describing them in plain text, one piece at a time, and checking each piece; the method below is how that works without ending in a program nobody understands.
P: Common AI mistakes in firmware (check every answer for these)
LI: Pins from a different board: the classic ESP32's I2C pins 21 and 22 on an ESP32-S3, which has no GPIO 22 at all.
LI: Wrong or default addresses: a library's default I2C address instead of the one on your module.
LI: Blocking calls in interrupt handlers: delay(), Serial.print, printf, or a mutex inside an ISR.
LI: Missing pull-ups or wrong input modes: buttons and I2C lines assumed to have resistors that are not on the board.
LI: Wrong baud rate, data format, units, or byte order between the two ends.
LI: Invented or outdated library APIs: a function that sounds right but does not exist in the version you use.
LI: Wrong register names or bit positions copied from a related chip.
LI: Error handling left out: return codes ignored, no timeouts, no reconnect.
LI: Security shortcuts that make an example work: certificate checks off, passwords in the source.
H2: 25.2 The method with an assistant
P: The nine steps of Chapter 1 apply unchanged; the assistant takes over part of step 3 and nothing else. The AI rule in Chapter 1 is the release gate: a successful build does not waive any of its checks. Step 1, the spec, matters more than before, because the spec becomes the prompt: everything the assistant does not know about your hardware must be written down, or it will be guessed. Step 2 splits the work into modules small enough to review in a few minutes; ask for one at a time. Step 4, review against the checklist, is where the engineer earns the salary. Steps 5 and 6, build and test on the PC and then on the bench with a scope or logic analyzer, catch what the review missed. Step 7, commit, makes every accepted change reversible. Step 8 turns a failure into a precise bug report, which is also the best possible next prompt. Step 9 documents what was built, including which parts came from an assistant and how they were checked.
P: Prompt skeleton
LI: Role and platform: chip, board, framework and version, language.
LI: Goal: one module, one sentence.
LI: Hardware facts from the spec: pins, addresses, voltages, pull-ups, clock and baud rates.
LI: Interface: exact formats, units, decimal separator, line endings, commands and replies.
LI: Constraints: libraries by name and version, no blocking in ISRs, timeouts, memory limits.
LI: Error behavior: what happens when the sensor, the link, or the input is missing or wrong.
LI: Deliverable: the file(s), plus a list of every assumption not stated in the prompt.

H2: Worked Example 25.1: From spec to prompt
P: Problem. Turn the reader lab's sensor-to-PC module into a prompt for the ESP32-S3 firmware, using the prompt skeleton.
P: Solution. Listing 25.1 is the result. Every item comes from the spec, not from memory: the board (ESP32-S3-DevKitC-1), the I2C pins 8 and 9 and the 4.7 kΩ pull-ups on the breakout, the address 0x76 because SDO is tied to ground, the line format with its decimals and the period as separator, the version command that the HIL test of Chapter 24 uses, the library by name, the forbidden delay() and Serial calls in ISRs, the error behavior when the sensor is missing, and a request to list unstated assumptions. Writing it took ten minutes; each line closes a door the assistant would otherwise have walked through with a guess. The last line is the cheapest review tool there is: the list of assumptions shows where the assistant filled gaps.

H2: Worked Example 25.2: Reviewing the first draft
P: Problem. Review Listing 25.2 against the review checklist and the spec. List every finding and its consequence on the bench.
P: Solution. Eight findings. (1) Wire.begin(21, 22) uses the classic ESP32's pins; the ESP32-S3 has no GPIO 22, and the spec says 8 and 9: no sensor. (2) bme.begin() without an address uses the library's default 0x77; the module is at 0x76: no sensor, and (3) the return value is ignored, so the loop prints readings from an unconfigured device, typically NaN or nonsense, instead of an error. (4) Serial.begin(9600), while the dashboard expects 115 200: garbage on the PC. (5) delay(30) and Serial.println inside the ISR: on the ESP32-S3 this can trigger the interrupt watchdog or a crash, and it blocks everything else while it runs. (6) delay(1000) in loop() leaves no way to answer the version command, which is missing anyway. (7) readPressure() returns pascals, printed as 101325.00 instead of 1013.25 hPa, and Serial.print(float) gives two decimals for humidity, not one. (8) The sensor runs in the library's default normal mode instead of forced mode. None of these is a compiler error; each fails on the bench. Listing 25.3 is the reviewed version, produced by giving the full prompt of Listing 25.1 and correcting the remaining details by hand.
P: Listing 25.3 — The reviewed firmware: pins and address from the spec, a checked sensor start, forced mode, a millis() schedule, an ISR that only records the edge, a version command, and the error line when the sensor is missing (Arduino C++ on the ESP32-S3).

H2: Worked Example 25.3: Two bugs and two bug reports
P: Problem. Listing 25.4 shows the temperature on the developer's PC. With Windows using the de-DE locale, it shows nothing, and the serial updates stop. Find both bugs and write the bug reports that make good follow-up prompts.
P: Solution. Bug 1: double.Parse(f[0]) uses the PC's culture; under de-DE "23.41" becomes 2341 (Chapter 5), so the display would show 2341.00 °C if it could update at all. Bug 2: the DataReceived handler runs on a thread-pool thread and sets _value.Text directly, which throws an InvalidOperationException; nothing catches it, so no value appears and the serial handling dies. Precise bug reports name the symptom, the condition, the cause, and the expected behavior: "With the de-DE locale active on Windows, '23.41' parses as 2341 because double.Parse uses the current culture. Parse with CultureInfo.InvariantCulture and NumberStyles.Float, and reject lines outside the BME280 ranges. Put the parsing in a separate class with xUnit tests, including one under de-DE." And: "DataReceived runs on a worker thread and sets TextBlock.Text directly, which throws. Marshal UI updates through Dispatcher.BeginInvoke and keep parsing on the worker thread." The answers to those two prompts, after review, are Listings 22.1 to 22.3, and all 13 xUnit tests pass. The vague report "it doesn't work on my PC" would have produced a guess.
H2: 25.4 When to trust and when to check
P: Not every line deserves the same scrutiny. Two questions decide it: how bad is the consequence if this line is wrong, and how readily will a wrong line show itself? A plotting script that draws a wrong axis label fails visibly and harmlessly: trust, glance, run. A parser is cheap to check with tests: check by testing. A pin assignment, an I2C address, or a register value fails silently or confusingly: check against the datasheet and the schematic every time. And anything touching safety, security, power electronics, or a battery charger is checked line by line by a person who understands it, then measured, whoever wrote it.

H2: Worked Example 25.4: Proving it on the hardware
P: Problem. The reviewed firmware and dashboard are ready. Which tests decide that the module is done, and what do they measure?
P: Solution. The acceptance tests come from the spec, not from the code. (1) The HIL tests of Listing 24.3 run against the board: plausible readings, an interval of 1.00 ± 0.05 s, and the version reply; against the simulated board in the box they passed 3 of 3 in 10.8 s, and on the bench they must pass on the real one. (2) A logic analyzer on SDA and SCL shows transactions to address 0x76 at 400 kHz and one forced measurement per second. (3) A scope on GPIO 0 while pressing the button 20 times, with the serial log beside it, shows exactly 20 "mark" lines, despite the bounce visible on the scope. (4) The dashboard runs for a night on a host using the de-DE locale, and the sensor is unplugged and replugged once: it reports "error,bme280" and recovers. Then commit, tag, and write in the README which parts were drafted with an assistant and how each was verified.
P: Key idea. An assistant drafts; the engineer specifies, reviews, tests, and owns the result. The spec is the prompt, one module at a time, the review checklist before every run, tests on the PC and the bench, a commit after every accepted step, and a precise bug report as the next prompt.
P: Common misconception. Accepting a large change because it compiles and the first run looks right. Compilers do not know your pins, your addresses, or your timing. Review the diff, run the tests, and measure; if a change is too large to review, ask for it in smaller pieces.
P: AI Pair-Programming Note
P: Keep a project notes file with the spec, the pin table, the decisions made, and the problems already solved, and paste the relevant part into every new session. Assistants have no memory of your project between sessions unless you give it to them, and the notes file is also step 9 of the method.
P: For a module revisited six months later, the minimum handoff is the source version, board and library versions, spec, assumptions, tests, known limits, and the last measured result. Without those, regeneration starts by rediscovering which guesses became design decisions; compare the new diff against the tests and recheck every version-sensitive API before accepting it.
P: On the Job
P: On the Job: Companies differ widely in what they allow: some forbid pasting source code into external services, some provide approved tools that keep code inside the company, some require AI-written code to be marked in reviews. Ask before you paste. Licensing matters too: an assistant can reproduce snippets of licensed code, so the usual rules for third-party code apply to its output. And in every company the person who commits the code is responsible for it, whoever drafted it.
BENCH: Keep claimed numbers out of the design until measured under the intended load. If the loop is supposed to run at 1 kHz, toggle a pin while logging and Wi-Fi are active; if sleep current is supposed to be 10 µA, measure the complete board in its actual sleep state. A bench result without the load conditions is not a timing or current limit.
