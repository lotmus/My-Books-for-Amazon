H1: Chapter 18. BLE, LoRa, and GPS Firmware
P: The LoRa node sent its readings once a minute, as JSON, because that was how the Wi-Fi version did it. On the bench everything arrived. On The Things Network, the 32-byte application payload plus 13 bytes of LoRaWAN overhead takes about 308 ms on air at SF9: roughly 444 seconds per day, almost fifteen times the network’s 30-second daily allowance. The 8-byte payload still takes about 185 ms per LoRaWAN uplink, or 267 seconds per day at one message a minute. At this rate and without extra MAC commands or retries, one message every ten minutes uses about 26.7 seconds a day. The raw-LoRa figures are shorter because they omit LoRaWAN overhead. On Wi-Fi bytes are free; on LoRa every byte is airtime, and airtime is regulated. Each radio in this chapter shapes the firmware differently.
P: Where you meet this: Fitness trackers and phone-connected gadgets (BLE), farm, water, and city sensors kilometers from any router (LoRa), asset trackers, drones, and anything that needs position or exact time (GPS).
H2: 18.1 BLE: services and characteristics
P: Bluetooth Low Energy organizes data as a GATT server: services, each a group of characteristics, each a small value with a UUID and properties such as read, write, and notify. The Bluetooth SIG defines standard services with 16-bit UUIDs, and using them means any generic app (nRF Connect, for example) understands the device without custom code. The Environmental Sensing service, 0x181A, fits the garden node: Temperature 0x2A6E as a signed 16-bit value in 0.01 °C, Humidity 0x2A6F as an unsigned 16-bit value in 0.01 %, and Pressure 0x2A6D as an unsigned 32-bit value in 0.1 Pa, all little-endian. A peripheral advertises until a phone connects, then sends notifications when values change. The ESP32-S3 runs BLE from ESP-IDF, Arduino, or MicroPython; the nRF52840 is the low-power specialist, usually programmed with Zephyr.
P: Listing 18.1 — A BLE Environmental Sensing peripheral with three notifying characteristics (MicroPython with aioble on the ESP32-S3).
P: # MicroPython with aioble: a BLE Environmental Sensing peripheral on the ESP32-S3.import asyncioimport structimport aiobleimport bluetoothESS_UUID = bluetooth.UUID(0x181A)        # Environmental Sensing serviceTEMP_UUID = bluetooth.UUID(0x2A6E)       # Temperature: sint16, 0.01 degCHUM_UUID = bluetooth.UUID(0x2A6F)        # Humidity: uint16, 0.01 %PRES_UUID = bluetooth.UUID(0x2A6D)       # Pressure: uint32, 0.1 PaADV_INTERVAL_US = 250_000                # advertise every 250 msess = aioble.Service(ESS_UUID)temp_c = aioble.Characteristic(ess, TEMP_UUID, read=True, notify=True)hum_c = aioble.Characteristic(ess, HUM_UUID, read=True, notify=True)pres_c = aioble.Characteristic(ess, PRES_UUID, read=True, notify=True)aioble.register_services(ess)def read_sensor():    return 23.41, 45.2, 1013.25          # from the Chapter 9 driverasync def sensor_task():    while True:        t, h, p = read_sensor()        temp_c.write(struct.pack("<h", round(t * 100)), send_update=True)   # little-endian        hum_c.write(struct.pack("<H", round(h * 100)), send_update=True)        pres_c.write(struct.pack("<I", round(p * 1000)), send_update=True)  # hPa -> 0.1 Pa        await asyncio.sleep_ms(2000)async def advertise_task():    while True:        async with await aioble.advertise(ADV_INTERVAL_US, name="garden-node",                                          services=[ESS_UUID]) as connection:            print("connected:", connection.device)            await connection.disconnected(timeout_ms=None)async def main():    await asyncio.gather(sensor_task(), advertise_task())asyncio.run(main())
H2: Worked Example 18.1: Encoding the characteristics
P: Problem. Encode 23.41 °C, 45.2 %, and 1013.25 hPa as the three Environmental Sensing characteristics, byte by byte.
P: Solution. Temperature: 23.41/0.01 = 2341 = 0x0925, sent little-endian as 25 09. Humidity: 45.2/0.01 = 4520 = 0x11A8, sent as A8 11. Pressure: 1013.25 hPa = 101 325 Pa = 1 013 250 units of 0.1 Pa = 0x000F7602, sent as 02 76 0F 00. The usual mistake is big-endian order (09 25), which a phone app shows as 94.77 °C, or pressure in hPa instead of 0.1 Pa, which reads as a near vacuum.
H2: 18.2 LoRa: every byte is airtime
P: LoRa trades data rate for range: a higher spreading factor (SF7 to SF12) makes each symbol longer and the link more robust, and every step roughly doubles the airtime. The modulation and the airtime formula are Book 5's; the firmware consequences are three. Pack the data in binary, with fixed scaling, not as text. Respect the duty-cycle limit of the band (1 % in the common EU 868 MHz sub-bands, so a 124 ms packet allows one transmission per 12.4 s) and any network policy. And decide between raw LoRa point to point and LoRaWAN, which adds a network server, encryption, and device management.
P: Listing 18.2 — Packing the garden reading into 8 bytes with fixed scaling, big-endian, and unpacking it on the gateway (C, runs on the PC).
P: // Pack one garden reading into 8 bytes for LoRa, and unpack it again.// Pure C, runs on the PC; the same functions run on the node and on the gateway.#include <stdint.h>#include <stdio.h>#include <math.h>typedef struct {    uint8_t version, seq;    float t_c, rh, p_hpa, vbat;} reading_t;static void put16(uint8_t *b, uint16_t v) { b[0] = (uint8_t)(v >> 8); b[1] = (uint8_t)v; }  // big-endianstatic uint16_t get16(const uint8_t *b) { return (uint16_t)((b[0] << 8) | b[1]); }static int clampi(long v, long lo, long hi) { return (int)(v < lo ? lo : v > hi ? hi : v); }void pack(const reading_t *r, uint8_t out[8]){    out[0] = r->version;    out[1] = r->seq;    put16(&out[2], (uint16_t)(int16_t)clampi(lround(r->t_c * 100.0f), -32768, 32767)); // 0.01 degC    out[4] = (uint8_t)clampi(lround(r->rh * 2.0f), 0, 200);                          // 0.5 %    put16(&out[5], (uint16_t)clampi(lround(r->p_hpa * 10.0f), 0, 65535));            // 0.1 hPa    out[7] = (uint8_t)clampi(lround((r->vbat - 2.5f) * 50.0f), 0, 255);             // 20 mV from 2.5 V}void unpack(const uint8_t in[8], reading_t *r){    r->version = in[0];    r->seq = in[1];    r->t_c = (int16_t)get16(&in[2]) / 100.0f;    r->rh = in[4] / 2.0f;    r->p_hpa = get16(&in[5]) / 10.0f;    r->vbat = 2.5f + in[7] / 50.0f;}int main(void){    reading_t r = { 1, 42, 23.41f, 45.2f, 1013.25f, 3.86f }, back;    uint8_t buf[8];    pack(&r, buf);    for (int i = 0; i < 8; i++) printf("%02X ", buf[i]);    unpack(buf, &back);    printf("\n-> v%u #%u  %.2f C  %.1f %%  %.1f hPa  %.2f V\n",           back.version, back.seq, back.t_c, back.rh, back.p_hpa, back.vbat);    r.t_c = -12.5f; pack(&r, buf); unpack(buf, &back);    printf("negative check: %.2f C\n", back.t_c);    return 0;}
H2: Worked Example 18.2: JSON or 8 bytes
P: Problem. Compare the airtime of the 32-byte JSON payload of Chapter 17 with the 8-byte binary payload of Listing 18.2 at SF9, 125 kHz, coding rate 4/5, 8-symbol preamble, explicit header and CRC. Then check one message per minute against The Things Network's fair-use limit of 30 s of uplink airtime per day.
P: Solution. For raw LoRa at SF9, Book 5’s formula gives 123.9 ms for an 8-byte packet and 246.8 ms for a 32-byte packet. Those figures do not include LoRaWAN framing. With the 13-byte LoRaWAN overhead and no extra MAC commands, an 8-byte application payload becomes a 21-byte on-air payload and takes 185.3 ms; a 32-byte application payload becomes 45 bytes and takes 308.2 ms. On The Things Network, one 32-byte message per minute therefore uses about 444 seconds of airtime per day, nearly 14.8 times the 30-second allowance. An 8-byte message per minute uses about 267 seconds, nearly 8.9 times the allowance. For the 8-byte payload, 30/0.1853 gives at most 161 messages per day, or an average interval of about 8 minutes 57 seconds. A ten-minute interval uses about 26.7 seconds per day and leaves a small margin for this example; added MAC commands, retries, or a different data rate require a fresh calculation. The EU 1 % duty-cycle rule is a separate limit, not a substitute for the network policy.

H2: 18.3 GPS firmware
P: A GPS module is a UART device that talks NMEA sentences (Chapter 9), by default often at 9600 baud and one fix per second. The firmware decisions are around it. A fix takes time: about half a minute from a cold start, a second or two from a hot start, which needs the module's backup battery or supply to keep the almanac and time. The module typically draws 20 to 30 mA while tracking, so a battery node switches it off between fixes or uses the module's own power-save modes. Many modules accept binary configuration commands (UBX on u-blox parts) to change the rate, the sentences, and the baud rate. And the PPS (pulse per second) output, aligned to UTC within well under a microsecond on good modules, makes GPS the best clock most projects will ever have: connect it to an interrupt pin and timestamp against it.
P: Listing 18.4 — GPS helpers: the haversine distance between fixes, the NMEA checksum, and speed from an RMC sentence (Python, runs on the PC or the Pi).
P: """GPS helpers for the PC or the Pi: distance between fixes, and an RMC speed parser."""import mathR_EARTH = 6_371_000.0   # mean Earth radius, mdef haversine_m(lat1, lon1, lat2, lon2):    p1, p2 = math.radians(lat1), math.radians(lat2)    dphi, dlmb = p2 - p1, math.radians(lon2 - lon1)    a = math.sin(dphi / 2) ** 2 + math.cos(p1) * math.cos(p2) * math.sin(dlmb / 2) ** 2    return 2 * R_EARTH * math.asin(math.sqrt(a))def nmea_checksum_ok(sentence):    body, _, given = sentence.strip().lstrip("$").partition("*")    calc = 0    for ch in body:        calc ^= ord(ch)    return given != "" and calc == int(given[:2], 16)def rmc_speed_kmh(sentence):    """Speed over ground from $GPRMC or $GNRMC, in km/h; None without a valid fix."""    if not nmea_checksum_ok(sentence):        return None    f = sentence.split("*")[0].split(",")    if not f[0].endswith("RMC") or f[2] != "A" or f[7] == "":        return None    return float(f[7]) * 1.852          # knots to km/hif __name__ == "__main__":    d = haversine_m(48.1173, 11.5167, 48.1374, 11.5755)    print("GGA fix to Marienplatz: %.0f m" % d)    print("1e-5 deg of latitude: %.2f m" % haversine_m(48.0, 11.0, 48.00001, 11.0))    s = "$GPRMC,123519,A,4807.038,N,01131.000,E,022.4,084.4,230394,003.1,W*6A"    print("RMC checksum ok:", nmea_checksum_ok(s), " speed %.1f km/h" % rmc_speed_kmh(s))
H2: Worked Example 18.3: What the digits mean
P: Problem. The GGA sentence of Chapter 9 places the node at 48.1173° N, 11.5167° E. How far is that from Munich's Marienplatz at 48.1374° N, 11.5755° E, and how much distance does the last digit of a fifth decimal place represent?
P: Solution. Listing 18.4 gives 4903 m by the haversine formula. One unit in the fifth decimal of latitude, 0.00001°, is 1.11 m; NMEA's 4807.038 format has a resolution of 0.001 minute = 1.85 m. Neither is the accuracy: a consumer module is typically good to a few meters in the open and much worse between buildings, so averaging or fusing with the IMU (Chapter 16) matters more than extra digits.
P: Key idea. Each radio shapes the firmware: BLE through standard services and little-endian characteristics, LoRa through airtime and duty cycle, GPS through fix time, power, and its PPS clock.
P: Common misconception. Treating a LoRa node like a Wi-Fi node with a longer range. Text payloads, frequent messages, and acknowledgments for everything break the duty-cycle limit and the network's policy. Design the payload in bytes, and send only what changed or what is due.
P: AI Pair-Programming Note
P: Ask an assistant for LoRa code and it often mixes libraries (RadioLib calls with another library's constructor), picks 915 MHz for an EU node or the reverse, or omits the duty-cycle check. Name the library, its version, the module, the band, and the duty-cycle limit in the prompt, and compile against the real library before trusting any of it.
BENCH: Use a phone app such as nRF Connect for every BLE peripheral: it lists the services, decodes the standard characteristics, and shows notifications as they arrive. If the app shows 94.77 °C, the bytes are in the wrong order; if it shows nothing, the characteristic is not notifying, or the phone never subscribed.
