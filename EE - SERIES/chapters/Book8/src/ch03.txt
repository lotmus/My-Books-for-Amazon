H1: Chapter 3. C for Microcontrollers: Bits, Types, and Memory
P: An int on your laptop is 32 bits. On a classic Arduino Uno it is 16 bits, so a millisecond counter stored in it goes negative after 32.8 seconds. The program that worked in a two-second test fails half a minute after power-up, every time, and the cause is one word in a declaration. Embedded C is ordinary C with the hardware's fingerprints on it: exact sizes, bits that mean something, variables that change behind the compiler's back, and memory that you can count.
P: Where you meet this: Every driver, every register write, every data sheet table of bit fields, and every bug that appears only after the board has run for 49.7 days.
P: This chapter is not a C course. It covers the five habits that separate C on a microcontroller from C on a PC: exact-width types, bit manipulation, volatile, the memory map, and wraparound arithmetic. If C is new to you, keep a general C reference beside this chapter (Appendix C names one) and type in every listing.
H2: 3.1 Exact-width types
P: The C standard says only that an int is at least 16 bits. On the ESP32, STM32, RP2040, and nRF52840 it is 32 bits; on 8-bit AVR chips it is 16. Firmware that talks to registers, packets, and files needs sizes that never change, so it uses the types from stdint.h: uint8_t, int16_t, uint32_t, and their relatives. A register is uint32_t; a byte from I2C is uint8_t; a temperature in hundredths of a degree fits int16_t, from −327.68 to +327.67 °C.
P: Mixing sizes has one rule that catches everyone once. In an expression, values smaller than int are promoted to int before the arithmetic. Two uint8_t values of 200 and 100 add to 300 without trouble, but storing the result back into a uint8_t keeps only the low eight bits, 300 − 256 = 44. The compiler is allowed to say nothing about it; turn on -Wall -Wextra and -Wconversion, and read the warnings.
H2: 3.2 Bits that mean something
P: Hardware is configured by writing bits into registers. A data sheet's register description is a map: bits 7 to 5 set the temperature oversampling, bits 4 to 2 the pressure oversampling, bits 1 and 0 the mode. Four operations cover almost all of it. OR with a mask sets bits, AND with the inverted mask clears them, XOR toggles them, and AND followed by a shift reads a field.
EQ: set: r |= m    clear: r &= ~m    toggle: r ^= m    read: (r & mask) >> shift
P: Listing 3.1 — Setting, clearing, and writing bit fields, ending with the BME280's ctrl_meas value (C, runs on the PC).
P: // Building the BME280 ctrl_meas register value with bit fields; runs on the PC.#include <stdint.h>#include <stdio.h>#define BIT(n)            (1u << (n))#define SET_BITS(r, m)    ((r) |= (m))#define CLEAR_BITS(r, m)  ((r) &= ~(m))// ctrl_meas (register 0xF4): osrs_t in bits 7..5, osrs_p in bits 4..2, mode in bits 1..0#define OSRS_T_SHIFT  5u#define OSRS_P_SHIFT  2u#define MODE_MASK     0x03u#define MODE_NORMAL   0x03ustatic uint8_t field_write(uint8_t reg, uint8_t mask, unsigned shift, uint8_t value){    return (uint8_t)((reg & ~(mask << shift)) | ((value & mask) << shift));}int main(void){    uint32_t reg = 0xA4u;                 // 1010 0100    SET_BITS(reg, BIT(3));                // 1010 1100 = 0xAC    CLEAR_BITS(reg, BIT(5));              // 1000 1100 = 0x8C    printf("reg = 0x%02X\n", (unsigned)reg);    uint8_t ctrl_meas = 0;    ctrl_meas = field_write(ctrl_meas, 0x07u, OSRS_T_SHIFT, 1);   // temperature x1    ctrl_meas = field_write(ctrl_meas, 0x07u, OSRS_P_SHIFT, 1);   // pressure x1    ctrl_meas = field_write(ctrl_meas, MODE_MASK, 0, MODE_NORMAL);    printf("ctrl_meas = 0x%02X\n", (unsigned)ctrl_meas);          // 0x27    return 0;}
H2: Worked Example 3.1: Building a register value
P: Problem. A register holds 0xA4. Set bit 3 and clear bit 5. Then build the BME280 ctrl_meas value for temperature oversampling ×1 (code 1 in bits 7..5), pressure oversampling ×1 (code 1 in bits 4..2), and normal mode (code 3 in bits 1..0).
P: Solution. 0xA4 is 1010 0100. Setting bit 3 (mask 0x08) gives 1010 1100 = 0xAC. Clearing bit 5 (mask 0x20) gives 1000 1100 = 0x8C. For ctrl_meas: 1 << 5 = 0x20, 1 << 2 = 0x04, and 3 in the low bits, so the value is 0x20 + 0x04 + 0x03 = 0x27, the value many BME280 examples write without explaining it. Listing 3.1 prints both results. The usual mistake is to shift by the field's highest bit (7) instead of its lowest (5), which writes 0x80 and selects ×4 oversampling.
H2: 3.3 Volatile: the variable that changes by itself
P: An optimizing compiler assumes that a variable changes only when the code in front of it changes it. That is false for a hardware register, which the peripheral updates, and for a flag that an interrupt handler sets. If the main loop waits for such a flag in a tight loop, the compiler may read it once, keep it in a CPU register, and loop forever. Declaring it volatile tells the compiler to read it from memory every time.
P: Volatile is necessary and not sufficient. It does not make a read-modify-write atomic, and it does not make a 64-bit value safe to read while an interrupt is changing it half-way. Chapter 6 shows the patterns for sharing data with interrupts, and Chapter 13 the patterns for sharing it between tasks.
P: Common misconception. Volatile makes a variable thread-safe. It only stops the compiler from caching it. Two tasks incrementing the same volatile counter still lose counts, because each increment is a read, an add, and a write that can be interrupted in between.
H2: 3.4 Where things live: the memory map
P: A microcontroller has two kinds of memory with different jobs. Flash keeps the program and constant data when the power is off; RAM holds everything that changes. The linker places each kind of object in its region, as Chapter 2's size report showed. Code and const tables go to flash. Initialized variables live in RAM, with their starting values copied from flash at startup. Zero-initialized variables live in RAM in the bss region. The heap grows upward from the end of bss for malloc, and the stack grows downward from the top of RAM for function calls and local variables. When the two meet, the program fails in ways that look random.
FIG: fig3_1.png | Figure 3.1 — The memory map of a typical Arm Cortex-M microcontroller. The gap between heap and stack is the only safety margin. | Two vertical columns. Flash, from the bottom: vector table, text (code), rodata (constants), initial values of data. RAM, from the bottom: data, bss, heap with an upward arrow, a free gap, and stack with a downward arrow from the top. An arrow shows the initial values copied from flash to the data region at startup.
P: Most firmware avoids the heap after startup. Allocating and freeing blocks of different sizes for months fragments it until an allocation fails, at an unpredictable time. The usual style is to allocate everything once at startup, or statically, and never free it. That is also a rule in the MISRA C guidelines of Chapter 24.
H2: 3.5 Structs, padding, and packets
P: A struct groups related fields, such as one log record. The compiler aligns each field to its natural boundary, so a uint32_t starts at an address divisible by four, and it inserts padding bytes to make that true. Field order therefore changes the size. It also means a struct is not a portable packet format: another compiler or processor may pad and order bytes differently. Firmware that sends data over a link packs the bytes explicitly, as Chapter 18 does.
P: Listing 3.2 — The same four fields in two orders; padding makes one struct 12 bytes and the other 8 (C, runs on the PC).
P: // Field order changes a struct's size: padding made visible; runs on the PC.#include <stddef.h>#include <stdint.h>#include <stdio.h>struct rec_a { uint8_t id; uint32_t time; uint16_t hum; uint8_t flags; };struct rec_b { uint32_t time; uint16_t hum; uint8_t id; uint8_t flags; };int main(void){    printf("rec_a: %zu bytes (time at %zu, hum at %zu, flags at %zu)\n",           sizeof(struct rec_a), offsetof(struct rec_a, time),           offsetof(struct rec_a, hum), offsetof(struct rec_a, flags));    printf("rec_b: %zu bytes\n", sizeof(struct rec_b));    return 0;}
H2: Worked Example 3.2: Padding in a log record
P: Problem. Find the size of struct rec_a { uint8_t id; uint32_t time; uint16_t hum; uint8_t flags; } on a 32-bit microcontroller, and the size after reordering the fields from largest to smallest. How much flash does the reordering save for 100 000 records?
P: Solution. id occupies byte 0; time must start at a multiple of 4, so bytes 1 to 3 are padding and time sits at 4 to 7; hum sits at 8 and 9; flags at 10; the struct's size is rounded up to a multiple of its largest alignment, 4, so it is 12 bytes. Ordered time, hum, id, flags, the fields occupy 0 to 3, 4 and 5, 6, 7, with no padding: 8 bytes. Listing 3.2 prints 12 and 8. For 100 000 records the reordering saves 400 000 bytes. The usual mistake is to "fix" the padding with a packed attribute, which saves the same space but makes every access to the misaligned uint32_t slower, and on some cores a fault.

Top row, rec_a: id in byte 0, padding in 1 to 3, time in 4 to 7, hum in 8 and 9, flags in 10, padding in 11. Bottom row, rec_b: time in 0 to 3, hum in 4 and 5, id in 6, flags in 7.
H2: 3.6 Time that wraps around
P: Firmware measures time with a counter that ticks every millisecond or microsecond. Every counter wraps: a uint16_t millisecond counter after 65 536 ms, 65.5 s; a uint32_t after 4 294 967 296 ms, 49.7 days. Code that compares absolute times breaks at the wrap. Code that subtracts first and compares the difference keeps working, because unsigned subtraction in C is defined to wrap the same way the counter does.
P: Listing 3.3 — A wraparound-safe timeout test, and the naive version that fails near the wrap (C, runs on the PC).
P: // Wraparound-safe timeouts with a 32-bit millisecond counter; runs on the PC.#include <stdbool.h>#include <stdint.h>#include <stdio.h>static bool timed_out(uint32_t now, uint32_t start, uint32_t timeout_ms){    return (uint32_t)(now - start) >= timeout_ms;   // correct across the wrap}static bool timed_out_naive(uint32_t now, uint32_t start, uint32_t timeout_ms){    return now >= start + timeout_ms;               // wrong near the wrap}int main(void){    uint32_t start = 0xFFFFFF00u;    // 256 ms before the counter wraps to 0    uint32_t now   = 0xFFFFFF80u;    // 128 ms later, before the wrap    printf("elapsed %u ms, safe %d, naive %d\n",           (unsigned)(now - start), timed_out(now, start, 1000),           timed_out_naive(now, start, 1000));      // 128, 0, 1 (naive is wrong)    now = 0x00000064u;               // 356 ms after start, after the wrap    printf("elapsed %u ms, safe %d\n",           (unsigned)(now - start), timed_out(now, start, 1000));   // 356, 0    return 0;}
H2: Worked Example 3.3: The 49.7-day bug
P: Problem. A uint32_t millisecond counter reads 0xFFFFFF00 when a 1000 ms timeout starts. 128 ms later it reads 0xFFFFFF80. Evaluate the safe test (now − start) >= 1000 and the naive test now >= start + 1000.
P: Solution. The safe test computes 0xFFFFFF80 − 0xFFFFFF00 = 0x80 = 128, which is less than 1000, so it correctly says "not yet". In the naive test, start + 1000 = 0xFFFFFF00 + 0x3E8 overflows to 0x2E8 = 744, and 0xFFFFFF80 is far above 744, so it says the timeout has expired 872 ms early. Listing 3.3 prints both results. The bug appears only within one timeout period of the wrap, once every 49.7 days, which is why it survives every test on the bench.
P: AI Pair-Programming Note
P: Assistants write timing code in the naive form surprisingly often, and they use int or long where a fixed width matters. In review, search the code for every comparison involving a time value and every place where a sensor value is stored, and check the type and the arithmetic.
BENCH: Compile firmware with the warnings on and treat them as errors once a project is stable: -Wall -Wextra -Werror in the build flags. The first time it costs an afternoon; after that it catches sign mistakes, truncations, and unused results before they ever reach the board.
