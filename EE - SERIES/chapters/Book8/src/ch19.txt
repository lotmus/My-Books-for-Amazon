H1: Chapter 19. OTA Updates and Security Basics
P: Two hundred sensor nodes went onto lamp posts with no over-the-air update. When a reconnect bug appeared, each repair required a cherry picker, a ladder, a laptop, and a USB cable. A later deployment had OTA, but accepted unsigned images over plain HTTP. The first design made every correction a field visit; the second let a nearby attacker choose the firmware. A useful update path must recover from a bad release and reject code the owner did not approve. This chapter treats both as product requirements, because the workshop is not where either failure will be found.
P: Where you meet this: Every connected product, from smart plugs to cars; regulators increasingly require secure updates and a vulnerability process, so this is now part of the job description, not an extra.
H2: 19.1 How OTA works on the ESP32-S3
P: On the ESP32-S3, this A/B pattern keeps the current image available while the other slot is written. Other platforms use different bootloaders, partition layouts, and rollback guarantees; check the target documentation rather than assuming they behave the same way.

H2: Worked Example 19.1: Sizing the slots and the download
P: Problem. The firmware image is 1.2 MB. Check that it fits the partition table of Listing 19.1 with room to grow, and find the download time over Wi-Fi at an effective 2 Mbit/s and the pure airtime over LoRa at SF9 and 125 kHz.
P: Solution. Each slot is 0x300000 = 3 145 728 bytes; 1.2 MB uses 38 %, leaving room for the firmware to grow to more than twice its size. The partitions end at 0x800000, exactly 8 MB. Over Wi-Fi: 1.2 × 10⁶ × 8 bits/(2 × 10⁶ bit/s) = 4.8 s. Over LoRa the raw bit rate at SF9, 125 kHz, CR 4/5 is 9 × 125 000/512 × 4/5 = 1758 bit/s (Book 5), so the pure airtime is 9.6 × 10⁶/1758 = 5460 s, 1.5 hours; at the EU 1 % duty cycle that becomes 152 hours, more than six days, before any packet overhead or retries. Full-image OTA over LoRa is impractical; LoRa devices update by delta patches, by a different radio, or not at all, and that decision belongs in the spec.

H2: 19.2 Integrity and authenticity
P: A SHA-256 hash detects accidental corruption only when the expected hash is trusted. If an attacker can replace both the image and its manifest, the matching hashes prove nothing about who made the image. Authenticity requires a digital signature that the device verifies with a trusted public key before accepting the update. On the ESP32-S3, Secure Boot V2 verifies RSA-3072 signatures when it is enabled and provisioned; ESP-IDF also documents software signature verification for OTA, with different protection limits. The HTTPS call in Listing 19.2 verifies the server certificate; it does not, by itself, configure image-signature verification. Flash encryption protects confidentiality at rest, not authenticity. Its eFuses are one-way, and losing the signing key can strand deployed devices without a valid update path.
P: Listing 19.3 — Write and check an update manifest with version, size, and SHA-256 (Python, runs on the build PC).
P: """Write and check an update manifest: version, size, and SHA-256 of the firmware image."""import hashlibimport jsonimport sysfrom pathlib import Pathdef sha256_file(path, chunk=65536):    h = hashlib.sha256()    with open(path, "rb") as f:        while block := f.read(chunk):            h.update(block)    return h.hexdigest()def make_manifest(image, version):    p = Path(image)    return {"version": version, "file": p.name, "size": p.stat().st_size, "sha256": sha256_file(p)}def check(image, manifest):    p = Path(image)    if p.stat().st_size != manifest["size"]:        return "size mismatch"    if sha256_file(p) != manifest["sha256"]:        return "hash mismatch"    return "ok"if __name__ == "__main__":    if len(sys.argv) != 3:        sys.exit("usage: l19_3_manifest.py firmware.bin 1.4.2")    m = make_manifest(sys.argv[1], sys.argv[2])    Path(sys.argv[1]).with_suffix(".json").write_text(json.dumps(m, indent=2))    print(json.dumps(m, indent=2))    print("check:", check(sys.argv[1], m))
H2: Worked Example 19.2: What the manifest catches
P: Problem. A 1 200 000-byte image and its manifest are created with Listing 19.3. One byte of the image is then changed. What does the check report, and what attack does the manifest not stop?
P: Solution. The PC utility reports a hash mismatch: the size still matches, but the changed byte changes the digest. Listing 19.3 demonstrates this check on the build PC; it does not implement on-device rejection. The device must verify a trusted digest or signed manifest before selecting the new image, or use image-signature verification. If an attacker controls the download server, a matching unsigned manifest is not protection. TLS with certificate verification protects the connection against an in-path attacker; it does not protect against a compromised server.
H2: Worked Example 19.3: Counting failed updates in a fleet
P: Problem. A staged rollout to 10 000 devices measures a 0.1 % unrecoverable first-boot failure rate. How many devices need another recovery path after one rollout? What changes if automatic rollback succeeds?
P: Solution. 10 000 × 0.001 = 10 devices. That is a scenario calculation, not a forecast or an acceptable target. If rollback is verified, those devices are service outages until the old image reconnects and resumes reporting; they are not counted as recovered merely because the bootloader selected the previous slot. Across a fleet, record the denominator, the failure definition, the recovery time, and the result by hardware and firmware version.
H2: 19.3 A security baseline for small devices
P: Security baseline for a connected node
LI: No default passwords: unique credentials per device, set at provisioning.
LI: No secrets in the source or in git; keys in NVS (encrypted) or a secure element.
LI: TLS with certificate verification for every connection that carries commands or updates.
LI: Signed updates (Secure Boot V2 or MCUboot) with rollback protection.
LI: JTAG and the serial bootloader disabled or locked in production.
LI: Every input from the network length-checked and range-checked before use.
LI: A way to report vulnerabilities, and a plan for how long the product gets updates.
P: The EU Cyber Resilience Act sets cybersecurity requirements for products with digital elements, including vulnerability handling and security updates. Its reporting obligations apply from 11 September 2026; its main obligations apply from 11 December 2027. As of this 2026 snapshot, Delegated Regulation (EU) 2022/30 under the Radio Equipment Directive also imposes cybersecurity requirements on specified categories of radio equipment; that delegated regulation is repealed from 11 December 2027 as the Cyber Resilience Act takes full effect. Check the rules and product scope for your market at design time; the engineering baseline is the same.
P: Key idea. Plan updates on day one: two slots, a self-test that confirms or rolls back, TLS server verification, and independent image-signature verification. If the new image cannot reach the broker but confirms itself anyway, the deployed node can remain unreachable until another recovery path exists; for a fleet, count those nodes as unavailable until recovery is demonstrated, not merely until the reboot completes. A hash checks integrity only against a trusted expected value; a signature checks who approved the image.
P: Common misconception. Enabling secure boot or flash encryption on the only prototype to see what happens. The eFuses are one-time, and a wrong key or a development setting burned into the chip can leave a board that never boots unsigned code again. Follow the vendor's development-mode instructions on a spare board first.
P: AI Pair-Programming Note
P: Apply Chapter 1's AI rule. Check TLS, image signatures, rollback, and eFuse settings against this ESP-IDF version. A successful download proves none of the failure paths. A measured 0.1 % unrecoverable first-boot rate corresponds to 1 affected device per 1 000 updated devices, or 10 in a rollout of 10 000. That is arithmetic, not a reliability target. Replace it with staged-rollout results and a tested recovery time before promising a service level.
P: On the Job
P: On the Job: Keep the production signing key on a build server or HSM, not developer laptops. Limit access, document key replacement, and require firmware to reject images without that signature.
BENCH: Interrupt Wi-Fi, serve a truncated image, alter an image, and force the self-test to fail. In each case, verify that the old image boots, reconnects, and resumes reporting. A bootloader message is encouraging; the device returning to its service is the test.
