H1: Chapter 19. OTA Updates and Security Basics
P: Two hundred sensor nodes were mounted on lamp posts across a town, and then someone found a bug in the reconnect code. The firmware had no over-the-air update. Fixing it meant a cherry picker, a ladder, a laptop, and a USB cable at every post, at a cost far above the value of the nodes. A year later, a different company's nodes did have updates, unsigned, over plain HTTP, and an attacker on the same network replaced their firmware with unauthorized code. A device you cannot update is stuck with its bugs; a device anyone can update is no longer yours. This chapter covers both halves.
P: Where you meet this: Every connected product, from smart plugs to cars; regulators increasingly require secure updates and a vulnerability process, so this is now part of the job description, not an extra.
H2: 19.1 How OTA works on the ESP32-S3
P: The flash holds two application slots, ota_0 and ota_1, and a small otadata partition that records which slot boots. The running firmware downloads the new image into the other slot while it keeps working, verifies it, and marks it as the next boot. If the download fails halfway, nothing has changed. After the restart the bootloader starts the new image in a pending-verify state; the new firmware runs a self-test and either confirms itself or asks for a rollback, and if it crashes before confirming, the bootloader returns to the old slot on the next reset. Every update scheme on every platform is a variation on this A/B pattern; the RP2040, STM32, and nRF52840 have bootloaders such as MCUboot that do the same.

H2: Worked Example 19.1: Sizing the slots and the download
P: Problem. The firmware image is 1.2 MB. Check that it fits the partition table of Listing 19.1 with room to grow, and find the download time over Wi-Fi at an effective 2 Mbit/s and the pure airtime over LoRa at SF9 and 125 kHz.
P: Solution. Each slot is 0x300000 = 3 145 728 bytes; 1.2 MB uses 38 %, leaving room for the firmware to grow to more than twice its size. The partitions end at 0x800000, exactly 8 MB. Over Wi-Fi: 1.2 × 10⁶ × 8 bits/(2 × 10⁶ bit/s) = 4.8 s. Over LoRa the raw bit rate at SF9, 125 kHz, CR 4/5 is 9 × 125 000/512 × 4/5 = 1758 bit/s (Book 5), so the pure airtime is 9.6 × 10⁶/1758 = 5460 s, 1.5 hours; at the EU 1 % duty cycle that becomes 152 hours, more than six days, before any packet overhead or retries. Full-image OTA over LoRa is impractical; LoRa devices update by delta patches, by a different radio, or not at all, and that decision belongs in the spec.
P: Listing 19.2 — HTTPS OTA with certificate verification, and the self-test that confirms the new image or rolls back (ESP-IDF, C).
P: // ESP-IDF: download a signed image over HTTPS into the other OTA slot, and confirm or roll back// after a self-test on first boot. Needs CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y.#include <stdbool.h>#include "esp_crt_bundle.h"#include "esp_https_ota.h"#include "esp_log.h"#include "esp_ota_ops.h"#include "esp_system.h"static const char *TAG = "ota";extern bool self_test(void);        // sensor answers, Wi-Fi connects, broker reachablevoid ota_confirm_or_rollback(void)  // call early in app_main{    const esp_partition_t *running = esp_ota_get_running_partition();    esp_ota_img_states_t state;    if (esp_ota_get_state_partition(running, &state) == ESP_OK &&        state == ESP_OTA_IMG_PENDING_VERIFY) {        if (self_test()) {            ESP_LOGI(TAG, "new image passed self-test, keeping it");            esp_ota_mark_app_valid_cancel_rollback();        } else {            ESP_LOGE(TAG, "self-test failed, rolling back");            esp_ota_mark_app_invalid_rollback_and_reboot();        }    }}esp_err_t ota_update(const char *url){    esp_http_client_config_t http = {        .url = url,        .crt_bundle_attach = esp_crt_bundle_attach,   // verify the server's TLS certificate        .timeout_ms = 10000,    };    esp_https_ota_config_t cfg = { .http_config = &http };    ESP_LOGI(TAG, "downloading %s", url);    esp_err_t err = esp_https_ota(&cfg);              // writes the inactive slot, sets it to boot next    if (err == ESP_OK) {        ESP_LOGI(TAG, "image written, restarting");        esp_restart();    }    ESP_LOGE(TAG, "OTA failed: %s", esp_err_to_name(err));    return err;                                       // the running image is untouched}
H2: 19.2 Integrity and authenticity
P: A SHA-256 hash in an update manifest proves that the file arrived intact: a single changed byte gives a completely different hash. It does not prove who made the file, because an attacker who can replace the image can replace the manifest too. Authenticity needs a signature: the build server signs the image with a private key that never leaves it, and the device checks the signature with the public key before booting. On the ESP32-S3 that is Secure Boot V2, which checks an RSA-3072 signature in the bootloader. Flash encryption adds confidentiality, so a firmware dump from the chip is unreadable. Both are switched on with eFuses that cannot be reset, so practice on a spare board, and keep the signing key in a safe place: losing it means no more updates for every device in the field.
P: Listing 19.3 — Write and check an update manifest with version, size, and SHA-256 (Python, runs on the build PC).
P: """Write and check an update manifest: version, size, and SHA-256 of the firmware image."""import hashlibimport jsonimport sysfrom pathlib import Pathdef sha256_file(path, chunk=65536):    h = hashlib.sha256()    with open(path, "rb") as f:        while block := f.read(chunk):            h.update(block)    return h.hexdigest()def make_manifest(image, version):    p = Path(image)    return {"version": version, "file": p.name, "size": p.stat().st_size, "sha256": sha256_file(p)}def check(image, manifest):    p = Path(image)    if p.stat().st_size != manifest["size"]:        return "size mismatch"    if sha256_file(p) != manifest["sha256"]:        return "hash mismatch"    return "ok"if __name__ == "__main__":    if len(sys.argv) != 3:        sys.exit("usage: l19_3_manifest.py firmware.bin 1.4.2")    m = make_manifest(sys.argv[1], sys.argv[2])    Path(sys.argv[1]).with_suffix(".json").write_text(json.dumps(m, indent=2))    print(json.dumps(m, indent=2))    print("check:", check(sys.argv[1], m))
H2: Worked Example 19.2: What the manifest catches
P: Problem. A 1 200 000-byte image and its manifest are created with Listing 19.3. One byte of the image is then changed. What does the check report, and what attack does the manifest not stop?
P: Solution. The size still matches, but the hash differs completely, so the check reports a hash mismatch and the device refuses the image; the run in the box printed "check: ok" for the original and "hash mismatch" after one changed byte. An attacker who controls the download server or the network can replace the image and write a matching manifest, so the hash alone stops corruption, not attack. Signing the image (Secure Boot V2) or the manifest closes that gap, and TLS with certificate verification (the crt_bundle_attach line of Listing 19.2) stops a man in the middle on the way.
H2: 19.3 A security baseline for small devices
P: Security baseline for a connected node
LI: No default passwords: unique credentials per device, set at provisioning.
LI: No secrets in the source or in git; keys in NVS (encrypted) or a secure element.
LI: TLS with certificate verification for every connection that carries commands or updates.
LI: Signed updates (Secure Boot V2 or MCUboot) with rollback protection.
LI: JTAG and the serial bootloader disabled or locked in production.
LI: Every input from the network length-checked and range-checked before use.
LI: A way to report vulnerabilities, and a plan for how long the product gets updates.
P: The EU Cyber Resilience Act sets cybersecurity requirements for products with digital elements, including vulnerability handling and security updates. Its reporting obligations apply from 11 September 2026; its main obligations apply from 11 December 2027. As of this 2026 snapshot, Delegated Regulation (EU) 2022/30 under the Radio Equipment Directive also imposes cybersecurity requirements on specified categories of radio equipment; that delegated regulation is repealed from 11 December 2027 as the Cyber Resilience Act takes full effect. Check the rules and product scope for your market at design time; the engineering baseline is the same.
P: Key idea. Plan updates on day one: two slots, a self-test that confirms or rolls back, and signed images delivered over verified TLS. A hash checks integrity; only a signature checks who made the image.
P: Common misconception. Enabling secure boot or flash encryption on the only prototype to see what happens. The eFuses are one-time, and a wrong key or a development setting burned into the chip can leave a board that never boots unsigned code again. Follow the vendor's development-mode instructions on a spare board first.
P: AI Pair-Programming Note
P: Ask an assistant for OTA code and it may disable certificate checks to make an example work (skip_cert_common_name_check set to true, or plain HTTP), omit the rollback confirmation, or invent a configuration field. Security settings are a hard "check" item in the review checklist: every flag that turns verification off is a finding, whoever wrote it.
P: On the Job
P: On the Job: In a company, the production signing key is protected: it lives on a build server or a hardware security module, two people know how to use it, and no developer laptop ever holds the production key. The firmware engineer's part is to make the device refuse anything not signed with it, and to write down the procedure for the day a key must be replaced.
BENCH: Test the failure paths of OTA, not only the success: pull the Wi-Fi halfway through a download, serve a truncated image, serve an image with one changed byte, and flash a test image whose self-test fails on purpose. Each must leave the node running the old firmware. A rollback you have never seen work is a rollback you do not have.
