H1: Chapter 22. C# Dashboards and Test Benches
P: The dashboard ran for an hour, then froze. The window could still be dragged, but the numbers stopped changing and the close button did nothing. The serial code was correct; it ran in the wrong place. A SerialPort raises its DataReceived event on a background thread, and the program updated a text box from that thread, which WPF forbids, so it threw an exception that nobody caught, inside a thread nobody watched. One line, Dispatcher.BeginInvoke, fixes it. This chapter builds the dashboard and the production test bench properly, with the parsing tested before any window exists.
P: Where you meet this: Lab dashboards, service and configuration tools shipped with products, end-of-line test stations in production, and the Windows programs that industrial customers expect alongside the hardware.
H2: 22.1 Separate the logic from the window
P: The most useful design decision in a desktop tool is to keep everything that can be tested away from the user interface. Parsing a line, checking limits, computing a pass or fail: these are plain classes with no reference to a window or a port, and xUnit tests them in a second on any PC. The window then only connects the port to the parser and the parser to the display. Chapter 5 introduced C# and the SerialPort class; this chapter builds on its "t,h,p" line format. The tools are Visual Studio (the Community edition is free for individuals) or VS Code with the C# Dev Kit; WPF is the mature Windows desktop framework, WinUI 3 the newer one, and .NET MAUI targets Windows, Android, and iOS from one code base.
P: Listing 22.1 — A parser for the node's "t,h,p" lines with culture-independent number parsing and range checks from the BME280 datasheet; no I/O, so it can be unit-tested (C#).
P: // Parse and validate one "t,h,p" line from the garden node. No I/O here, so it can be unit-tested.using System.Globalization;namespace GardenBench;public readonly record struct Reading(double TempC, double HumidityPct, double PressureHPa);public static class ReadingParser{    // BME280 operating ranges from the datasheet: -40..85 degC, 0..100 %RH, 300..1100 hPa.    public static bool TryParse(string? line, out Reading reading, out string error)    {        reading = default;        error = "";        if (string.IsNullOrWhiteSpace(line)) { error = "empty line"; return false; }        string[] f = line.Trim().Split(',');        if (f.Length != 3) { error = $"expected 3 fields, got {f.Length}"; return false; }        var inv = CultureInfo.InvariantCulture;      // "23.41" on every PC, regardless of host locale        if (!double.TryParse(f[0], NumberStyles.Float, inv, out double t) ||            !double.TryParse(f[1], NumberStyles.Float, inv, out double h) ||            !double.TryParse(f[2], NumberStyles.Float, inv, out double p))        { error = "not a number"; return false; }        if (t is < -40 or > 85)    { error = $"temperature {t} out of range"; return false; }        if (h is < 0 or > 100)     { error = $"humidity {h} out of range"; return false; }        if (p is < 300 or > 1100)  { error = $"pressure {p} out of range"; return false; }        reading = new Reading(t, h, p);        return true;    }}
P: Listing 22.2 — xUnit tests for the parser: a valid line, six kinds of bad line with the expected reason, and a check under de-DE culture settings (C#).
P: // xUnit tests for ReadingParser: dotnet test runs them in about a second, no hardware needed.using GardenBench;using Xunit;public class ReadingParserTests{    [Fact]    public void ValidLine_IsParsed()    {        Assert.True(ReadingParser.TryParse("23.41,45.2,1013.25\r\n", out var r, out _));        Assert.Equal(23.41, r.TempC, 3);        Assert.Equal(45.2, r.HumidityPct, 3);        Assert.Equal(1013.25, r.PressureHPa, 3);    }    [Theory]    [InlineData("", "empty line")]    [InlineData("23.41,45.2", "expected 3 fields, got 2")]    [InlineData("23,41;45,2;1013,25", "expected 3 fields, got 4")]    // Decimal-comma locale input    [InlineData("23.41,abc,1013.25", "not a number")]    [InlineData("123.0,45.2,1013.25", "temperature 123 out of range")]    [InlineData("23.41,45.2,0", "pressure 0 out of range")]    public void BadLine_IsRejectedWithReason(string line, string expected)    {        Assert.False(ReadingParser.TryParse(line, out _, out string error));        Assert.Equal(expected, error);    }    [Fact]    public void ParsingDoesNotDependOnPcCulture()    {        var saved = System.Globalization.CultureInfo.CurrentCulture;        try        {            System.Globalization.CultureInfo.CurrentCulture = new System.Globalization.CultureInfo("de-DE");            Assert.True(ReadingParser.TryParse("23.41,45.2,1013.25", out var r, out _));            Assert.Equal(23.41, r.TempC, 3);        }        finally { System.Globalization.CultureInfo.CurrentCulture = saved; }    }}
H2: Worked Example 22.1: Tests that find a locale-dependent parsing bug
P: Problem. A first draft of the parser used double.Parse(f[0]) without a culture. Which test of Listing 22.2 fails with the de-DE locale active, what does the user see, and why does the test set the culture explicitly?
P: Solution. Under de-DE the comma is the decimal separator and the period a thousands separator, so double.Parse("23.41") returns 2341, as Problem 3 of Chapter 5 showed. ParsingDoesNotDependOnPcCulture switches the thread to de-DE and expects 23.41; with the old code it would fail with 2341, and the user would see the temperature out of range or, worse, accepted as 2341 if the range check were missing. The test sets the culture itself so it fails on every developer's PC and on the build server, not only on the customer's. With Listing 22.1 all 13 tests of Listings 22.2 and 22.5 pass in under half a second (dotnet test, .NET 10).
H2: 22.2 The dashboard and its threads
P: WPF, like every desktop framework, allows only the UI thread to touch controls. SerialPort's DataReceived event runs on a thread-pool thread. The bridge is the window's Dispatcher: BeginInvoke queues a small piece of work on the UI thread and returns at once. Keep the work in the event handler short (read the lines, parse them) and the work on the UI thread shorter (update the text and the plot). For real projects a chart library such as ScottPlot or LiveCharts replaces the hand-drawn Polyline of the listing.

P: Listing 22.3, part 2 — The dashboard code: serial data parsed on the event thread and handed to the UI thread with Dispatcher.BeginInvoke, with a five-minute rolling plot (C#, WPF).
P: // WPF dashboard: serial data arrives on a worker thread and is handed to the UI thread.using System;using System.Collections.Generic;using System.IO.Ports;using System.Linq;using System.Windows;using System.Windows.Media;namespace GardenBench;public partial class MainWindow : Window{    private SerialPort? _port;    private readonly Queue<double> _temps = new();    private const int MaxPoints = 300;               // 5 minutes at one reading per second    public MainWindow()    {        InitializeComponent();        PortBox.ItemsSource = SerialPort.GetPortNames();        PortBox.SelectedIndex = 0;        Closed += (_, _) => _port?.Close();    }    private void Connect_Click(object sender, RoutedEventArgs e)    {        if (PortBox.SelectedItem is not string name) return;        _port?.Close();        _port = new SerialPort(name, 115200) { NewLine = "\r\n", ReadTimeout = 2000 };        _port.DataReceived += OnData;                // raised on a thread-pool thread        try { _port.Open(); StatusText.Text = $"connected to {name}"; }        catch (Exception ex) { StatusText.Text = ex.Message; }    }    private void OnData(object sender, SerialDataReceivedEventArgs e)    {        var port = (SerialPort)sender;        while (port.IsOpen && port.BytesToRead > 0)        {            string line;            try { line = port.ReadLine(); } catch (TimeoutException) { return; }            bool ok = ReadingParser.TryParse(line, out var r, out string error);            // Never touch a control from this thread: queue the update on the UI thread.            Dispatcher.BeginInvoke(() =>            {                if (ok) Show(r); else StatusText.Text = "bad line: " + error;            });        }    }    private void Show(Reading r)    {        ValueText.Text = $"{r.TempC:F2} °C   {r.HumidityPct:F1} %   {r.PressureHPa:F1} hPa";        _temps.Enqueue(r.TempC);        if (_temps.Count > MaxPoints) _temps.Dequeue();        double lo = _temps.Min() - 0.5, hi = _temps.Max() + 0.5;        double w = Plot.ActualWidth, h = Plot.ActualHeight;        TempLine.Points = new PointCollection(_temps.Select((t, i) =>            new Point(i * w / (MaxPoints - 1), h - (t - lo) / (hi - lo) * h)));    }}

H2: Worked Example 22.2: How much does the plot keep?
P: Problem. The node sends one line per second. The plot keeps the last 300 points in a queue and redraws a Polyline on every reading. How much time does the plot cover, how much memory does it hold, and is redrawing every second a problem?
P: Solution. 300 points at one per second is 5 minutes. The queue holds 300 doubles, 2400 bytes, and the PointCollection 300 points of two doubles, 4800 bytes: nothing. Redrawing 300 points once a second costs well under a millisecond. The limits arrive at higher rates: at 1000 lines per second, each BeginInvoke call is a small allocation and a queued message, and the UI thread spends its time on updates the eye cannot follow. Then the handler should collect readings and the UI should refresh on a timer at 10 to 30 Hz with whatever has arrived, and the plot should decimate to about the pixel width of the canvas.
H2: 22.3 The production test bench
P: A test bench in production is a program that measures every board against limits and writes a record no one can argue with: the board's serial number, each step's measured value, its limits, pass or fail, and the time in UTC. Its own logic is tested like any other code, with fake instruments behind small interfaces, so the limit arithmetic is proven before the first board arrives. The real DMM behind IDmm is a SCPI instrument (Chapter 21's commands, sent from C# through a VISA library or a raw socket); the real IDut is the board's serial port.
P: Listing 22.4 — A production test with instrument interfaces, limit checks for the 3.3 V rail and the sensor, and a CSV record per step (C#).
P: // Production test: check the 3.3 V rail and the sensor of each garden-node board, log pass/fail.using System;using System.Collections.Generic;using System.Globalization;using System.IO;namespace GardenBench;public interface IDmm { double ReadVoltage(); }                 // real: SCPI over USB; tests: a fakepublic interface IDut { string SerialNumber { get; } string? ReadLine(); }public record StepResult(string Name, double Value, double Low, double High){    public bool Pass => Value >= Low && Value <= High;}public class TestBench{    private readonly IDmm _dmm;    private readonly IDut _dut;    public TestBench(IDmm dmm, IDut dut) { _dmm = dmm; _dut = dut; }    public List<StepResult> Run()    {        var results = new List<StepResult>();        const double nominal = 3.30, tol = 0.03;                  // 3.30 V +-3 %        results.Add(new StepResult("3V3 rail", _dmm.ReadVoltage(), nominal * (1 - tol), nominal * (1 + tol)));        bool ok = ReadingParser.TryParse(_dut.ReadLine(), out var r, out _);        results.Add(new StepResult("sensor answers", ok ? 1 : 0, 1, 1));        if (ok) results.Add(new StepResult("room temperature", r.TempC, 15, 35));        return results;    }    public static void Log(string path, string serial, IEnumerable<StepResult> steps)    {        using var w = new StreamWriter(path, append: true);        string stamp = DateTime.UtcNow.ToString("yyyy-MM-ddTHH:mm:ssZ", CultureInfo.InvariantCulture);        foreach (var s in steps)            w.WriteLine(string.Join(",", stamp, serial, s.Name,                s.Value.ToString("F3", CultureInfo.InvariantCulture),                s.Low.ToString("F3", CultureInfo.InvariantCulture),                s.High.ToString("F3", CultureInfo.InvariantCulture), s.Pass ? "PASS" : "FAIL"));    }}

P: // Test the test bench itself with fake instruments: no board, no DMM, runs in CI.using System.Linq;using GardenBench;using Xunit;class FakeDmm : IDmm { public double V; public double ReadVoltage() => V; }class FakeDut : IDut { public string SerialNumber => "GN-0001"; public string? Line; public string? ReadLine() => Line; }public class TestBenchTests{    [Theory]    [InlineData(3.30, true)]    [InlineData(3.205, true)]      // just above the low limit 3.201    [InlineData(3.19, false)]    [InlineData(3.41, false)]    public void RailLimits(double volts, bool pass)    {        var bench = new TestBench(new FakeDmm { V = volts }, new FakeDut { Line = "23.41,45.2,1013.25" });        Assert.Equal(pass, bench.Run().Single(s => s.Name == "3V3 rail").Pass);    }    [Fact]    public void SilentSensor_FailsAndSkipsTemperature()    {        var steps = new TestBench(new FakeDmm { V = 3.30 }, new FakeDut { Line = null }).Run();        Assert.False(steps.Single(s => s.Name == "sensor answers").Pass);        Assert.DoesNotContain(steps, s => s.Name == "room temperature");    }}
H2: Worked Example 22.3: Limits and the guard band
P: Problem. The 3.3 V rail must be within ±3 %. Find the limits. The DMM's uncertainty at this range is ±0.010 V. Find guard-banded limits that keep bad boards from passing, and decide a board that measures 3.205 V under both.
P: Solution. Limits: 3.30 × 0.97 = 3.201 V and 3.30 × 1.03 = 3.399 V; Listing 22.5 confirms that 3.205 V passes and 3.19 V and 3.41 V fail. A reading of 3.205 V could come from a true 3.195 V, outside the specification, so a guard band shrinks the test limits by the uncertainty: 3.211 V to 3.389 V. The board at 3.205 V now fails and is retested or examined. The guard band costs a few good boards near the edge and keeps bad ones from shipping; how large the uncertainty really is belongs to the instrument's specifications and Book 7.

P: Key idea. Put parsing, limits, and decisions in plain classes with unit tests; let the window and the port do nothing but connect them. Update controls only on the UI thread, through the Dispatcher.
P: Common misconception. Testing the dashboard only on the developer's PC. The customer's PC has a different culture, a different COM port number, a USB hub that sleeps, and a second program holding the port. Parse with the invariant culture, let the user choose the port, catch the exception from Open, and show a message that says what to do.

P: On the Job
P: On the Job: A test bench in production outlives its author. Write the limits into a configuration file with a revision number, log that revision with every result, and keep the bench software under version control with tagged releases. When a customer asks in two years how board 4711 was tested, the answer is one search in the log and one checkout of the tag.
BENCH: Before a test bench goes to production, run a known-good board through it twenty times and look at the spread of each measurement. If the 3.3 V reading varies by 15 mV between runs, the fixture's contacts or the DMM's settling, not the boards, will decide who passes near the limits.
