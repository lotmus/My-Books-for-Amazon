PART: Part IV. Connected and Intelligent Devices
H1: Chapter 17. Wi-Fi and MQTT
P: Forty sensor nodes in a greenhouse ran without trouble for a month. Then the power failed for ten seconds. When it came back, all forty rebooted at the same moment, all forty asked the router for an address, all forty hammered the broker, and the broker, a small Pi in a cupboard, fell over and took the rest of the night to recover. Each node's firmware was correct on its own. Together they were a denial-of-service attack. Connected firmware has to be written for the bad day: the dropped link, the restarted router, and the thousand siblings that restart with it.
P: Where you meet this: Home automation, smart meters, greenhouse and building sensors, industrial monitoring, anything with a cloud dashboard, and every "it was online yesterday" support call.
H2: 17.1 Wi-Fi from firmware
P: The ESP32-S3 has 2.4 GHz Wi-Fi (802.11 b/g/n) and Bluetooth LE on the chip, and the ESP-IDF driver is event-driven: you start the station, and the driver reports events such as started, connected, got an IP address, and disconnected, to a handler you register. The firmware's job is to react to those events, never to assume the link is up. Three rules prevent most field failures. Credentials are configuration, not code: they come from menuconfig, a secrets file kept out of version control, or a provisioning step, never from a string literal that ends up in git. Every disconnect leads to a reconnect, forever. And nothing that needs the network blocks anything that does not: the sensor keeps measuring and the display keeps updating while Wi-Fi is down. Remember from Chapter 8 that ADC2 is not available while Wi-Fi runs.
H2: 17.2 MQTT in one page
P: MQTT is a small publish-subscribe protocol over TCP. Devices do not talk to each other; they publish messages to a broker under a topic such as lab/garden/bme280, and any client that subscribed to that topic, or to a wildcard such as lab/garden/#, receives them. The broker can be Mosquitto on the Pi 5 or a cloud service. Four features do most of the work. QoS 0 sends once with no confirmation; QoS 1 repeats until the broker acknowledges, so a message can arrive twice; QoS 2 delivers exactly once at the cost of a four-message handshake. A retained message is stored by the broker and delivered at once to new subscribers, so a dashboard that starts later sees the last value. The keepalive makes a silent client's connection time out. And the last will is a message the broker publishes on the client's behalf when it disappears without saying goodbye, such as lab/garden/status = offline.

H2: Worked Example 17.1: The spec for the network module
P: Problem. Apply step 1 of the method to the garden node's network module before writing any code: topics, payload, QoS, timing, and failure behavior.
P: Solution. Purpose: publish one BME280 reading per minute to the lab broker. Topics: lab/garden/bme280 for data, lab/garden/status for "online" (retained, published on connect) and "offline" (the last will). Payload: JSON {"t":23.41,"h":45.2,"p":1013.25}, units °C, %, hPa, fixed decimals. QoS 1 for data (a duplicate is harmless, a gap is not), keepalive 120 s. Failure behavior: sensor reading and display continue without the network; Wi-Fi and MQTT reconnect with exponential back-off from 1 s to 60 s with 25 % jitter; readings during an outage are dropped in this version (buffering is a later iteration). Acceptance tests: (1) messages arrive in the CSV log every 60 ± 1 s; (2) the router is switched off for 5 minutes and the node is publishing again within 75 s of it returning; (3) the broker shows "offline" within 3 minutes of unplugging the node (1.5 × keepalive); (4) 7 days without a reset.

H2: Worked Example 17.2: How big is one reading?
P: Problem. Find the size of one MQTT PUBLISH packet for the topic lab/garden/bme280 and the payload {"t":23.41,"h":45.2,"p":1013.25} at QoS 0 and at QoS 1, and the data per day at one message per minute.
P: Solution. The topic is 17 bytes and the payload 32. The variable header holds a 2-byte topic length and the topic, so the remaining length is 2 + 17 + 32 = 51 bytes, which fits in one length byte; with the 1-byte packet type the packet is 53 bytes at QoS 0. QoS 1 adds a 2-byte packet identifier (55 bytes) and a 4-byte PUBACK from the broker. At 1440 messages per day, 53 bytes make 76 kB; with 40 bytes of IPv4 and TCP headers per packet it is 134 kB per day before Wi-Fi framing. That is nothing for Wi-Fi, but it is the reason the same reading goes as 8 binary bytes over LoRa (Chapter 18).
H2: 17.3 Reconnecting politely
P: A reconnect loop that retries at once, forever, works for one device and fails for a hundred. Exponential back-off doubles the wait after every failure up to a cap, so a dead broker is not hammered. Jitter, a random fraction taken off each wait, spreads devices that failed at the same moment, so they do not all return in the same second.
P: Listing 17.3 — Exponential back-off from 1 s to a 60 s cap with up to 25 % jitter (C, runs on the PC).
P: // Reconnect back-off: 1, 2, 4, ... s capped at 60 s, with up to 25 % random jitter.// Pure C, runs on the PC; on the ESP32-S3 replace rand() with esp_random().#include <stdint.h>#include <stdio.h>#include <stdlib.h>static uint32_t backoff_ms(unsigned attempt){    uint32_t base = 1000u << (attempt < 6 ? attempt : 6);   // 1 s .. 64 s    if (base > 60000u) base = 60000u;                       // cap at 60 s    uint32_t jitter = (uint32_t)rand() % (base / 4 + 1);    // 0 .. 25 %    return base - jitter;                                   // never more than the cap}int main(void){    srand(1);    uint32_t total = 0;    for (unsigned a = 0; a < 10; a++) {        uint32_t d = backoff_ms(a);        total += d;        printf("attempt %u: wait %5.1f s (total %6.1f s)\n", a + 1, d / 1000.0, total / 1000.0);    }    return 0;}
H2: Worked Example 17.3: Forty nodes after a power cut
P: Problem. Forty nodes reboot together. Without jitter, with the waits 1, 2, 4, 8, 16, 32, 60, 60, 60, 60 s, how long has a node waited after ten failed attempts, and how many nodes reach the broker in the same second? With 25 % jitter at the 60 s step, how are they spread?
P: Solution. Without jitter the waits add to 1 + 2 + 4 + 8 + 16 + 32 + 4 × 60 = 303 s, and all forty retry in the same second every time, which is the hook's failure. With 25 % jitter each wait at the cap falls anywhere between 45 and 60 s, so the forty retries spread over 15 s, about 2.7 per second, a load any broker survives. Listing 17.3 prints one node's sequence: 0.8, 1.6, 3.2, 8.0, 13.5, 30.7, 57.6 s, and so on.

P: Key idea. Write connected firmware for the bad day: event-driven connection handling, credentials outside the source, reconnect forever with back-off and jitter, and a last will so the rest of the system knows when a node is gone.
P: Common misconception. Testing the network code only on a good link. Unplug the router, restart the broker, fill the Wi-Fi band with traffic, and power-cycle all nodes together before calling it done; those are the failures the field delivers in the first month.

P: On the Job
P: On the Job: In a product team the broker, the topic tree, and the payload format are usually owned by a backend or cloud colleague, not the firmware engineer. Agree them in writing (step 1 of the method, shared) before either side writes code, and version the payload with a field such as "v":1 from day one. The most expensive bug in connected products is a payload change that the server and half the deployed devices understand differently.
BENCH: Run mosquitto_sub -v -t "lab/#" in a terminal on the PC or Pi whenever a networked node is on the bench. It shows every message with its topic, so a misspelled topic, a missing decimal, or a node that went silent is visible at once without any dashboard.
