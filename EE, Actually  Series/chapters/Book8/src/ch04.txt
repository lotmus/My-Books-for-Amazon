H1: Chapter 4. Python Twice: MicroPython on the Board, Python on the PC
P: Type four lines into a serial terminal connected to an ESP32-S3, press Enter, and the board lists every I2C device it can see. No compiler, no flashing, no build folder: the chip runs a Python interpreter, and you are talking to it. Ten minutes later the same language, on your PC, is writing the sensor's readings to a spreadsheet file. That double life is why Python is the fastest way from "does this sensor even answer?" to a plot of last night's temperature.
P: Where you meet this: Bringing up a new sensor, teaching and prototyping on the Pico and ESP32, logging data on the PC, and every bench script that talks to a board over USB.
H2: 4.1 MicroPython and CircuitPython
P: MicroPython is a compact implementation of Python 3 for microcontrollers. It runs on the ESP32 family, the RP2040 and RP2350, STM32 boards, and the nRF52840. After flashing its firmware once, you get an interactive prompt, the REPL, over USB serial, and you upload .py files with an editor such as Thonny or the mpremote command-line tool. A file named main.py runs at boot. The machine module gives access to pins, buses, timers, and sleep modes; the API is similar across chips, so code moves between an ESP32-S3 and a Pico with few changes.
P: CircuitPython is Adafruit's version of the same idea, tuned for beginners. The board appears as a USB drive called CIRCUITPY, you edit code.py on it, and the board restarts the program every time the file is saved. Its library bundle covers hundreds of sensors and displays with a uniform style. It uses the board and busio modules instead of machine, so code does not move unchanged between the two.
P: The price of this convenience is speed and memory. Python code is interpreted, so a loop that toggles a pin runs many times slower than the same loop in C, and every object carries overhead in RAM. For reading a sensor once a second, driving a display, or logging, it does not matter. For a 40 kHz control loop or a protocol with microsecond timing, it does; there, the work belongs in C or in a hardware peripheral that MicroPython configures, such as the RP2040's PIO state machines or a hardware timer.
P: Listing 4.1 — MicroPython on the ESP32-S3: scan the I2C bus, read the BME280 chip ID, and read the raw temperature once a second.
P: # MicroPython on the ESP32-S3: find the BME280, read its chip ID and raw temperature.from machine import I2C, Pinimport timei2c = I2C(0, scl=Pin(9), sda=Pin(8), freq=400_000)print("devices:", [hex(a) for a in i2c.scan()])   # expect 0x3c (OLED) and 0x76BME = 0x76chip_id = i2c.readfrom_mem(BME, 0xD0, 1)[0]print("chip id: 0x%02x" % chip_id)                # 0x60 = BME280, 0x58 = BMP280i2c.writeto_mem(BME, 0xF2, b"\x01")   # humidity oversampling x1 (set before ctrl_meas)i2c.writeto_mem(BME, 0xF4, b"\x27")   # temperature x1, pressure x1, normal modewhile True:    d = i2c.readfrom_mem(BME, 0xFA, 3)            # temp_msb, temp_lsb, temp_xlsb    raw_t = (d[0] << 12) | (d[1] << 4) | (d[2] >> 4)    print("raw temperature:", raw_t)              # 20-bit value; compensation needs the calibration data    time.sleep(1)
P: Listing 4.1 is the bring-up script for the reader lab's BME280. The scan should report 0x76 (or 0x77, if the board's address pin is tied high) and 0x3C for the OLED. A chip ID of 0x60 confirms a BME280; 0x58 means the board carries the cheaper BMP280, which has no humidity sensor, a mix-up that is common with low-cost modules. The raw temperature is a 20-bit number that the sensor's calibration constants turn into degrees; in practice you use a driver library for that step, and Chapter 9 shows what such a driver does.
H2: Worked Example 4.1: Is MicroPython fast enough?
P: Problem. You time a MicroPython loop that toggles a pin 10 000 times with time.ticks_us() and measure 52 ms. What square-wave frequency does the loop produce? Is MicroPython fast enough to (a) read the BME280 once per second, (b) generate the 40 kHz burst of an ultrasonic transmitter by toggling a pin?
P: Solution. Each toggle takes 52 ms/10 000 = 5.2 µs. One period of the square wave is two toggles, 10.4 µs, so the frequency is about 96 kHz, with jitter whenever the interpreter does housekeeping such as garbage collection. (a) Yes, by a factor of thousands: a BME280 read takes about a millisecond of bus time. (b) No: 40 kHz needs a toggle every 12.5 µs with jitter well below a microsecond, and the interpreter's pauses would ruin the burst. Use a PWM peripheral (Chapter 7) configured from MicroPython instead. The method's point is to decide with a measurement, not a feeling.
H2: 4.2 Python on the PC
P: On the PC, Python is the glue of the bench. With the pyserial package it reads a board's serial output; with pyvisa it controls oscilloscopes and power supplies (Chapter 21); with numpy and matplotlib it analyzes and plots; with pytest it runs automated tests (Chapter 24). The same code runs on Windows, macOS, Linux, and on the Raspberry Pi 5, which is a full Linux computer.
P: Two habits keep PC scripts reliable. Create a virtual environment for each project (python -m venv .venv) and record its packages in a requirements.txt file, so that the script still runs next year on another machine. And treat the serial link as unreliable: lines can be truncated at startup, characters can be corrupted, and the board can be unplugged. Listing 4.2 shows the pattern: a timeout, a check of the field count, and a check that each field is a number, before anything is written.
P: Listing 4.2 — A PC logger with pyserial: reads CSV lines from the board, validates them, and appends them with a timestamp to log.csv (Python).
P: """Log 'temperature,humidity,pressure' lines from the ESP32-S3 to log.csv with PC timestamps."""import csvimport sysfrom datetime import datetimeimport serial  # pyserialPORT = sys.argv[1] if len(sys.argv) > 1 else "COM5"with serial.Serial(PORT, 115200, timeout=2) as ser, open("log.csv", "a", newline="") as f:    writer = csv.writer(f)    while True:        line = ser.readline().decode("ascii", errors="replace").strip()        if not line:            print("timeout: no data for 2 s")            continue        fields = line.split(",")        if len(fields) != 3:            print("bad line:", line)            continue        try:            t, h, p = (float(x) for x in fields)        except ValueError:            print("bad number:", line)            continue        writer.writerow([datetime.now().isoformat(timespec="seconds"), t, h, p])        f.flush()   # keep the file valid if the script is stopped
H2: Worked Example 4.2: How many lines per second can the link carry?
P: Problem. The ESP32-S3 sends lines such as 23.41,45.2,1013.25 followed by carriage return and line feed, at 115 200 baud with 8N1 framing. How long does one line take, and what is the maximum line rate? How big does log.csv grow in 24 hours at one line per second, if each logged row is 40 bytes?
P: Solution. The line has 18 visible characters plus 2 line-ending characters, 20 bytes. With 10 bits per byte, that is 200 bits, and at 115 200 bit/s it takes 200/115 200 = 1.74 ms. The maximum rate is 1/1.74 ms = 576 lines per second. At one line per second the link is 0.17 % busy. The log grows by 86 400 × 40 = 3 456 000 bytes, about 3.5 MB per day, or about 1.2 GB per year. The usual mistake is to forget the start and stop bits and divide by 8 instead of 10, which overstates the rate by 25 %.

P: The Pi 5 deserves a separate mention. It runs the same desktop Python, has I2C, SPI, UART, and GPIO on its 40-pin header, and its gpiozero and lgpio libraries drive them. For a project that needs a camera, a large display, or a neural network (Chapter 20), the Pi 5 does the heavy work in Python while an ESP32 or Pico handles the microsecond timing.
P: AI Pair-Programming Note
P: Assistants often mix MicroPython, CircuitPython, and desktop Python: import board in a MicroPython script, machine.Pin on a PC, or a CPython library that does not exist on the microcontroller. Name the exact runtime and board in the prompt, and run the script once in the REPL line by line before trusting it.
BENCH: When the REPL stops answering, the board is usually stuck in a loop in main.py. Press Ctrl-C in the terminal to interrupt it, or Ctrl-D for a soft reset. If main.py crashes the board before the REPL appears, connect with mpremote and use its command to remove the file, or reflash MicroPython. Keep main.py short and do the work in an imported module, so a typo does not lock you out.
