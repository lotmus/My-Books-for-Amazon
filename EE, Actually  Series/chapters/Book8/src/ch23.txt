H1: Chapter 23. Debugging
P: The node crashed about once a day, never on the bench, always at night. The developer added printf calls around the suspicious code, and the crash stopped. When the developer removed them, the crash returned. The printf calls had not fixed anything; at 115 200 baud each one took three and a half milliseconds, which changed the timing enough to hide a race between an interrupt and a task. A debugging tool that changes the behavior it observes can make a bug vanish without removing it. This chapter is about seeing inside a running system while disturbing it as little as possible, and about a procedure that finds bugs instead of chasing them.
P: Where you meet this: Every project, every week. Debugging is most of the time spent on firmware, and the engineers who are fast at it are fast because they are systematic, not because they guess well.
H2: 23.1 A procedure, not a hunt
P: Debugging follows the scientific method in small steps. Reproduce the failure, ideally on demand; a bug that occurs once a day becomes tractable when a test makes it occur once a minute. Gather facts before theories: the exact symptom, the last good version, what changed. Form one hypothesis, design an observation that can disprove it, and make it. Change one thing at a time. When it is fixed, explain why the fix works, add a test that would have caught it, and write the cause into the commit message: this is step 8 of the method, a precise bug report, written to your future self. "Git bisect" automates the search for the last good version: it checks out the commit halfway between a good and a bad one, you test, and in about ten steps it finds the guilty commit among a thousand.
H2: 23.2 The instruments of debugging
P: Each tool sees something the others miss. A debug probe on the SWD or JTAG pins (the ESP32-S3 has one built in on its USB port; the Pico uses the Raspberry Pi Debug Probe, STM32 boards an ST-LINK, and J-Link works with most) lets you stop the CPU, step through code, read variables and registers, and set watchpoints that stop the program when a memory location changes, the fastest way to find out who overwrites a variable. Serial logging shows the history but costs time. A logic analyzer records digital signals over seconds with exact timing and decodes I2C, SPI, and UART; inexpensive 8-channel analyzers with the open-source sigrok and PulseView software cover most hobby needs. An oscilloscope shows the analog truth: rise times, ringing, and brown-outs that a logic analyzer cannot see. And a spare GPIO toggled in the code is the cheapest timing instrument there is.
H2: Worked Example 23.1: What printf costs
P: Problem. A debug line of 40 characters is printed at 115 200 baud with 8N1 framing. How long does it take if the call waits for the UART, and what does that do to a 1 kHz control loop?
P: Solution. Each character is 10 bits on the line (start, 8 data, stop), so 40 × 10/115 200 = 3.47 ms. In a 1 kHz loop that has 1 ms per cycle, one such line makes the loop miss three or four deadlines. With a buffered UART driver, printf returns sooner until the buffer fills, which makes the cost intermittent, worse for debugging than a constant one. A RAM trace avoids UART transmission in the timing-critical path, but its overhead must be measured on the target; the same is true of a GPIO timing probe.

P: Listing 23.1 — A RAM trace buffer with timestamps and an atomic index (C, PC simulation). On a target, verify that atomic_uint is lock-free and ISR-safe; dump only after writers stop or protect the snapshot, since the counter does not synchronize reads of the trace buffer.
P: // A RAM trace avoids serial output in the timing-critical path; measure its target overhead.// Events are stored in RAM with a timestamp and printed later, outside the timing-critical code.// Pure C, runs on the PC; on the target, now_us() reads a hardware timer.#include <stdatomic.h>#include <stdint.h>#include <stdio.h>#define TRACE_LEN 64                       // power of two, so the index wraps with a masktypedef struct { uint32_t t_us; uint16_t id; uint16_t arg; } trace_t;static trace_t trace_buf[TRACE_LEN];static atomic_uint trace_head;             // total events ever writtenstatic uint32_t fake_clock;static uint32_t now_us(void) { return fake_clock; }      // target: esp_timer_get_time() etc.static inline void trace(uint16_t id, uint16_t arg)      // Atomic ticket; verify lock-free ISR support on the target{    uint32_t i = atomic_fetch_add(&trace_head, 1) & (TRACE_LEN - 1);    trace_buf[i] = (trace_t){ now_us(), id, arg };}enum { EV_ISR = 1, EV_TASK_START, EV_TASK_END, EV_I2C_NACK };static const char *names[] = { "?", "isr", "task start", "task end", "i2c nack" };static void trace_dump(void)               // call from a low-priority task or on a fault{    uint32_t head = atomic_load(&trace_head);    uint32_t n = head < TRACE_LEN ? head : TRACE_LEN;    for (uint32_t k = head - n; k != head; k++) {        const trace_t *e = &trace_buf[k & (TRACE_LEN - 1)];        printf("%8lu us  %-10s %u\n", (unsigned long)e->t_us, names[e->id], e->arg);    }}int main(void){    for (int cycle = 0; cycle < 25; cycle++) {        // 25 x 3 + 1 = 76 events; the buffer keeps 64        fake_clock = 1000u * cycle;      trace(EV_ISR, cycle);        fake_clock += 12;                trace(EV_TASK_START, cycle);        if (cycle == 22) { fake_clock += 250; trace(EV_I2C_NACK, 0x76); }        fake_clock += 180;               trace(EV_TASK_END, cycle);    }    printf("%u events written, the last %d kept\n", atomic_load(&trace_head), TRACE_LEN);    trace_dump();    return 0;}
H2: Worked Example 23.2: Reading the trace
P: Problem. Listing 23.1 records an interrupt, a task start, and a task end every millisecond for 25 cycles, plus one I2C NACK in cycle 22. The buffer holds 64 events. Which events are kept, and what does the tail tell you?
P: Solution. 25 × 3 + 1 = 76 events are written; the buffer keeps the last 64, so the first 12, cycles 0 to 3, are overwritten, and the dump starts at 4000 µs. The normal cycle reads isr at 0, task start at +12 µs, task end at +192 µs: the task runs for 180 µs. In cycle 22 the trace shows i2c nack 118 (0x76, the BME280) at 22 262 µs and the task end at 22 442 µs, 430 µs after the start: the NACK and its retry cost 250 µs, which is what this cycle's late output came from. These PC timestamps come from fake_clock; on hardware, replace now_us with a verified timer and measure capture overhead on the target.

H2: Worked Example 23.3: Choosing the logic analyzer's sample rate
P: Problem. Find a sample rate for decoding I2C at 400 kHz and UART at 115 200 baud, and the timing resolution each gives. The analyzer can do up to 24 MS/s on 8 channels.
P: Solution. An I2C bit at 400 kHz lasts 2.5 µs. Decoders need at least four samples per bit and work reliably with about ten, so 4 MS/s or more; at 24 MS/s there are 60 samples per bit and the resolution is 42 ns. A UART bit at 115 200 baud lasts 8.68 µs; 1 MS/s gives 8.7 samples per bit, enough to decode, and 4 MS/s makes the timing of a stop bit or a gap clear to 0.25 µs. Undersampling does not produce an error message; the decoder shows wrong bytes, which look like a firmware bug.

P: Key idea. Reproduce, observe, form one hypothesis, change one thing. Choose the tool that disturbs least: a probe pin or a trace buffer for timing, a debugger for state, a logic analyzer for buses, a scope for the analog truth.
P: Common misconception. Debugging by changing code until the symptom disappears. A bug that vanished without an explanation has usually moved. If you cannot say why the fix works, keep looking, and keep the reproduction case as a test.
P: AI Pair-Programming Note
P: Assistants are good debugging partners when given facts: paste the exact panic output, the decoded backtrace, the relevant code, and what you have already ruled out, and ask for hypotheses ranked by likelihood with an observation to test each. They are poor at guessing from "it crashes sometimes". Their first suggestion is often a plausible change to try, which is the trial-and-error the procedure avoids; ask what observation would distinguish the hypotheses instead.
BENCH: When a board resets for no visible reason, print the reset reason at boot (esp_reset_reason() on the ESP32-S3) before anything else. Brown-out, watchdog, panic, and power-on each point in a different direction, and a brown-out sends you to the scope and the supply (Book 6), not to the code.
H2: Practice
P: 1. (Core) How long does a 25-character debug line take at 115 200 baud, 8N1?
P: 2. (Core) What does a watchpoint do, and which kind of bug does it find fastest?
P: 3. (Core) Which instrument shows ringing on an SPI clock line, a logic analyzer or a scope?
P: 4. (Core) A git history has 1000 commits between a good and a bad version. How many bisect steps, at most?
P: 5. (Extension) A probe pin shows a 6.4 µs pulse at each interrupt, 2000 times per second. What fraction of the CPU does the ISR use?
P: 6. (Extension) Why must the trace buffer's index be claimed atomically, and what goes wrong with trace_head++ on a plain variable?
P: 7. (Extension) Choose a sample rate for SPI at 8 MHz, and say whether a 24 MS/s analyzer is enough.
P: 8. (Challenge) A node resets every few days with reset reason "task watchdog". Write the debugging plan: what to log, how to make it reproduce faster, and which hypotheses to test first.
