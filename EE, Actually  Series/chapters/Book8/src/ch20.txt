H1: Chapter 20. Cameras, Point Clouds, and Edge AI
P: A light pulse leaves the sensor, hits a wall one meter away, and comes back 6.7 nanoseconds later. To tell one meter from one meter and one centimeter, the chip must resolve 67 picoseconds, the time light needs for two centimeters. The VL53L1X, a chip a few millimeters across, does this thousands of times per measurement and hands the firmware a single number in millimeters. A camera hands it 150 000 bytes per frame instead, and an event camera a stream of individual pixel changes with microsecond timestamps. This chapter is about turning those three kinds of optical data into decisions on small hardware.
P: Where you meet this: Doorbells and wildlife cameras, robot vacuums, gesture and presence sensors in phones and laptops, drones that avoid obstacles, industrial inspection, and every product described as having "AI on the edge".
H2: 20.1 A camera on the ESP32-S3
P: The ESP32-S3 boards with a camera, such as the ESP32-S3-EYE and its many clones, connect an OV2640 or similar sensor through an 8-bit parallel interface plus a configuration bus (SCCB, a dialect of I2C). The esp32-camera component configures the sensor and fills frame buffers by DMA. Three choices dominate. The pixel format: JPEG compressed by the sensor itself, or raw RGB565 or grayscale for image processing. The frame size. And where the buffers live: raw frames are large, so they go in PSRAM. The camera also takes most of the free GPIO, so the spec's pin table must be redone: on the ESP32-S3-EYE pinout, GPIO 8 and 9, the reader lab's I2C pins, become camera data lines, and the BME280 moves.
P: Listing 20.1 — Camera setup for an ESP32-S3-EYE-style board: QVGA JPEG with two frame buffers in PSRAM, and a frame-rate measurement (ESP-IDF with esp32-camera, C).
P: // ESP-IDF + esp32-camera: OV2640 on an ESP32-S3-EYE-style board, QVGA JPEG, frame buffers in PSRAM.#include "esp_camera.h"#include "esp_log.h"#include "esp_timer.h"static const char *TAG = "cam";esp_err_t camera_start(void){    camera_config_t c = {        .pin_pwdn = -1, .pin_reset = -1, .pin_xclk = 15,        .pin_sccb_sda = 4, .pin_sccb_scl = 5,        .pin_d7 = 16, .pin_d6 = 17, .pin_d5 = 18, .pin_d4 = 12,        .pin_d3 = 10, .pin_d2 = 8, .pin_d1 = 9, .pin_d0 = 11,        .pin_vsync = 6, .pin_href = 7, .pin_pclk = 13,        .xclk_freq_hz = 20000000,        .ledc_timer = LEDC_TIMER_0, .ledc_channel = LEDC_CHANNEL_0,        .pixel_format = PIXFORMAT_JPEG,          // the sensor compresses; RGB565 would be 153 600 bytes        .frame_size = FRAMESIZE_QVGA,            // 320 x 240        .jpeg_quality = 12,                      // 0..63, lower is better quality        .fb_count = 2,                           // capture the next frame while this one is used        .fb_location = CAMERA_FB_IN_PSRAM,        .grab_mode = CAMERA_GRAB_LATEST,    };    return esp_camera_init(&c);}void camera_measure(int frames){    int64_t t0 = esp_timer_get_time();    size_t bytes = 0;    for (int i = 0; i < frames; i++) {        camera_fb_t *fb = esp_camera_fb_get();        if (!fb) { ESP_LOGE(TAG, "capture failed"); continue; }        bytes += fb->len;                        // use fb->buf here: send, save, or analyze        esp_camera_fb_return(fb);                // always give the buffer back    }    int64_t us = esp_timer_get_time() - t0;    ESP_LOGI(TAG, "%d frames, %.1f fps, %u bytes per frame",             frames, frames * 1e6 / (double)us, (unsigned)(bytes / (frames ? frames : 1)));}
H2: Worked Example 20.1: The frame budget
P: Problem. Find the size of one QVGA (320 × 240) frame in RGB565 and of two buffers, the data rate of 640 × 480 RGB at 30 frames per second, and the Wi-Fi rate of a QVGA JPEG stream at about 10 kB per frame and 25 frames per second.
P: Solution. QVGA RGB565: 320 × 240 × 2 = 153 600 bytes; two buffers 307 200 bytes, most of the ESP32-S3's 512 kB internal SRAM, which Wi-Fi and FreeRTOS also need, so the buffers go in PSRAM. VGA RGB at 30 fps: 640 × 480 × 3 × 30 = 27.6 MB/s, far more than the chip can move or process, which is why the sensor's JPEG engine matters. The JPEG stream: 10 kB × 25 = 250 kB/s = 2 Mbit/s, comfortable on Wi-Fi. Image analysis on the S3 therefore works on small grayscale frames (96 × 96 for many person-detection models) while JPEG goes to the network.

H2: 20.2 Time of flight: one number, many photons
P: A direct time-of-flight sensor sends short infrared pulses (940 nm on the VL53L1X) and times their return with single-photon detectors (SPADs) and a time-to-digital converter. The round trip takes 2d/c, so one centimeter of distance is 66.7 ps of time. No single photon is timed that precisely; the sensor builds a histogram from thousands of pulses during its timing budget, and the peak gives the distance to a millimeter. The photonics are Book 3's. For the firmware the VL53L1X is an I2C device at address 0x29 with 16-bit register addresses, a model ID of 0xEA at register 0x010F, a timing budget from 20 ms (short mode only) or 33 ms (all modes) up to 1000 ms, and up to 50 measurements per second. Longer budgets reach farther: about 140 ms for the full 4 m in long mode.
EQ: t = 2d/c,    Δt per 1 cm = 2 × 0.01 m/(3 × 10⁸ m/s) = 66.7 ps
P: Listing 20.2 — Identifying a VL53L1X by its 16-bit model-ID register, then continuous ranging at 20 Hz with the Pololu library (Arduino C++ on the ESP32-S3).
P: // Arduino on the ESP32-S3: identify a VL53L1X by its 16-bit model-ID register,// then range continuously with the Pololu VL53L1X library.#include <Arduino.h>#include <Wire.h>#include <VL53L1X.h>const uint8_t ADDR = 0x29;                 // 7-bit address (0x52 in 8-bit notation)VL53L1X tof;static int read_reg8(uint16_t reg)         // VL53L1X registers have 16-bit addresses{    Wire.beginTransmission(ADDR);    Wire.write(reg >> 8);    Wire.write(reg & 0xFF);    if (Wire.endTransmission(false) != 0) return -1;   // repeated start    if (Wire.requestFrom(ADDR, (uint8_t)1) != 1) return -1;    return Wire.read();}void setup(){    Serial.begin(115200);    Wire.begin(1, 2, 400000);              // SDA 1, SCL 2: the camera board uses 8 and 9    int id = read_reg8(0x010F), type = read_reg8(0x0110);    Serial.printf("model id 0x%02X (expect 0xEA), module type 0x%02X (expect 0xCC)\n", id, type);    if (id != 0xEA || !tof.init()) {        Serial.println("VL53L1X not found");        while (true) delay(1000);    }    tof.setTimeout(500);    tof.setDistanceMode(VL53L1X::Long);    tof.setMeasurementTimingBudget(50000); // 50 ms, in microseconds    tof.startContinuous(50);               // one measurement every 50 ms, 20 Hz}void loop(){    uint16_t mm = tof.read();              // waits for the next result    if (tof.timeoutOccurred()) Serial.println("timeout");    else Serial.printf("%u mm\n", mm);}
H2: Worked Example 20.2: Light against sound
P: Problem. Compare the round-trip time for 1 m and the time per centimeter of the VL53L1X with the ultrasonic sensor of Chapter 7 (sound at 343 m/s), and find the measurement rate at a 50 ms timing budget.
P: Solution. Light: 2 × 1 m/(3 × 10⁸ m/s) = 6.67 ns for 1 m, 66.7 ps per centimeter. Sound: 2 × 1 m/343 m/s = 5.83 ms for 1 m, 58.3 µs per centimeter, almost a million times slower, which is why the ultrasonic sensor can be timed with a GPIO interrupt and the ToF sensor needs dedicated silicon. At a 50 ms budget the VL53L1X delivers 1/0.050 = 20 readings per second, and the 2-byte result is 40 bytes per second on the bus.
H2: 20.3 Point clouds
P: A multizone ToF sensor (the VL53L5CX reports an 8 × 8 grid over 45° by 45°), a 2-D LiDAR, a depth camera, and the radar of Chapter 16 all produce the same kind of data: a set of points in space. Each zone or beam has a direction; its range along that direction becomes x, y, z. Once the data is a point cloud, the same tools apply to every source: fit planes to find the floor or a wall, cluster points into objects, drop points into a grid (Chapter 16's occupancy grid), and compare clouds to find motion. A microcontroller handles 64 points per frame comfortably; tens of thousands of LiDAR points per second belong on the Pi 5, with NumPy or the Open3D library.
P: Listing 20.3 — Converting an 8 × 8 multizone ToF frame into a point cloud and fitting a plane (Python with NumPy).
P: """Turn an 8 x 8 multizone ToF depth frame into a point cloud and fit the floor plane."""import numpy as npZONES, FOV_DEG = 8, 45.0                     # VL53L5CX-class sensor: 8 x 8 zones, 45 x 45 degdef zone_angles():    step = np.radians(FOV_DEG) / ZONES    a = (np.arange(ZONES) - (ZONES - 1) / 2) * step   # zone centers, radians    return np.meshgrid(a, a)                           # azimuth (columns), elevation (rows)def to_points(depth_mm):    """Each zone reports range along its own ray; convert to x (right), y (up), z (forward), meters."""    az, el = zone_angles()    r = depth_mm / 1000.0    x = r * np.cos(el) * np.sin(az)    y = r * np.sin(el)    z = r * np.cos(el) * np.cos(az)    pts = np.stack([x, y, z], axis=-1).reshape(-1, 3)    return pts[np.isfinite(pts).all(axis=1)]def fit_plane(pts):    """Least-squares plane through the points: returns unit normal and rms distance."""    c = pts.mean(axis=0)    _, _, vt = np.linalg.svd(pts - c)    n = vt[-1]    return n, float(np.sqrt(np.mean(((pts - c) @ n) ** 2)))if __name__ == "__main__":    # Synthetic frame: the sensor looks at a flat wall 1.000 m ahead, with 5 mm range noise.    az, el = zone_angles()    rng = np.random.default_rng(1)    depth = 1000.0 / (np.cos(el) * np.cos(az)) + rng.normal(0, 5, (ZONES, ZONES))    pts = to_points(depth)    n, rms = fit_plane(pts)    print("points:", len(pts), " corner zone range %.0f mm" % depth[0, 0])    print("normal (%.3f, %.3f, %.3f), rms %.1f mm" % (*n, rms * 1000))
H2: Worked Example 20.3: A wall in 64 points
P: Problem. The sensor faces a flat wall 1.000 m away, and each zone reports range along its own ray. What range does a corner zone report, and how well does a plane fit recover the wall with 5 mm of range noise?
P: Solution. With 8 zones over 45°, zone centers are 5.625° apart, and the corner zone sits 3.5 steps = 19.69° off axis in both directions. Its ray meets the wall at 1/(cos 19.69° × cos 19.69°) = 1.128 m, so a corner reading of 1128 mm is correct, not an error: the wall is flat and the ray is long. Listing 20.3 converts all 64 ranges and fits a plane with normal (0.001, −0.002, −1.000), the z axis, with an rms residual of 4.0 mm, consistent with the noise. The usual mistake is to treat every zone's range as the distance straight ahead, which bends a flat wall into a bowl. Check the datasheet: some sensors report the perpendicular distance instead.

H2: 20.4 Event cameras
P: An event camera has no frames. Each pixel reports, on its own, when its brightness changes by more than a threshold: an event of x, y, a timestamp with microsecond resolution, and a polarity (brighter or darker). A static scene produces almost nothing; a moving edge produces a dense stream with no motion blur and a very wide dynamic range. Sony's IMX636, developed with Prophesee, is a 1280 × 720 example. The processing is different too: events are accumulated over a short window into an image, or fed to algorithms that work on the stream directly. Event sensors are established in industrial vibration and counting applications; their wider use in phones, cars, and robots is an outlook, not yet a fact.
P: Listing 20.4 — Generating a synthetic event stream for a moving edge, accumulating it into a 10 ms frame, and comparing the data rate with frames (Python with NumPy).
P: """Event-camera data: accumulate (x, y, t, polarity) events into frames, and estimate data rates."""import numpy as npW, H = 320, 240EVENT_DTYPE = np.dtype([("x", "<u2"), ("y", "<u2"), ("t", "<u4")])   # 8 bytes; polarity in bit 15 of xdef synthetic_edge(speed_px_per_s=1000.0, duration_s=0.1, seed=2):    """A vertical edge sweeping right; every crossed pixel fires one ON event (with timing jitter)."""    rng = np.random.default_rng(seed)    xs = np.arange(int(speed_px_per_s * duration_s))    xx, yy = np.meshgrid(xs, np.arange(H))    t_us = (xx / speed_px_per_s * 1e6 + rng.normal(0, 50, xx.shape)).clip(0)    ev = np.zeros(xx.size, EVENT_DTYPE)    ev["x"] = xx.ravel() | 0x8000          # ON polarity    ev["y"] = yy.ravel()    ev["t"] = t_us.ravel().astype(np.uint32)    return np.sort(ev, order="t")def accumulate(ev, t0_us, window_us):    """Sum polarities (+1 ON, -1 OFF) of the events inside one time window into an image."""    sel = ev[(ev["t"] >= t0_us) & (ev["t"] < t0_us + window_us)]    img = np.zeros((H, W), np.int16)    pol = np.where(sel["x"] & 0x8000, 1, -1)    np.add.at(img, (sel["y"], sel["x"] & 0x7FFF), pol)    return imgif __name__ == "__main__":    ev = synthetic_edge()    rate = len(ev) / 0.1    print("events: %d in 100 ms, %.2f Mev/s, %.2f MB/s at 8 bytes/event" % (len(ev), rate / 1e6, rate * 8 / 1e6))    frame = accumulate(ev, 50_000, 10_000)    cols = np.nonzero(frame.any(axis=0))[0]    print("10 ms window at t = 50 ms: edge spans columns %d..%d" % (cols.min(), cols.max()))    print("same scene as 8-bit frames at 100 fps: %.2f MB/s" % (W * H * 100 / 1e6))
H2: Worked Example 20.4: Events or frames
P: Problem. A vertical edge crosses a 320 × 240 sensor at 1000 pixels per second. Each crossed pixel fires one event of 8 bytes. Compare the event data rate with 8-bit frames at 100 fps.
P: Solution. Each column of 240 pixels fires as the edge passes, 1000 columns per second, so 240 000 events per second; Listing 20.4 counts 24 000 events in 100 ms, 0.24 million events per second and 1.92 MB/s. The frames would be 320 × 240 × 100 = 7.68 MB/s, four times more, and still blurred. In a 10 ms window the edge spans columns 50 to 60, ten pixels, which is its motion in that time. The advantage shrinks for busy scenes: a camera shaking in front of foliage can produce tens of millions of events per second, more than frames, so the choice depends on the scene.

H2: 20.5 Edge AI
P: A neural network trained on a PC can run on the device if it is small enough and stored in integers. Quantization maps each float tensor to int8 with a scale and a zero point, real = scale × (q − zero_point), which cuts the memory by four and lets the chip use fast integer arithmetic: products of int8 values summed in int32. TensorFlow Lite Micro and Espressif's ESP-DL run such models on the ESP32-S3, whose vector instructions speed up exactly those multiply-accumulate loops; typical tasks are wake-word detection, gesture recognition from the IMU, and person detection on 96 × 96 grayscale images. Larger models move to the Pi 5: the Raspberry Pi AI HAT+ adds a Hailo accelerator of 13 or 26 TOPS over PCIe, and the Raspberry Pi AI Camera runs the network inside its Sony IMX500 sensor and outputs results instead of images.
P: Listing 20.5 — Affine int8 quantization and an int8 dot product with int32 accumulation, compared with float (Python with NumPy).
P: """Affine int8 quantization as used by TensorFlow Lite Micro: real = scale * (q - zero_point)."""import numpy as npdef qparams(rmin, rmax):    scale = (rmax - rmin) / 255.0    zero_point = int(round(-128 - rmin / scale))    return scale, zero_pointdef quantize(x, scale, zp):    return np.clip(np.round(x / scale) + zp, -128, 127).astype(np.int8)def dequantize(q, scale, zp):    return scale * (q.astype(np.int32) - zp)if __name__ == "__main__":    s, zp = qparams(-2.0, 6.0)    print("scale %.5f (8/255), zero point %d" % (s, zp))    x = np.array([-2.0, 0.0, 1.0, 3.3, 6.0])    q = quantize(x, s, zp)    print("q =", q.tolist(), " back =", np.round(dequantize(q, s, zp), 4).tolist())    rng = np.random.default_rng(0)    v = rng.uniform(-2, 6, 10_000)    err = np.abs(dequantize(quantize(v, s, zp), s, zp) - v)    print("max error %.5f (scale/2 = %.5f)" % (err.max(), s / 2))    # A dot product the way an int8 kernel does it: int8 x int8 products summed in int32.    w = rng.uniform(-1, 1, 64); a = rng.uniform(-2, 6, 64)    sw, zw = qparams(-1, 1); qw = quantize(w, sw, zw); qa = quantize(a, s, zp)    acc = np.sum((qw.astype(np.int32) - zw) * (qa.astype(np.int32) - zp))    print("float %.4f, int8 %.4f" % (w @ a, sw * s * acc))
H2: Worked Example 20.5: Quantizing an activation
P: Problem. An activation ranges from −2.0 to 6.0. Find the int8 scale and zero point, quantize 1.0 and 3.3, find the largest rounding error, and the memory of a 250 000-parameter model in float32 and int8.
P: Solution. Scale = 8.0/255 = 0.03137; zero point = round(−128 − (−2.0/0.03137)) = round(−64.25) = −64. 1.0 → round(31.9) − 64 = −32, which dequantizes to 1.0039; 3.3 → 105 − 64 = 41 → 3.2941. The largest error is half a step, 0.0157, as Listing 20.5 confirms over 10 000 random values; the rounded zero point shifts the ends slightly, so −2.0 comes back as −2.0078. A 64-element dot product gives 4.1097 in int8 against 4.1143 in float. The model shrinks from 250 000 × 4 = 1 MB to 250 kB, which fits the ESP32-S3's flash and PSRAM with room for the application.

P: Key idea. Optical data comes as one number (ToF), a frame (camera), or a stream (event camera), and the firmware's first job is to reduce it: JPEG in the sensor, a point cloud fitted to a plane, events accumulated over a window, a model quantized to int8.
P: Common misconception. Judging an edge-AI model by its accuracy on the PC. The int8 model on the device sees images from a different camera, with different lighting, at a different resolution. Collect test images with the real device, in the real place, and measure there.
P: AI Pair-Programming Note
P: Assistants give camera pin maps for the wrong board (there are dozens of ESP32 camera boards), pick a frame size that needs PSRAM on a board without it, and claim frame rates without measuring. Put the exact board, the PSRAM size, and the target frame rate in the spec, and run the measurement of Listing 20.1 before trusting any number.
BENCH: A phone camera sees the 940 nm emitter of a ToF sensor or the IR LEDs of a night-vision camera as a faint purple glow (many phones filter it on the main camera; try the front camera). It is the quickest check that the emitter works before you suspect the firmware.
