H1: Chapter 2. Toolchains and Builds: From Source File to Flash
P: You press Build, and forty seconds later a file appears that makes an LED blink on a chip the size of a fingernail. In between, about a dozen programs ran: a preprocessor, a compiler, an assembler, a linker that placed every byte at a fixed address, and a flasher that pushed the result through a USB cable. When something goes wrong in that chain, and it will, the error message comes from one of those programs. Knowing which one is half of fixing it.
P: Where you meet this: The first hour of every new project, every "undefined reference" error, every "region FLASH overflowed" message, and every board that will not accept new firmware.
H2: 2.1 What a build does
P: A C file is text. Turning it into instructions that run on a microcontroller takes four steps. The preprocessor pastes in the header files and expands macros. The compiler translates each C file into machine code for the target processor, an Xtensa core for the ESP32-S3, an Arm Cortex-M for the STM32, RP2040, and nRF52840, and writes one object file per source file. The linker joins the object files and libraries, and places every function and variable at an address, following a linker script that describes the chip's flash and RAM. Finally a converter turns the linked ELF file into the format the flasher wants: a .bin for esptool, a .hex for many Arm programmers, or a .uf2 file that a Pico accepts by drag and drop.
FIG: fig2_1.png | Figure 2.1 — The build pipeline. Source and header files go through the preprocessor and compiler into one object file each; the linker combines them with libraries according to the linker script and writes the ELF file and a map file; a converter writes the image that the flasher sends to the chip. Errors name their stage: "fatal error: no such file" is the preprocessor, "expected ';'" the compiler, "undefined reference" and "region overflowed" the linker. | A left-to-right flow: .c and .h files into preprocessor, then compiler, producing .o files; the .o files, libraries, and a linker script into the linker, producing an .elf file and a .map file; the .elf into a converter producing .bin, .hex, or .uf2; then a flasher arrow into a chip. Under each stage, a typical error message.
P: The ELF file also contains debug information, the map between machine instructions and source lines that a debugger needs (Chapter 23). The map file lists where every symbol landed and how big it is. When the flash fills up, the map file shows which function or table is responsible.
H2: 2.2 The five toolchains of this book
P: ESP-IDF is Espressif's official framework for the ESP32 family. It uses CMake and a command-line tool, idf.py, with three everyday commands: idf.py build, idf.py flash, and idf.py monitor. Its menuconfig screen sets hundreds of options, from the FreeRTOS tick rate to the flash size, and it includes drivers, Wi-Fi, Bluetooth, and FreeRTOS. It is the most complete and the most demanding of the five.
P: The Arduino framework wraps the same chips in a simpler interface: setup() runs once, loop() runs forever, and functions such as digitalWrite() hide the hardware. On an ESP32 the Arduino core sits on top of ESP-IDF, so FreeRTOS is still there underneath. Its strength is its libraries; its weakness is that the hidden layers make timing and power harder to control.
P: PlatformIO is a build system and package manager that runs inside VS Code. One small file, platformio.ini, names the board, the framework, the serial speed, and the libraries with their versions, and PlatformIO downloads the right compiler and libraries for each project. It handles ESP32, Pico, STM32, nRF52, and Teensy boards with the same commands, and it pins library versions, which matters more than it seems (Section 2.4).
P: The Pico SDK is Raspberry Pi's C/C++ kit for the RP2040 and RP2350. It also uses CMake. Its output includes a .uf2 file: hold the BOOTSEL button while plugging in the Pico, it appears as a USB drive, and copying the file onto it flashes the chip. STM32CubeIDE is ST's Eclipse-based IDE. Its configurator, CubeMX, generates the startup code, clock tree, and peripheral setup from a graphical pin map, and its HAL library is what most STM32 code in industry is written against (Chapter 11).
P: Listing 2.1 — Blinking an LED with ESP-IDF on the ESP32-S3 (C). Build and flash with idf.py build flash monitor.
P: // Blink an external LED on GPIO 4 of an ESP32-S3 (ESP-IDF 5.x).// Wire: GPIO 4 -> 330 ohm -> LED anode, LED cathode -> GND.#include "freertos/FreeRTOS.h"#include "freertos/task.h"#include "driver/gpio.h"#define LED_GPIO GPIO_NUM_4void app_main(void){    gpio_reset_pin(LED_GPIO);    gpio_set_direction(LED_GPIO, GPIO_MODE_OUTPUT);    int level = 0;    while (1) {        level = !level;        gpio_set_level(LED_GPIO, level);        vTaskDelay(pdMS_TO_TICKS(500));   // 0.5 s on, 0.5 s off    }}

P: Listing 2.3 — The same blink with the Pico SDK (C), with a counter printed over USB serial.
P: // Blink the on-board LED of a Raspberry Pi Pico (Pico SDK).// GPIO 25 is the LED on the original Pico; the Pico W routes it through the radio chip.#include <stdio.h>#include "pico/stdlib.h"#define LED_PIN 25int main(void){    stdio_init_all();               // printf over USB serial    gpio_init(LED_PIN);    gpio_set_dir(LED_PIN, GPIO_OUT);    unsigned n = 0;    while (true) {        gpio_put(LED_PIN, 1);        sleep_ms(500);        gpio_put(LED_PIN, 0);        sleep_ms(500);        printf("blink %u\n", ++n);    }}
P: The three listings do the same thing and show the family resemblance. Each sets a pin as output, writes it high and low, and waits. The ESP-IDF version waits with vTaskDelay, a FreeRTOS call that lets other tasks run; the Pico version busy-waits in sleep_ms, which is fine on a chip that has nothing else to do. Chapter 13 explains why that difference matters.
H2: 2.3 Reading the size report
P: Every toolchain prints a size report after linking, and it is worth reading every time. The GNU tool size prints three numbers. Text is code and constant data, stored in flash. Data is initialized variables: they occupy flash, which holds their starting values, and RAM, where they live while the program runs. Bss is variables that start at zero; they occupy only RAM. So flash used is text plus data, and static RAM used is data plus bss. The stack and the heap come on top of the static RAM, and the linker script reserves room for them.
EQ: flash = text + data,    static RAM = data + bss
H2: Worked Example 2.1: Will it fit?
P: Problem. An STM32F411 project (512 KB flash, 128 KB RAM) reports text = 38 412, data = 1 204, bss = 6 880 bytes. Find the flash and RAM used and the percentages. The linker script reserves 1 KB of stack and 512 bytes of heap. How much RAM is left?
P: Solution. Flash = 38 412 + 1 204 = 39 616 bytes, which is 39 616/524 288 = 7.6 % of 512 KB. Static RAM = 1 204 + 6 880 = 8 084 bytes, 8 084/131 072 = 6.2 %. With 1024 bytes of stack and 512 of heap, 9 620 bytes are committed and 131 072 − 9 620 = 121 452 bytes remain. The trap is the stack: 1 KB is CubeIDE's default minimum, and a single 1 KB local buffer in a function uses all of it. The linker does not check the stack's real depth; Chapter 13 shows how to measure it.

H2: 2.4 Flashing and the serial monitor
P: Flashing moves the image from the PC into the chip's flash. The ESP32-S3 can be flashed through a USB-to-UART bridge or through its own USB port, which also provides a serial console and a JTAG debugger without extra hardware. The Pico takes a .uf2 file by drag and drop or through picotool. STM32 boards are flashed through an ST-LINK probe over SWD, the two-wire debug port of Chapter 23.
H2: Worked Example 2.2: How long does flashing take?
P: Problem. An ESP32-S3 image is 1 200 000 bytes. It is flashed over a USB-to-UART bridge at 921 600 baud with 8N1 framing (10 bits per byte). Estimate the transfer time without compression. Why is the real time shorter?
P: Solution. The byte rate is 921 600/10 = 92 160 bytes per second, so 1 200 000/92 160 = 13.0 s. esptool compresses the image before sending it and the chip decompresses it on the fly, so a firmware image with large zero-filled or repetitive regions often goes over in less than half that time. Over the native USB port the link is not limited by a UART baud rate at all. A common mistake is to raise the baud rate further on a long or cheap USB cable and then blame the firmware for the checksum errors.
P: Library versions deserve the same care as pin numbers. An example that uses version 2 of a library can fail to compile against version 3, or, worse, compile and behave differently. PlatformIO's lib_deps and ESP-IDF's component manager both let you pin a version; do it as soon as a project works, and record the toolchain version in the README.
P: AI Pair-Programming Note
P: Assistants often mix framework conventions: an ESP-IDF answer with Arduino's delay(), a Pico SDK file with an STM32 HAL include, or an API from an older ESP-IDF major version. State the framework and its version in the first line of the prompt, and paste the compiler's exact error message, not a summary, when asking for a fix.
BENCH: When a board refuses to flash, work through the chain in order: is the right serial port selected, is another program (a serial monitor) holding it open, is the cable a data cable rather than a charge-only cable, and does the chip enter its boot mode? On the ESP32-S3 that means holding BOOT while tapping RESET; on the Pico, holding BOOTSEL while plugging in. Most "dead" boards are one of those four.
