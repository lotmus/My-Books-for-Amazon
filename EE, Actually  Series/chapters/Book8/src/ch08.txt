H1: Chapter 8. The ADC: Sampling, Scaling, and Calibration
P: Two identical ESP32-S3 boards measure the same 18650 cell and disagree by 80 millivolts. Neither is broken. Each chip's analog-to-digital converter has its own small offset and gain error, and 80 mV is the difference between "60 % charged" and "time to shut down". Firmware turns a raw code into a trustworthy voltage in three steps, scale, average, calibrate, and this chapter does all three on the reader lab's battery.
P: Where you meet this: Battery monitors, potentiometers and joysticks, analog sensors such as thermistors, light sensors, and current-sense amplifiers, and every number on a dashboard that started as a voltage.
H2: 8.1 From voltage to code and back
P: An N-bit ADC divides its input range into 2^N steps and returns the number of the step the input falls in. With a 3.3 V reference and 12 bits, one step, one LSB, is 3.3/4096 = 0.806 mV. Converting back is the same arithmetic in reverse, and a divider in front of the pin multiplies the result by its ratio. Book 1 owns the ADC as a circuit: sampling, the reference, and why the input needs a low source impedance. Firmware owns the arithmetic and the errors that are left over.
EQ: code = V_in / V_ref × 2^N,    V_in = code × V_ref / 2^N
P: The microcontrollers in this book differ. The RP2040 on the Pico has a 12-bit ADC whose reference is its 3.3 V supply, so any error in that rail is an error in every reading. The ESP32-S3 has two 12-bit ADCs with selectable input attenuation; at the 12 dB setting the usable range is roughly 0 to 3.1 V, and the chip stores factory calibration data that ESP-IDF's calibration driver applies. ADC2 on the ESP32 family is shared with the Wi-Fi radio, so use ADC1 pins for anything measured while Wi-Fi runs. The STM32 parts have 12-bit converters with an internal reference channel that firmware can measure to correct for the supply.
H2: Worked Example 8.1: Reading the 18650 on a Pico
P: Problem. The reader lab's 18650 cell, at 3.70 V, is measured through a 100 kΩ/100 kΩ divider by a Pico (12 bits, 3.3 V reference). Find the pin voltage, the ideal code, the voltage the code converts back to, and the divider's current drain.
P: Solution. The divider halves the voltage: 1.850 V at the pin. Code = 1.850/3.3 × 4096 = 2296.2, so the ADC returns 2296. Back: 2296 × 3.3/4096 × 2 = 3.6996 V, within one LSB of the truth, 1.6 mV at the cell. The divider draws 3.70 V/200 kΩ = 18.5 µA all the time. That sounds tiny, but it is more than twice the ESP32-S3's deep-sleep current, which matters for the battery budgets of Chapter 14 and Book 6. Raise the divider to 1 MΩ/1 MΩ (1.85 µA) with a 100 nF capacitor at the pin to supply the sampling charge, or switch the divider with a MOSFET (Book 2).
P: Listing 8.1 — Battery voltage on a Pico with a divider and 16-sample averaging (MicroPython).
P: # MicroPython on a Pico: 18650 cell voltage through a 100k/100k divider on GPIO 26 (ADC0).from machine import ADCimport timeadc = ADC(26)VREF = 3.3            # replace with the measured 3V3 rail for better accuracyDIVIDER = 2.0         # (100k + 100k) / 100kdef cell_volts(n=16):    total = 0    for _ in range(n):        total += adc.read_u16() >> 4      # read_u16 scales to 16 bits; the ADC has 12    code = total / n    return code * VREF / 4096 * DIVIDERwhile True:    v = cell_volts()    state = "LOW - shut down soon" if v < 3.3 else "ok"    print("cell %.3f V  %s" % (v, state))    time.sleep(5)
H2: 8.2 Averaging
P: Every ADC reading carries noise: from the reference, the supply, the input, and the converter itself. Averaging n readings reduces random noise by the square root of n, so 16 readings cut it by a factor of 4, two bits' worth. Averaging only helps if the noise is random and at least about one LSB; a perfectly quiet input that sits between two codes always reads the same code, and averaging cannot recover the fraction. That is why a little noise, called dither, can improve resolution.
EQ: σ_avg = σ / √n
H2: Worked Example 8.2: How many samples?
P: Problem. Single readings of a steady input scatter with a standard deviation of 3 LSB on a 3.3 V, 12-bit ADC. How many samples must be averaged to bring the noise below 1 mV? How long does that take at 10 µs per conversion?
P: Solution. 3 LSB is 3 × 0.806 = 2.42 mV. To reach 1 mV the noise must fall by a factor of 2.42, so n ≥ 2.42² = 5.9; use 8, the next power of two, which gives 2.42/√8 = 0.85 mV. Eight conversions take 80 µs, negligible for a battery read every few seconds. The usual mistake is to average many more samples than needed and miss a fast change; averaging is also a low-pass filter, which Chapter 15 makes precise.

H2: 8.3 Calibration
P: After averaging, what remains is systematic: an offset (the code at 0 V is not 0) and a gain error (the slope is not exactly V_ref/2^N). Both are fixed for a given chip, so two measurements of known voltages correct them. Apply a reference voltage near the bottom of the range and one near the top, record the codes, and fit a straight line through the two points. Store the two constants in flash, and use them in every conversion. The ESP32-S3's factory calibration does the same with data measured at the factory, and a two-point bench calibration on top of it removes most of what remains, including the divider's resistor tolerances.
P: Listing 8.2 — Two-point calibration and integer averaging, tested on the PC with the numbers of Worked Example 8.3 (C).
P: // Two-point ADC calibration and averaging; pure C, tested on the PC with bench numbers.#include <stdint.h>#include <stdio.h>typedef struct { float gain_v_per_code; float offset_v; } adc_cal_t;// Measured on the bench: code c1 at v1 and code c2 at v2 from a reference source.static adc_cal_t adc_cal_two_point(uint16_t c1, float v1, uint16_t c2, float v2){    adc_cal_t cal;    cal.gain_v_per_code = (v2 - v1) / (float)(c2 - c1);    cal.offset_v = v1 - cal.gain_v_per_code * (float)c1;    return cal;}static float adc_to_volts(const adc_cal_t *cal, uint16_t code){    return cal->offset_v + cal->gain_v_per_code * (float)code;}// Average n samples (n <= 64) with an integer sum, then convert once.static uint16_t adc_average(const uint16_t *s, unsigned n){    uint32_t sum = 0;    for (unsigned i = 0; i < n; i++) sum += s[i];    return (uint16_t)((sum + n / 2) / n);             // rounded mean}int main(void){    adc_cal_t cal = adc_cal_two_point(412, 0.500f, 3690, 3.000f);    printf("gain %.1f uV/code, offset %.4f V\n", cal.gain_v_per_code * 1e6, cal.offset_v);    const uint16_t s[4] = {2398, 2401, 2403, 2398};    uint16_t code = adc_average(s, 4);    printf("code %u -> %.4f V calibrated, %.4f V ideal (3.3 V / 4096)\n",           (unsigned)code, adc_to_volts(&cal, code), code * 3.3f / 4096.0f);    return 0;}
H2: Worked Example 8.3: A two-point calibration
P: Problem. A bench supply checked with a good multimeter gives 0.500 V and 3.000 V. The ADC reads codes 412 and 3690. Find the gain and offset, and convert an averaged code of 2400 with the calibration and with the ideal formula.
P: Solution. Gain = (3.000 − 0.500)/(3690 − 412) = 2.5/3278 = 762.7 µV per code, against the ideal 805.7 µV. Offset = 0.500 − 412 × 762.7 µV = 0.186 V. Code 2400 gives 0.186 + 2400 × 762.7 µV = 2.016 V calibrated, and 2400 × 3.3/4096 = 1.934 V ideal: an 83 mV difference, 4 % of the reading. Listing 8.2 prints exactly these values. The usual mistakes are to calibrate with the meter's probes on the board's connector rather than where the reference is applied, so the divider's own error is not included, and to calibrate at one point only, which fixes the offset or the gain but not both.

P: Listing 8.3 — ESP32-S3 one-shot ADC with the chip's curve-fitting calibration and 16-sample averaging (ESP-IDF, C).
P: // ESP32-S3 one-shot ADC read with the chip's calibration (ESP-IDF 5.x).// GPIO 4 is ADC1 channel 3 on the ESP32-S3.#include <stdbool.h>#include "freertos/FreeRTOS.h"#include "freertos/task.h"#include "esp_adc/adc_oneshot.h"#include "esp_adc/adc_cali.h"#include "esp_adc/adc_cali_scheme.h"#include "esp_log.h"static const char *TAG = "adc";void app_main(void){    adc_oneshot_unit_handle_t adc;    const adc_oneshot_unit_init_cfg_t ucfg = { .unit_id = ADC_UNIT_1 };    ESP_ERROR_CHECK(adc_oneshot_new_unit(&ucfg, &adc));    const adc_oneshot_chan_cfg_t ccfg = { .atten = ADC_ATTEN_DB_12, .bitwidth = ADC_BITWIDTH_12 };    ESP_ERROR_CHECK(adc_oneshot_config_channel(adc, ADC_CHANNEL_3, &ccfg));    adc_cali_handle_t cali;    const adc_cali_curve_fitting_config_t kcfg = {        .unit_id = ADC_UNIT_1, .chan = ADC_CHANNEL_3,        .atten = ADC_ATTEN_DB_12, .bitwidth = ADC_BITWIDTH_12,    };    ESP_ERROR_CHECK(adc_cali_create_scheme_curve_fitting(&kcfg, &cali));    while (true) {        int raw = 0, mv = 0, sum_mv = 0;        for (int i = 0; i < 16; i++) {            ESP_ERROR_CHECK(adc_oneshot_read(adc, ADC_CHANNEL_3, &raw));            ESP_ERROR_CHECK(adc_cali_raw_to_voltage(cali, raw, &mv));            sum_mv += mv;        }        ESP_LOGI(TAG, "pin %d mV, cell %d mV", sum_mv / 16, 2 * sum_mv / 16);        vTaskDelay(pdMS_TO_TICKS(5000));    }}
P: Key idea. A raw ADC code is a promise, not a measurement. Scale it, average it to the noise you can afford, and calibrate it against a known reference before you print it with three decimals.
P: AI Pair-Programming Note
P: Assistants often copy an ESP32 example that uses ADC2 while Wi-Fi is running, use the old ADC_ATTEN_DB_11 name or the legacy esp_adc_cal API from ESP-IDF 4, or multiply by 3.3/4095 on one line and by 3.3/4096 on the next. The review checklist's "units and scaling at both ends of the range" catches all three: test the conversion at 0 V and at full scale.
BENCH: Before blaming the ADC, measure the reference. On a Pico, a reading that drifts with the USB cable is usually the 3.3 V rail moving with the load; measure it with the multimeter and, if the drift matters, use an external reference or measure a known voltage on a second channel and scale by it.
