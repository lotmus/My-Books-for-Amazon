H1: Chapter 9. UART and I2C: The BME280 and the GPS
P: Two wires, a pull-up resistor on each, and a dozen chips can share them: the BME280, the OLED, an IMU, and a clock. Two different wires, no clock at all, and a GPS module streams its position to you as plain text at 9600 baud. Most of the reader lab talks to the ESP32-S3 over one of these two buses, and most first-day bugs live in them: the wrong address, the wrong baud rate, a missing pull-up, or a bus that hangs because one transfer never finished.
P: Where you meet this: Every sensor breakout, every GPS and cellular module, every debug console, and every "no device found at 0x76".
H2: 9.1 UART: asynchronous serial
P: A UART sends each byte as a frame: a start bit (low), eight data bits with the least significant bit first, and a stop bit (high). There is no clock line; both ends agree on the bit time in advance, the baud rate, and the receiver re-synchronizes on every start bit. That is why the settings must match exactly: 115 200 baud, 8 data bits, no parity, 1 stop bit, written 115200 8N1. The electrical side, 3.3 V logic levels versus RS-232 and RS-485 line drivers, belongs to Books 1 and 7.
FIG: fig9_1.png | Figure 9.1 — One UART frame: the character 'A' (0x41) at 115 200 baud, 8N1, as a logic analyzer shows it. The start bit, eight data bits sent LSB first (1, 0, 0, 0, 0, 0, 1, 0), and the stop bit each last 8.68 µs; the whole frame takes 86.8 µs. | A digital waveform over 0 to 95 microseconds. Idle high, then a low start bit, then data bits 1, 0, 0, 0, 0, 0, 1, 0, then a high stop bit, with each bit cell 8.68 microseconds wide and labeled with its bit number D0 to D7.
P: Because the receiver samples each bit near its middle, timed from the start edge, the two ends' clocks may differ a little. By the tenth bit an error of e accumulates to 10e bit times, and the sample must still land inside the right bit, so the total mismatch must stay below a few percent. Practical designs keep each side within about 2 %. The error comes from dividing the peripheral clock by an integer, or by an integer plus a fraction on chips with fractional dividers.
H2: Worked Example 9.1: Baud-rate error
P: Problem. Find the actual baud rate and the error for 115 200 baud on (a) a 16 MHz AVR with 16× oversampling and an integer divider, (b) the same chip with 8× oversampling, (c) an STM32 at 84 MHz with 16× oversampling and a 4-bit fractional divider.
P: Solution. (a) The divider is 16 MHz/(16 × 115 200) = 8.68, rounded to 9 (register value 8). The actual rate is 16 MHz/(16 × 9) = 111 111 baud, −3.5 %: too far, and the classic reason a 16 MHz Uno is unreliable at 115 200 with some partners. (b) 16 MHz/(8 × 115 200) = 17.36, rounded to 17: 117 647 baud, +2.1 %, usable. (c) 84 MHz/(16 × 115 200) = 45.57; with sixteenths, 45 + 9/16 = 45.5625, giving 115 226 baud, +0.02 %. The ESP32-S3 and RP2040 also have fractional dividers. When two boards will not talk at a high baud rate, compute this before anything else.
H2: 9.2 GPS: text over UART
P: The reader lab's GPS module speaks NMEA 0183: lines of ASCII text that start with $, carry comma-separated fields, and end with * and a two-digit hexadecimal checksum, the XOR of every character between $ and *. Most modules start at 9600 baud and send a burst of sentences once per second. GGA carries the fix: time, latitude and longitude in degrees and minutes, fix quality, satellites, and altitude. RMC adds speed and date. A parser must check the checksum, reject sentences without a fix, and convert ddmm.mmmm into decimal degrees.
P: Listing 9.1 — NMEA checksum and GGA parsing, with the standard example sentence as a test (Python, runs on the PC, Pi, or MicroPython).
P: """NMEA 0183 checksum and GGA parsing for the reader lab's GPS (runs on the PC or a Pi)."""def nmea_checksum_ok(sentence: str) -> bool:    """XOR of every character between '$' and '*' must equal the two hex digits after '*'."""    if not sentence.startswith("$") or "*" not in sentence:        return False    body, _, given = sentence[1:].partition("*")    calc = 0    for ch in body:        calc ^= ord(ch)    return given[:2].upper() == "%02X" % calcdef parse_gga(sentence: str):    """Return (lat_deg, lon_deg, fix_quality, satellites, altitude_m) or None."""    if not nmea_checksum_ok(sentence):        return None    f = sentence.split("*")[0].split(",")    if not f[0].endswith("GGA") or f[6] == "0":        return None                                   # wrong type or no fix    lat = int(f[2][:2]) + float(f[2][2:]) / 60        # ddmm.mmmm    lon = int(f[4][:3]) + float(f[4][3:]) / 60        # dddmm.mmmm    if f[3] == "S":        lat = -lat    if f[5] == "W":        lon = -lon    return lat, lon, int(f[6]), int(f[7]), float(f[9])if __name__ == "__main__":    s = "$GPGGA,123519,4807.038,N,01131.000,E,1,08,0.9,545.4,M,46.9,M,,*47"    print(nmea_checksum_ok(s), parse_gga(s))    print(nmea_checksum_ok(s.replace("4807", "4808")))   # one corrupted digit -> False
H2: Worked Example 9.2: Checking a GPS sentence
P: Problem. Check and decode $GPGGA,123519,4807.038,N,01131.000,E,1,08,0.9,545.4,M,46.9,M,,*47. How busy is a 9600-baud link carrying about 450 characters of NMEA per second?
P: Solution. XORing every character from G to the last comma gives 0x47, matching the *47, so the sentence is intact; Listing 9.1 confirms it and rejects the same sentence with one digit changed. Latitude 4807.038 N is 48° + 7.038'/60 = 48.1173°; longitude 01131.000 E is 11° + 31.000'/60 = 11.5167°, a point in Munich. Fix quality 1 (GPS fix), 8 satellites, altitude 545.4 m. At 10 bits per character, 450 characters per second are 4500 bit/s, 47 % of the link. Raising the update rate to 5 Hz without raising the baud rate or disabling unneeded sentences overflows it, a common reason for "GPS freezes at 5 Hz".
H2: 9.3 I2C: two wires, many chips
P: I2C uses a clock line, SCL, and a data line, SDA, both open-drain with pull-up resistors (sized in Book 1, and checked for rise time in Book 7). The controller starts a transfer with a START condition, sends a 7-bit address and a read/write bit, and every byte is followed by an acknowledge bit from the receiver. A device that does not exist, or is busy, answers with a NACK. Reading a sensor register is a write of the register number followed by a repeated START and a read.

Below, the SCL and SDA lines are drawn for the first byte.

H2: Worked Example 9.3: The method applied to a driver
P: Problem. Apply the nine steps to the BME280 driver, and find the bus time for one 8-byte burst read of pressure, temperature, and humidity at 100 kHz and 400 kHz.
P: Solution. (1) Spec: Worked Example 1.1's, plus "returns temperature in 0.01 °C, humidity in 0.001 %, pressure in Pa; error codes for NACK and timeout". (2) Modules: bus access (write_reg, read block), calibration read, compensation, and the public read function. (3) Write the compensation first, because it is pure. (4) Review: address, register numbers, and byte order checked against the data sheet; ctrl_hum written before ctrl_meas, because the data sheet says humidity settings take effect only after a ctrl_meas write. (5) PC test: Listing 9.3 with the data sheet vector. (6) Bench: logic analyzer on SDA and SCL, chip ID 0x60, transfers under the 10 ms budget. (7) Commit. (8) Bug report if needed, with the analyzer capture. (9) README with pins and units. Bus time: address and register write, 2 × 9 clocks; address read, 9; eight data bytes, 72; with START, repeated START, and STOP about 100 clock periods in all. At 100 kHz that is about 1.0 ms; at 400 kHz about 0.25 ms. Either fits the budget easily.
P: Key idea. Serial-bus bugs are found with the logic analyzer, not by rereading the code. Decode the bus, compare every byte with the data sheet, and the bug is usually visible in the first capture.
P: Common misconception. The I2C address in the data sheet is the one to type into the code. Some data sheets give the 8-bit form with the read/write bit included, 0xEC for a BME280 at 0x76, or 0x52 for the VL53L1X that most libraries call 0x29. Software almost always wants the 7-bit address. If a scan finds the device at half the value you expected, this is why.
P: AI Pair-Programming Note
P: Generated I2C code often uses the BMP280 or BME680 register map for a BME280, the 8-bit address, the legacy i2c_cmd_link API of ESP-IDF 4 in a version 5 project, or a timeout of portMAX_DELAY, which hangs forever if the sensor is unplugged. Each of these is a line in the review checklist.
BENCH: A bus that worked yesterday and hangs today often has SDA stuck low: a sensor was reset in the middle of a read and is still waiting to send its next bit. The standard recovery is to toggle SCL up to nine times as a GPIO until SDA goes high, then send a STOP. Build it into the driver's init, and the board recovers from a brown-out without a power cycle.
