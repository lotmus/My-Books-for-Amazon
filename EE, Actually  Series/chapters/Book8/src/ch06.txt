PART: Part II. Talking to Hardware
H1: Chapter 6. GPIO, Buttons, and Interrupts
P: Press a cheap push button once and look at the pin with a scope: the contacts slam together, bounce apart, and touch again, five or ten times in a few milliseconds. To the microcontroller, which can read the pin millions of times per second, that one press is a burst of presses. The counter you wrote to count button presses counts seven. Nothing is wrong with the button; the firmware has not been told what a press is, and that is the job of this chapter.
P: Where you meet this: Every button, switch, PIR sensor, encoder, limit switch, and "data ready" line, and every interrupt handler you will ever write.
H2: 6.1 A pin, in software
P: A general-purpose I/O pin is configured by a few settings: direction (input or output), pull-up or pull-down resistor (inputs), drive mode (push-pull or open-drain, outputs), and interrupt trigger. The electrical side, logic levels, why a floating input reads random values, and how to size an external pull-up, is Book 1's. The firmware's job is to set those options deliberately, in one place, from the spec's pin table.
P: Not every pin is free. On the ESP32-S3, GPIO 0, 3, 45, and 46 are strapping pins, read at reset to choose the boot mode, so an external circuit that pulls them the wrong way stops the board from booting. GPIO 19 and 20 are the USB data lines, and GPIO 26 to 32 connect to the module's flash and PSRAM; modules with octal PSRAM also use GPIO 33 to 37. On the RP2040 every GPIO is 3.3 V only. The spec's pin table is the place to check all of this, before the board is laid out.
H2: 6.2 Debouncing
P: There are two families of debounce. Time lockout: accept the first edge, then ignore the pin for a fixed time, typically 20 to 50 ms. It is fast and simple, and it accepts a single noise spike as a press. Sampling: read the pin at a fixed rate, every 5 ms for example, and accept a new level only after several identical samples in a row. It rejects spikes and is the usual choice for products. Both are a few lines of C, and both are pure logic that can be tested on the PC with recorded sample sequences, which is how Listing 6.1 checks itself.
P: Listing 6.1 — A sampled debouncer with a PC test that replays a bouncing press and release (C).
P: // Sampled debouncer: call every 5 ms; the output changes after 4 equal samples.// Pure logic, so it is unit-tested on the PC before it ever sees a button.#include <stdbool.h>#include <stdint.h>#include <stdio.h>#define DEBOUNCE_SAMPLES 4utypedef struct {    bool    stable;     // debounced level    uint8_t count;      // consecutive samples that disagree with 'stable'} debounce_t;// Returns true exactly once per accepted change of level.static bool debounce_update(debounce_t *d, bool raw){    if (raw == d->stable) {        d->count = 0;        return false;    }    if (++d->count >= DEBOUNCE_SAMPLES) {        d->stable = raw;        d->count = 0;        return true;    }    return false;}int main(void){    // Raw samples every 5 ms: released (1), a bouncing press, held, then released.    const bool raw[] = {1, 1, 0, 1, 0, 0, 0, 0, 0, 0, 1, 0, 1, 1, 1, 1, 1};    debounce_t d = { .stable = true, .count = 0 };    for (unsigned i = 0; i < sizeof raw / sizeof raw[0]; i++) {        if (debounce_update(&d, raw[i]))            printf("t = %3u ms: level -> %d\n", i * 5u, d.stable);    }    return 0;   // prints: t = 35 ms: level -> 0, t = 75 ms: level -> 1}
H2: Worked Example 6.1: How fast is a debounced button?
P: Problem. A button bounces for up to 3 ms. The debouncer of Listing 6.1 samples every 5 ms and needs 4 equal samples. What is the shortest and longest delay from the first contact to the accepted press? Does it meet a spec of "recognized within 50 ms"?
P: Solution. The bouncing ends at most 3 ms after first contact. The first sample that is certain to be clean comes at the next sample instant, 0 to 5 ms later, and the press is accepted at the fourth clean sample, 15 ms after that, so the longest delay is 3 + 5 + 15 = 23 ms. The shortest is 15 ms, when the first sample falls at the moment of contact and every sample happens to read low. Both meet 50 ms with margin. In Listing 6.1's test the first low sample is at 10 ms, the bounce resets the count at 15 ms, and the four clean samples at 20, 25, 30, and 35 ms accept the press at 35 ms.

H2: 6.3 Interrupts
P: Polling reads a pin in the main loop; an interrupt makes the hardware call a function, the interrupt service routine (ISR), the moment an edge arrives. Interrupts react within microseconds and let the processor sleep between events, which Chapter 14 depends on. Their cost is that the ISR runs in the middle of whatever the program was doing, so it must be short and must not break the interrupted code.
P: Four rules keep ISRs safe. Do the minimum: record a timestamp, set a flag, or send a small item to a queue, and leave the work to the main loop or a task. Never block: no delays, no waiting for a bus, no printf, no malloc. Share data safely: a variable that the ISR writes and the main code reads must be volatile, and anything larger than one machine word needs a critical section or a queue. On the ESP32, mark the ISR IRAM_ATTR so it is in RAM and can run while the flash cache is busy.
P: Listing 6.2 — The PIR sensor on an interrupt: the ISR timestamps the edge and queues it; a FreeRTOS task logs it (ESP-IDF, C).
P: // PIR motion sensor on GPIO 5 of an ESP32-S3 (ESP-IDF 5.x): the interrupt only// queues an event; a task does the slow work (logging, display, camera).#include <stdint.h>#include "freertos/FreeRTOS.h"#include "freertos/queue.h"#include "freertos/task.h"#include "driver/gpio.h"#include "esp_log.h"#include "esp_timer.h"#define PIR_GPIO GPIO_NUM_5static const char *TAG = "pir";static QueueHandle_t pir_queue;static void IRAM_ATTR pir_isr(void *arg){    int64_t t_us = esp_timer_get_time();          // ISR-safe timestamp    BaseType_t woken = pdFALSE;    xQueueSendFromISR(pir_queue, &t_us, &woken);  // never block in an ISR    if (woken) portYIELD_FROM_ISR();}static void pir_task(void *arg){    int64_t t_us;    for (;;) {        if (xQueueReceive(pir_queue, &t_us, portMAX_DELAY) == pdTRUE)            ESP_LOGI(TAG, "motion at %lld ms", (long long)(t_us / 1000));    }}void app_main(void){    pir_queue = xQueueCreate(8, sizeof(int64_t));    const gpio_config_t cfg = {        .pin_bit_mask = 1ULL << PIR_GPIO,        .mode = GPIO_MODE_INPUT,        .pull_up_en = GPIO_PULLUP_DISABLE,        .pull_down_en = GPIO_PULLDOWN_ENABLE,     // PIR output idles low        .intr_type = GPIO_INTR_POSEDGE,           // motion = rising edge    };    ESP_ERROR_CHECK(gpio_config(&cfg));    ESP_ERROR_CHECK(gpio_install_isr_service(0));    ESP_ERROR_CHECK(gpio_isr_handler_add(PIR_GPIO, pir_isr, NULL));    xTaskCreate(pir_task, "pir", 3072, NULL, 5, NULL);}
P: A PIR sensor module already produces a clean, slow output: it goes high for a few seconds when it sees motion, so it needs no debouncing, and a rising-edge interrupt is the natural trigger. A mechanical button is different: an edge interrupt on a bouncing contact fires several times. The common fix combines both techniques: the interrupt wakes the system or records the time, and a lockout or sampling debounce in the main code decides whether it was a real press, as Listing 6.3 does in MicroPython.
P: Listing 6.3 — A button interrupt that records only the time, with a 50 ms lockout in the main loop (MicroPython).
P: # MicroPython (Pico or ESP32-S3): a button interrupt that only records the time;# the main loop applies a 50 ms lockout and does the work.from machine import Pinimport timebutton = Pin(14, Pin.IN, Pin.PULL_UP)     # button to GND, active lowlast_edge = 0pressed = Falsedef on_edge(pin):    global last_edge, pressed    last_edge = time.ticks_ms()    pressed = True                       # keep the handler tinybutton.irq(trigger=Pin.IRQ_FALLING, handler=on_edge)count = 0while True:    if pressed and time.ticks_diff(time.ticks_ms(), last_edge) > 50:        pressed = False        if button.value() == 0:          # still held after the bounces: a real press            count += 1            print("press", count)    time.sleep_ms(5)
H2: Worked Example 6.2: The interrupt budget of a rotary encoder
P: Problem. A rotary encoder knob gives 20 detents per turn with 4 edges per detent on its two channels. A user spins it at up to 3 turns per second. Each ISR takes 2.5 µs on a 240 MHz ESP32-S3. How many interrupts per second, and what fraction of the CPU do they use?
P: Solution. 20 × 4 = 80 edges per turn, × 3 turns per second = 240 edges per second. At 2.5 µs each that is 600 µs per second, 0.06 % of one core. The interrupt load is negligible; the risk lies elsewhere. If the ISR also updated the OLED, at about 25 ms per update over I2C (Chapter 10), 240 updates per second would need 6 s of work every second. That is why the ISR only counts, and the display reads the count ten times per second.
P: Key idea. An interrupt handler records that something happened; the rest of the program decides what it means and does the work. Short handlers, queues, and flags keep every other deadline intact.
P: Common misconception. Interrupts are always better than polling. Polling a slow input every few milliseconds in a loop that already runs that often costs almost nothing and cannot cause a race condition. Interrupts earn their complexity when the event is short, rare, or must wake the chip from sleep.
P: AI Pair-Programming Note
P: Generated ISR code often calls Serial.println, printf, or ESP_LOGI inside the handler, uses delay() for debouncing inside the ISR, or forgets the pull-up. Search every ISR for any call that can block or print, and compare every pin's pull configuration with the spec's pin table.
BENCH: To see how long your ISR really takes, set a spare GPIO high at the start of the ISR and low at the end, and measure the pulse on a scope or logic analyzer. The same trick, on the edge that triggers the interrupt and the GPIO, measures the interrupt latency. Two pins and two lines of code replace a lot of guessing.
